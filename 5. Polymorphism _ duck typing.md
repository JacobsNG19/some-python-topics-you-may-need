Polymorphism means “one interface, many forms”: the same operation can work with different kinds of objects. **Duck typing** is Python’s practical version of this idea—if an object supports the behavior your code needs, Python usually lets you use it, regardless of its exact class. Python is dynamically and strongly typed: variables do not have fixed types, while unsupported operations fail when attempted.[[en.wikipedia](https://en.wikipedia.org/wiki/Python_\(programming_language\))]

# 1. The central idea

The word **polymorphism** comes from Greek:

```
poly = many
morph = forms
```

In programming, it means that different objects can respond to the same method call in their own way.

Example:

```
class Dog:
    def speak(self):
        return "Woof!"


class Cat:
    def speak(self):
        return "Meow!"


class Cow:
    def speak(self):
        return "Moo!"
```

All three objects have a `speak()` method:

```
animals = [Dog(), Cat(), Cow()]

for animal in animals:
    print(animal.speak())
```

Output:

```
Woof!
Meow!
Moo!
```

The loop does not need to ask:

```
if type(animal) == Dog:
    ...
elif type(animal) == Cat:
    ...
```

It simply says:

```
animal.speak()
```

Each object provides its own implementation. That is polymorphism.

---

# 2. Why polymorphism matters

Without polymorphism, code becomes full of long `if`/`elif` chains.

## Weak design

```
def make_sound(animal):
    if isinstance(animal, Dog):
        return "Woof!"

    elif isinstance(animal, Cat):
        return "Meow!"

    elif isinstance(animal, Cow):
        return "Moo!"

    else:
        raise ValueError("Unknown animal.")
```

Every time you add a new animal, you must edit the function.

```
class Bird:
    pass
```

Now you must go back and modify `make_sound()`.

## Better design

```
def make_sound(animal):
    return animal.speak()
```

Now any object that supports `.speak()` can work:

```
class Bird:
    def speak(self):
        return "Chirp!"
```

```
animals = [Dog(), Cat(), Cow(), Bird()]

for animal in animals:
    print(make_sound(animal))
```

Output:

```
Woof!
Meow!
Moo!
Chirp!
```

You extend the system by adding new classes—not by continually rewriting existing logic.

This becomes extremely useful in real AI systems:

- Different LLM providers: OpenAI, Anthropic, local models
- Different storage backends: PostgreSQL, Redis, files
- Different payment providers
- Different notification channels: email, SMS, Slack
- Different data sources
- Different model-evaluation strategies
- Different agent tools

---

# 3. Polymorphism vs inheritance

Polymorphism and inheritance are related, but they are not the same thing.

|Concept|Meaning|Example|
|---|---|---|
|Inheritance|A class derives from another class|`Dog(Animal)`|
|Polymorphism|One interface works with many object types|`animal.speak()`|
|Duck typing|Behavior matters more than inheritance|Any object with `.speak()` works|
|Method overriding|A child class replaces a parent’s method|`Dog.speak()` replaces `Animal.speak()`|

Inheritance is one way to organize polymorphism. Duck typing means you often do **not** need inheritance at all.

# 4. Basic polymorphism with methods

Let’s begin from scratch.

```
class Circle:
    def area(self):
        return 3.14159 * 5 ** 2


class Square:
    def area(self):
        return 4 ** 2
```

Use them in one function:

```
def print_area(shape):
    print(f"Area: {shape.area()}")
```

```
circle = Circle()
square = Square()

print_area(circle)
print_area(square)
```

Output:

```
Area: 78.53975
Area: 16
```

The function does not care whether the object is a `Circle` or a `Square`.

It only needs this contract:

```
The object must have an area() method.
```

That contract is the important idea.

---

# 5. Duck typing 🦆

Duck typing comes from this saying:

> “If it walks like a duck and quacks like a duck, then it can be treated as a duck.”

In Python:

> If an object has the methods and behavior your code needs, it can be used—even if it does not inherit from a particular class.

Example:

```
class Duck:
    def sound(self):
        return "Quack!"


class Person:
    def sound(self):
        return "I can imitate a duck: quack!"
```

```
def make_sound(entity):
    print(entity.sound())
```

```
make_sound(Duck())
make_sound(Person())
```

Output:

```
Quack!
I can imitate a duck: quack!
```

`Person` is not a subclass of `Duck`.

```
isinstance(Person(), Duck)
```

is:

```
False
```

But it works because `Person` provides the behavior the function requires:

```
.sound()
```

That is duck typing.

Python’s design emphasizes this practical, behavior-based style rather than requiring type declarations for every variable.[[en.wikipedia](https://en.wikipedia.org/wiki/Python_\(programming_language\))]

# 6. The most important duck-typing rule

Do not ask:

```
"What type is this object?"
```

Ask:

```
"Can this object do what I need?"
```

## Less Pythonic

```
def save_document(document):
    if isinstance(document, PDFDocument):
        document.save()

    elif isinstance(document, WordDocument):
        document.save()

    else:
        raise TypeError("Unsupported document type.")
```

## More polymorphic

```
def save_document(document):
    document.save()
```

Any object with:

```
.save()
```

will work.

```
class PDFDocument:
    def save(self):
        return "PDF saved."


class WordDocument:
    def save(self):
        return "Word document saved."


class MarkdownDocument:
    def save(self):
        return "Markdown document saved."
```

```
documents = [
    PDFDocument(),
    WordDocument(),
    MarkdownDocument(),
]

for document in documents:
    print(save_document(document))
```

Output:

```
PDF saved.
Word document saved.
Markdown document saved.
```

This makes your code easier to extend.

# 7. Polymorphism through inheritance

Inheritance-based polymorphism starts with a parent class.

```
class Animal:
    def speak(self):
        return "Some generic animal sound."
```

Then child classes override the method.

```
class Dog(Animal):
    def speak(self):
        return "Woof!"


class Cat(Animal):
    def speak(self):
        return "Meow!"


class Cow(Animal):
    def speak(self):
        return "Moo!"
```

Use all objects the same way:

```
animals = [Dog(), Cat(), Cow()]

for animal in animals:
    print(animal.speak())
```

Output:

```
Woof!
Meow!
Moo!
```

## Method overriding

When a child class defines a method with the same name as its parent, the child version replaces the parent version for child objects.

```
class Vehicle:
    def move(self):
        return "The vehicle moves."


class Car(Vehicle):
    def move(self):
        return "The car drives on roads."


class Boat(Vehicle):
    def move(self):
        return "The boat sails on water."


class Airplane(Vehicle):
    def move(self):
        return "The airplane flies in the sky."
```

```
vehicles = [Car(), Boat(), Airplane()]

for vehicle in vehicles:
    print(vehicle.move())
```

Output:

```
The car drives on roads.
The boat sails on water.
The airplane flies in the sky.
```

One method name:

```
.move()
```

Many implementations.

# 8. `super()` in polymorphic classes

Sometimes a subclass wants to extend the parent’s behavior rather than entirely replace it.

```
class Employee:
    def work(self):
        return "Completing general company tasks."
```

```
class AIEngineer(Employee):
    def work(self):
        base_work = super().work()

        return (
            f"{base_work} "
            "Building, evaluating, and deploying AI systems."
        )
```

Usage:

```
engineer = AIEngineer()

print(engineer.work())
```

Output:

```
Completing general company tasks. Building, evaluating, and deploying AI systems.
```

`super()` calls the parent-class implementation.

This is useful when the parent class provides shared behavior such as:

- Logging
- Input validation
- Authentication
- Error handling
- Database setup
- Rate limiting
- Common preprocessing
- Shared metrics

# 9. Parent classes as contracts

A base class can define what child classes are expected to implement.

```
class PaymentProcessor:
    def pay(self, amount):
        raise NotImplementedError(
            "Subclasses must implement pay()."
        )
```

Child classes:

```
class MobileMoneyProcessor(PaymentProcessor):
    def pay(self, amount):
        return f"Paid {amount} using Mobile Money."


class CardProcessor(PaymentProcessor):
    def pay(self, amount):
        return f"Paid {amount} using a bank card."


class CryptoProcessor(PaymentProcessor):
    def pay(self, amount):
        return f"Paid {amount} using cryptocurrency."
```

Use them polymorphically:

```
def process_checkout(processor, amount):
    return processor.pay(amount)
```

```
processors = [
    MobileMoneyProcessor(),
    CardProcessor(),
    CryptoProcessor(),
]

for processor in processors:
    print(process_checkout(processor, 50))
```

Output:

```
Paid 50 using Mobile Money.
Paid 50 using a bank card.
Paid 50 using cryptocurrency.
```

The checkout system does not need to know the exact payment provider. It relies on the shared `.pay(amount)` interface.

# 10. Abstract base classes (ABCs)

The `NotImplementedError` approach works, but Python provides a more formal method: **abstract base classes**.

An abstract base class defines a required interface. You cannot create an instance of it until its abstract methods are implemented.

```
from abc import ABC, abstractmethod
```

```
class PaymentProcessor(ABC):

    @abstractmethod
    def pay(self, amount):
        pass
```

Now this fails:

```
processor = PaymentProcessor()
```

because `PaymentProcessor` has no concrete `pay()` implementation.

Create a valid subclass:

```
class MobileMoneyProcessor(PaymentProcessor):

    def pay(self, amount):
        if amount <= 0:
            raise ValueError("Payment amount must be positive.")

        return f"Paid {amount} using Mobile Money."
```

```
class CardProcessor(PaymentProcessor):

    def pay(self, amount):
        if amount <= 0:
            raise ValueError("Payment amount must be positive.")

        return f"Paid {amount} by card."
```

```
def checkout(processor, amount):
    return processor.pay(amount)
```

```
print(checkout(MobileMoneyProcessor(), 25))
print(checkout(CardProcessor(), 25))
```

Output:

```
Paid 25 using Mobile Money.
Paid 25 by card.
```

## Why use an ABC?

Use an abstract base class when:

- You own the family of related classes.
- You want a documented, explicit contract.
- A missing method should be caught immediately.
- You want to share base implementations.
- Your team benefits from a formal architecture.
- You are building plugins, frameworks, providers, adapters, or services.

Python’s `functools.singledispatch` can also use abstract base classes when selecting registered implementations.[[docs.python](https://docs.python.org/3/library/functools.html)]

# 11. ABC example for AI model providers

This is a realistic architecture for an AI product.

```
from abc import ABC, abstractmethod
```

```
class LLMProvider(ABC):

    @abstractmethod
    def generate(self, prompt):
        pass
```

```
class LocalModelProvider(LLMProvider):

    def generate(self, prompt):
        return f"Local model response to: {prompt}"
```

```
class CloudModelProvider(LLMProvider):

    def generate(self, prompt):
        return f"Cloud model response to: {prompt}"
```

Now build code that depends on the contract, not the provider:

```
class SupportAssistant:
    def __init__(self, llm_provider):
        self._llm_provider = llm_provider

    def answer_customer(self, question):
        prompt = f"Answer this support question: {question}"

        return self._llm_provider.generate(prompt)
```

Usage:

```
local_provider = LocalModelProvider()
assistant = SupportAssistant(local_provider)

print(
    assistant.answer_customer(
        "How do I reset my password?"
    )
)
```

Later, switch providers:

```
cloud_provider = CloudModelProvider()
assistant = SupportAssistant(cloud_provider)
```

You do not need to rewrite `SupportAssistant`.

This is called **programming to an interface**, and it is one of the most useful forms of polymorphism in production systems.

# 12. Duck typing without a base class

You do not always need an ABC.

```
class EmailNotifier:
    def send(self, message):
        return f"Email sent: {message}"
```

```
class SMSNotifier:
    def send(self, message):
        return f"SMS sent: {message}"
```

```
class SlackNotifier:
    def send(self, message):
        return f"Slack message sent: {message}"
```

One function supports all of them:

```
def notify(notifier, message):
    return notifier.send(message)
```

```
notifiers = [
    EmailNotifier(),
    SMSNotifier(),
    SlackNotifier(),
]

for notifier in notifiers:
    print(notify(notifier, "Your report is ready."))
```

Output:

```
Email sent: Your report is ready.
SMS sent: Your report is ready.
Slack message sent: Your report is ready.
```

None of these classes inherited from a common parent.

They work because they all provide:

```
.send(message)
```

That is pure duck typing.

# 13. EAFP: Python’s duck-typing style

Python often follows a philosophy called **EAFP**:

```
Easier to Ask for Forgiveness than Permission
```

Instead of checking everything before acting, you try the operation and handle an appropriate error if it fails.

## LBYL: “Look Before You Leap”

```
if hasattr(item, "read"):
    content = item.read()
else:
    raise TypeError("Object must provide read().")
```

This is often called LBYL:

```
Look Before You Leap
```

It can be useful, but it has limitations.

## EAFP: preferred in many situations

```
try:
    content = item.read()
except AttributeError as error:
    raise TypeError(
        "Object must provide a read() method."
    ) from error
```

The code simply attempts the behavior it requires.

### Example: accepting a path or file-like object

```
def read_text(source):
    try:
        return source.read()
    except AttributeError:
        with open(source, "r", encoding="utf-8") as file:
            return file.read()
```

This function can accept:

- A file path such as `"notes.txt"`
- An open file object
- A `StringIO` object
- Any custom object with a `.read()` method

That flexibility comes from duck typing.

## Important warning

Do not catch errors too broadly.

Bad:

```
try:
    return item.read()
except Exception:
    return "Something failed."
```

This can hide real bugs inside `item.read()`.

Better:

```
try:
    return item.read()
except AttributeError as error:
    raise TypeError(
        "Expected an object with a read() method."
    ) from error
```

Handle only the error you actually expect.

# 14. `hasattr()`—when it is useful

`hasattr()` checks whether an object appears to have an attribute.

```
class Report:
    def export(self):
        return "Report exported."
```

```
report = Report()

print(hasattr(report, "export"))
```

Output:

```
True
```

You can use it for optional behavior:

```
def close_resource(resource):
    if hasattr(resource, "close"):
        resource.close()
```

This is sensible when `.close()` is genuinely optional.

But if `.save()` is _required_, do not quietly skip it:

```
def save_resource(resource):
    resource.save()
```

Let Python raise an error, or convert it into a clear `TypeError`.

# 15. Duck typing in built-in Python objects

You already use duck typing constantly.

## Iteration

This works:

```
for item in [1, 2, 3]:
    print(item)
```

It also works:

```
for character in "Python":
    print(character)
```

And:

```
for key in {"name": "Toussaint", "role": "AI engineer"}:
    print(key)
```

Lists, strings, tuples, dictionaries, generators, sets, and many custom objects can all be iterated over because they support Python’s iteration protocol.

```
__iter__()
```

or, in some older-compatible cases:

```
__getitem__()
```

The `for` loop does not care whether the object is specifically a list. It cares whether it is iterable.

## Length

```
len([1, 2, 3])
len("TrustDesk")
len({"a": 1, "b": 2})
```

All work because those objects support the length protocol:

```
__len__()
```

## Context managers

This:

```
with open("notes.txt", "r") as file:
    content = file.read()
```

works because the file object supports the context-management protocol:

```
__enter__()
__exit__()
```

Python’s special methods define much of its behavior-based polymorphism.

# 16. Operator polymorphism

Polymorphism also appears in operators.

```
print(2 + 3)
print("Trust" + "Desk")
print([1, 2] + [3, 4])
```

Output:

```
5
TrustDesk
[1, 2, 3, 4]
```

The `+` operator behaves differently depending on object types.

Internally, Python uses special methods such as:

```
__add__()
```

For integers:

```
2 + 3
```

conceptually calls behavior like:

```
int.__add__(2, 3)
```

For strings:

```
"Trust" + "Desk"
```

uses string concatenation behavior.

For lists:

```
[1, 2] + [3, 4]
```

uses list concatenation behavior.

This is operator polymorphism.

# 17. Creating your own operator polymorphism

Suppose you have a `Money` class.

```
class Money:
    def __init__(self, amount, currency="BIF"):
        self.amount = amount
        self.currency = currency

    def __add__(self, other):
        if not isinstance(other, Money):
            return NotImplemented

        if self.currency != other.currency:
            raise ValueError(
                "Cannot add money in different currencies."
            )

        return Money(
            self.amount + other.amount,
            self.currency
        )

    def __repr__(self):
        return f"Money({self.amount}, '{self.currency}')"
```

Usage:

```
budget_a = Money(10_000, "BIF")
budget_b = Money(5_000, "BIF")

total = budget_a + budget_b

print(total)
```

Output:

```
Money(15000, 'BIF')
```

You made this possible:

```
budget_a + budget_b
```

by implementing:

```
__add__()
```

## Why return `NotImplemented`?

If `other` is not a `Money` object:

```
budget_a + 100
```

returning `NotImplemented` tells Python:

> “This class does not know how to add itself to that object.”

Python can then try the other object’s reflected operation, such as `__radd__`, or raise a proper `TypeError`.

This is better than manually returning a confusing value.

# 18. Other useful special methods

Python supports many protocols through special “dunder” methods.

|Behavior|Special method|Example|
|---|---|---|
|Addition|`__add__`|`a + b`|
|Equality|`__eq__`|`a == b`|
|Less than|`__lt__`|`a < b`|
|String display|`__str__`|`str(a)`|
|Developer representation|`__repr__`|`repr(a)`|
|Length|`__len__`|`len(a)`|
|Iteration|`__iter__`|`for x in a`|
|Index access|`__getitem__`|`a[0]`|

|Context manager entry|`__enter__`|`with a:`|
|Context manager exit|`__exit__`|cleanup after `with`|

These methods let your own classes behave naturally with the rest of Python.

# 19. Callable objects with `__call__`

An object can behave like a function.

```
class TextCleaner:
    def __call__(self, text):
        return text.strip().lower()
```

Usage:

```
clean = TextCleaner()

print(clean("  Hello, TrustDesk!  "))
```

Output:

```
hello, trustdesk!
```

The object is not technically a normal function, but it can be called like one because it supports:

```
__call__()
```

This is valuable in ML pipelines.

```
class NormalizeText:
    def __call__(self, text):
        return text.lower().strip()


class RemovePunctuation:
    def __call__(self, text):
        return "".join(
            character
            for character in text
            if character.isalnum() or character.isspace()
        )
```

```
pipeline = [
    NormalizeText(),
    RemovePunctuation(),
]

text = "  Hello, WORLD!!!  "

for transform in pipeline:
    text = transform(text)

print(text)
```

Output:

```
hello world
```

Every pipeline stage can be called with:

```
transform(text)
```

It does not matter whether the stage is:

- A normal function
- A lambda
- A class instance implementing `__call__`
- A third-party callable object

That is polymorphism through Python’s callable protocol.

# 21. `functools.singledispatch`

Python does not support traditional method overloading based only on parameter types in the same way as Java or C++.

This does **not** work as many beginners expect:

```
class Calculator:
    def add(self, a, b):
        return a + b

    def add(self, a, b, c):
        return a + b + c
```

The second definition replaces the first one.

Instead, one option is default arguments:

```
class Calculator:
    def add(self, a, b, c=0):
        return a + b + c
```

For type-based function dispatch, Python provides `functools.singledispatch`. It transforms a function into a generic function and chooses an implementation based on the type of its **first argument**.[[docs.python](https://docs.python.org/3/library/functools.html)]

```
from functools import singledispatch
```

```
@singledispatch
def serialize(value):
    raise TypeError(
        f"Cannot serialize type: {type(value).__name__}"
    )
```

```
@serialize.register
def _(value: str):
    return {"type": "text", "value": value}
```

```
@serialize.register
def _(value: int):
    return {"type": "integer", "value": value}
```

```
@serialize.register
def _(value: list):
    return {
        "type": "list",
        "items": [serialize(item) for item in value],
    }
```

Usage:

```
print(serialize("hello"))
print(serialize(42))
print(serialize(["AI", 2026]))
```

Possible output:

```
{'type': 'text', 'value': 'hello'}
{'type': 'integer', 'value': 42}
{'type': 'list', 'items': [
    {'type': 'text', 'value': 'AI'},
    {'type': 'integer', 'value': 2026}
]}
```

## When to use `singledispatch`

Use it when:

- You are writing a function-oriented API.
- Different input types genuinely require different behavior.
- Dispatching on the first argument makes sense.
- You want to extend behavior without changing the original function.
- You are building serializers, formatters, converters, or parsers.

Avoid it when a well-designed object method would be simpler.

# 22. `singledispatchmethod`

For class methods, Python provides `singledispatchmethod`.

```
from functools import singledispatchmethod
```

```
class DataFormatter:

    @singledispatchmethod
    def format(self, value):
        raise TypeError(
            f"Unsupported type: {type(value).__name__}"
        )

    @format.register
    def _(self, value: str):
        return value.strip().title()

    @format.register
    def _(self, value: int):
        return f"{value:,}"
```

Usage:

```
formatter = DataFormatter()

print(formatter.format("   trustdesk platform "))
print(formatter.format(1250000))
```

Output:

```
Trustdesk Platform
1,250,000
```

The official documentation notes that `singledispatchmethod` turns a method into a generic function in the same style as `singledispatch`.[[docs.python](https://docs.python.org/3/library/functools.html)]

# 23. Structural typing with `Protocol`

Duck typing is dynamic: Python tries the behavior at runtime.

But in larger projects, you may want your editor and static type checker to understand the expected behavior _before_ runtime.

For this, use `typing.Protocol`.

```
from typing import Protocol
```

```
class Notifier(Protocol):
    def send(self, message: str) -> str:
        ...
```

Now define unrelated classes:

```
class EmailNotifier:
    def send(self, message: str) -> str:
        return f"Email: {message}"
```

```
class SMSNotifier:
    def send(self, message: str) -> str:
        return f"SMS: {message}"
```

Use the protocol as a type hint:

```
def alert(notifier: Notifier, message: str) -> str:
    return notifier.send(message)
```

```
print(alert(EmailNotifier(), "Deployment completed."))
print(alert(SMSNotifier(), "Deployment completed."))
```

Output:

```
Email: Deployment completed.
SMS: Deployment completed.
```

Neither class needs to inherit from `Notifier`.

They match structurally because they both provide:

```
send(message: str) -> str
```

This is called **structural subtyping**.

## Why Protocol is powerful

For a professional Python codebase:

- Duck typing keeps code flexible.
- Type hints document expected behavior.
- `Protocol` gives static analysis tools a shared contract.
- You avoid forcing unrelated classes into an artificial inheritance tree.
- IDE autocomplete and tools such as mypy or pyright can find interface mistakes earlier.

For AI-agent systems, protocols are excellent for contracts such as:

```
class LLMClient(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

```
class VectorStore(Protocol):
    def search(self, query: str, limit: int) -> list[str]:
        ...
```

```
class Tool(Protocol):
    def run(self, input_text: str) -> str:
        ...
```

# 24. Runtime-checkable protocols

Normal protocols are mainly for static type checking.

If you need runtime `isinstance()` checks, add `@runtime_checkable`.

```
from typing import Protocol, runtime_checkable
```

```
@runtime_checkable
class Runnable(Protocol):
    def run(self) -> str:
        ...
```

```
class BackupJob:
    def run(self) -> str:
        return "Backup completed."
```

```
job = BackupJob()

print(isinstance(job, Runnable))
```

Output:

```
True
```

Use runtime protocol checks sparingly. In many cases, simply calling the required method and handling a clear failure is more Pythonic.

# 25. Duck typing vs ABC vs Protocol

|Approach|Main purpose|Inheritance required?|Checked when?|Best use case|
|---|---|---|---|---|
|Pure duck typing|Flexibility based on behavior|No|Runtime|Small-to-medium Python code, adapters, simple APIs|
|Abstract base class|Formal runtime contract and shared base behavior|Usually yes|Object creation/runtime|Frameworks, plugins, related provider families|
|`Protocol`|Static structural contract|No|Static analysis, optionally runtime|Large typed projects, APIs, AI systems, teams|
|`singledispatch`|Type-based function behavior|No|Runtime|Serializers, formatters, conversion functions|

## Practical guidance

Choose **duck typing** when:

```
def save(item):
    item.save()
```

is clear, simple, and enough.

Choose an **ABC** when you control a class family and want to enforce implementation:

```
class Storage(ABC):
    @abstractmethod
    def save(self, data):
        ...
```

Choose a **Protocol** when different independent implementations should share a typed interface:

```
class Storage(Protocol):
    def save(self, data: bytes) -> None:
        ...
```

Choose **`singledispatch`** when one standalone function should act differently by first-argument type.

# 26. Liskov substitution principle

A very important advanced rule of polymorphism is the **Liskov Substitution Principle**.

In plain language:

> If a program expects a parent type or interface, any valid child implementation should be usable without breaking the program.

Suppose your code expects a `Bird` that can fly:

```
class Bird:
    def fly(self):
        return "Flying"
```

Then you create:

```
class Penguin(Bird):
    def fly(self):
        raise RuntimeError("Penguins cannot fly.")
```

This is a design problem.

```
def make_bird_fly(bird):
    return bird.fly()
```

```
make_bird_fly(Penguin())
```

fails.

The issue is not that penguins are wrong. The issue is that the parent class made a false promise: it implied all birds can fly.

## Better design

```
class Bird:
    def move(self):
        return "The bird moves."
```

```
class FlyingBird(Bird):
    def fly(self):
        return "Flying."
```

```
class Penguin(Bird):
    def swim(self):
        return "Swimming."
```

Now your abstractions reflect reality.

For software systems, this means:

- Do not make a subclass unexpectedly reject valid parent-class operations.
- Do not change expected return types without reason.
- Do not require stronger input restrictions in child classes.
- Do not remove behavior the parent contract promised.
- Keep interfaces small and truthful.

# 27. Composition often beats inheritance

A major lesson: not every “has a behavior” relationship needs inheritance.

Instead of this:

```
class EmailReportGenerator:
    ...
```

```
class SlackReportGenerator:
    ...
```

```
class SMSReportGenerator:
    ...
```

you can separate responsibilities.

```
class ReportGenerator:
    def generate(self, data):
        return f"Report created from: {data}"
```

```
class EmailSender:
    def send(self, message):
        return f"Email sent: {message}"
```

```
class SlackSender:
    def send(self, message):
        return f"Slack message sent: {message}"
```

Then compose them:

```
class ReportService:
    def __init__(self, generator, sender):
        self._generator = generator
        self._sender = sender

    def create_and_send(self, data):
        report = self._generator.generate(data)
        return self._sender.send(report)
```

Usage:

```
service = ReportService(
    generator=ReportGenerator(),
    sender=EmailSender(),
)

print(service.create_and_send("weekly AI-agent metrics"))
```

Later:

```
service = ReportService(
    generator=ReportGenerator(),
    sender=SlackSender(),
)
```

You changed only the component, not the whole design.

This is **composition + polymorphism**. It is extremely useful for startup systems because it prevents class hierarchies from becoming too rigid.

# 28. Real-world project: pluggable storage

Imagine you are building TrustDesk and want to save support tickets. Initially you store tickets in memory; later you may use a database or a cloud service.

## Step 1: Define behavior

```
from typing import Protocol
```

```
class TicketRepository(Protocol):
    def save(self, ticket: dict) -> None:
        ...

    def get_by_id(self, ticket_id: str) -> dict | None:
        ...
```

## Step 2: In-memory implementation

```
class InMemoryTicketRepository:
    def __init__(self):
        self._tickets = {}

    def save(self, ticket: dict) -> None:
        self._tickets[ticket["id"]] = ticket.copy()

    def get_by_id(self, ticket_id: str) -> dict | None:
        ticket = self._tickets.get(ticket_id)

        return ticket.copy() if ticket else None
```

## Step 3: Service depends on behavior

```
class TicketService:
    def __init__(self, repository: TicketRepository):
        self._repository = repository

    def create_ticket(self, ticket_id, title, priority):
        ticket = {
            "id": ticket_id,
            "title": title,
            "priority": priority,
            "status": "open",
        }

        self._repository.save(ticket)

        return ticket
```

## Step 4: Use it

```
repository = InMemoryTicketRepository()
service = TicketService(repository)

ticket = service.create_ticket(
    ticket_id="T-001",
    title="Cannot log in",
    priority="high",
)

print(ticket)
print(repository.get_by_id("T-001"))
```

The important point:

```
TicketService
```

does not care whether the repository is:

- In-memory
- PostgreSQL
- SQLite
- Redis
- MongoDB
- A REST API
- A mock repository for testing

As long as it provides:

```
save(ticket)
get_by_id(ticket_id)
```

it works.

That is polymorphism powering clean architecture.

# 29. Polymorphism for testing

Polymorphism makes testing much easier because you can inject a fake implementation.

class FakeLLMProvider:

```
assistant = SupportAssistant(FakeLLMProvider())

Output:

```

You do not need:

- Internet access
- Paid model calls
- Unpredictable model outputs
- Slow external requests

The production object and test object share the same `.generate(prompt)` behavior contract.

# 30. Common mistakes

## Checking exact types everywhere

Avoid:

```
if type(storage) is PostgreSQLStorage:
    ...
```

It prevents compatible alternatives from working.

Better:

```
storage.save(data)
```

Or, when a formal relationship matters:

```
isinstance(storage, StorageBase)
```

But prefer behavior over exact class identity when possible.

---

## Using inheritance only for code reuse

Do not inherit just because two classes share a few lines of code.

Bad relationship:

```
class DatabaseConnection:
    ...
```

```
class EmailSender(DatabaseConnection):
    ...
```

An email sender is not a database connection.

Use composition:

```
class EmailSender:
    def __init__(self, database_connection):
        self._database_connection = database_connection
```

---

## An overly broad interface

Avoid designing a giant base class:

```
class EverythingService:
    def save(self):
        ...
    
    def send_email(self):
        ...
    
    def generate_ai_response(self):
        ...
    
    def process_payment(self):
        ...
```

Most subclasses will not logically support all methods.

Prefer small interfaces:

```
class Saveable(Protocol):
    def save(self):
        ...
```

```
class Sendable(Protocol):
    def send(self, message):
        ...
```

```
class GenerativeModel(Protocol):
    def generate(self, prompt):
        ...
```

Small, focused interfaces create more reliable polymorphism.

---

## Catching every exception in duck typing

Avoid:

```
try:
    return tool.run(command)
except Exception:
    return None
```

This hides bugs from inside `tool.run()`.

Better:

```
try:
    return tool.run(command)
except AttributeError as error:
    raise TypeError(
        "Tool must provide a run(command) method."
    ) from error
```

---

## Overusing `isinstance()`

`isinstance()` is not forbidden. It is useful when behavior truly depends on a category, such as:

- Handling `str` versus `bytes`
- Numeric validation
- Security-sensitive input validation
- Serialization boundaries
- Interoperating with external libraries
- Special handling for `None`

But if you use `isinstance()` only because your design lacks a shared behavior contract, improve the design instead.

## Exercise 3 answer

```
from abc import ABC, abstractmethod
```

```
class ModelEvaluator(ABC):

    @abstractmethod
    def evaluate(self, predictions, labels):
        pass
```

```
class AccuracyEvaluator(ModelEvaluator):

    def evaluate(self, predictions, labels):
        correct = sum(
            prediction == label
            for prediction, label in zip(predictions, labels)
        )

        return correct / len(labels)
```

```
class PrecisionEvaluator(ModelEvaluator):

    def evaluate(self, predictions, labels):
        true_positives = sum(
            prediction == 1 and label == 1
            for prediction, label in zip(predictions, labels)
        )

        predicted_positives = sum(
            prediction == 1
            for prediction in predictions
        )

        if predicted_positives == 0:
            return 0.0

        return true_positives / predicted_positives
```

```
def print_score(evaluator, predictions, labels):
    score = evaluator.evaluate(predictions, labels)

    print(f"Score: {score:.2f}")
```

```
predictions = [1, 0, 1, 1]
labels = [1, 0, 0, 1]

print_score(AccuracyEvaluator(), predictions, labels)
print_score(PrecisionEvaluator(), predictions, labels)
```

class Cache(Protocol):

class InMemoryCache:
    def __init__(self):
        self._data = {}

    def get(self, key):
        return self._data.get(key)

    def set(self, key, value):
        self._data[key] = value
```

```
class UserService:
    def __init__(self, cache: Cache):
        self._cache = cache

    def get_user_name(self, user_id):
        cache_key = f"user:{user_id}"

        cached_name = self._cache.get(cache_key)

        if cached_name is not None:
            return cached_name

        name = f"User {user_id}"
        self._cache.set(cache_key, name)

        return name

## Exercise 5 answer

```
class Vector2D:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __add__(self, other):
        if not isinstance(other, Vector2D):
            return NotImplemented

        return Vector2D(
            self.x + other.x,
            self.y + other.y
        )

    def __repr__(self):
        return f"Vector2D({self.x}, {self.y})"
```

Vector2D(4, 6)

# 33. Final mental model

Remember this sentence:

> Polymorphism lets different objects be used through the same interface.

And remember this sentence for duck typing:

> In Python, what an object can do is often more important than what class it belongs to.

Use this progression in your own code:

```
# 1. Start simple: duck typing
def run(tool, task):
    return tool.run(task)
```

```
# 2. Add a Protocol for large typed projects
class Tool(Protocol):
    def run(self, task: str) -> str:
        ...
```

```
# 3. Use an ABC when you need a formal hierarchy
class ToolBase(ABC):
    @abstractmethod
    def run(self, task):
        ...
```

```
# 4. Use composition to combine interchangeable components
agent = Agent(
    model=CloudModelProvider(),
    memory=RedisMemory(),
    tools=[SearchTool(), DatabaseTool()],
)
```

For your future AI systems, this lets you swap a local model for a cloud model, an in-memory store for PostgreSQL, a simple rule-based classifier for a trained ML model, or a fake test service for a live production API—without rewriting the rest of the system.
