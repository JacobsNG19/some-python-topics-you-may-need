A **context manager** controls setup and cleanup around a block of code. The `with` statement ensures cleanup happens even if an exception occurs, which makes it ideal for files, database connections, locks, transactions, temporary resources, and AI/API sessions.[[docs.python](https://docs.python.org/3/library/contextlib.html)][[docs.python](https://docs.python.org/3/tutorial/inputoutput.html)]

# 1. The basic `with` statement

You have probably seen:

```
with open("notes.txt", "w", encoding="utf-8") as file:
    file.write("Learning context managers.")
```

The file is automatically closed after the indented block finishes—even if an error occurs inside the block. Python’s documentation recommends this pattern for file objects because it guarantees proper cleanup.[[docs.python](https://docs.python.org/3/tutorial/inputoutput.html)]

Without `with`, you would write:

```
file = open("notes.txt", "w", encoding="utf-8")

try:
    file.write("Learning context managers.")
finally:
    file.close()
```

The `with` version is shorter and safer:

```
with open("notes.txt", "w", encoding="utf-8") as file:
    file.write("Learning context managers.")
```

The core idea is:

```
Enter resource
    ↓
Run block
    ↓
Clean up resource
```

---

# 2. What is a context manager?

A context manager is an object that defines how to:

1. Enter a context.
2. Exit the context.
3. Clean up resources.
4. Optionally handle exceptions.

The protocol uses two special methods:

```
__enter__()
__exit__()
```

A class becomes a context manager when it implements these methods.

```
class SimpleContext:
    def __enter__(self):
        print("Entering the context.")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        print("Leaving the context.")
```

Use it:

```
with SimpleContext():
    print("Inside the block.")
```

Output:

```
Entering the context.
Inside the block.
Leaving the context.
```

The code in `__enter__()` runs before the block.

The code in `__exit__()` runs after the block.

# 3. Understanding `as`

This:

```
with SimpleContext() as context:
    print(context)
```

means:

1. Create a `SimpleContext` object.
2. Call its `__enter__()` method.
3. Store the result in `context`.
4. Run the block.
5. Call `__exit__()`.

The value assigned after `as` is whatever `__enter__()` returns.

```
class DatabaseSession:
    def __enter__(self):
        print("Opening session.")
        return self

    def query(self, sql):
        return f"Executing: {sql}"

    def __exit__(self, exc_type, exc_value, traceback):
        print("Closing session.")
```

```
with DatabaseSession() as session:
    result = session.query("SELECT * FROM tickets")
    print(result)
```

Output:

```
Opening session.
Executing: SELECT * FROM tickets
Closing session.
```

Because `__enter__()` returns `self`, the variable `session` refers to the context-manager object.

You can return something else:

```
class TemporaryValue:
    def __enter__(self):
        return "Prepared value"

    def __exit__(self, exc_type, exc_value, traceback):
        print("Cleanup complete.")
```

```
with TemporaryValue() as value:
    print(value)
```

Output:

```
Prepared value
Cleanup complete.
```

# 4. The real equivalent of `with`

This:

```
with Resource() as resource:
    resource.use()
```

is conceptually similar to:

```
manager = Resource()
resource = manager.__enter__()

try:
    resource.use()
finally:
    manager.__exit__(None, None, None)
```

If an exception occurs:

```
manager = Resource()
resource = manager.__enter__()

try:
    resource.use()
except BaseException as error:
    suppress_error = manager.__exit__(
        type(error),
        error,
        error.__traceback__,
    )

    if not suppress_error:
        raise
else:
    manager.__exit__(None, None, None)
```

This is a conceptual translation, not code you normally write manually.

The important lesson:

```
__exit__() is called whether the block succeeds or fails.
```

That is why context managers are safer than relying on a line of code after the block:

```
resource.close()
```

If an exception occurs before that line, cleanup may never happen.

# 5. Understanding `__exit__`

The method signature is:

```
def __exit__(self, exc_type, exc_value, traceback):
    ...
```

The arguments describe an exception raised inside the `with` block.

|Argument|Meaning|
|---|---|
|`exc_type`|Exception class, such as `ValueError`|
|`exc_value`|Actual exception object|
|`traceback`|Traceback information|
|All three are `None`|The block completed successfully|

Example:

```
class DebugContext:
    def __enter__(self):
        print("Entering.")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        if exc_type is None:
            print("Block completed successfully.")
        else:
            print(f"Exception type: {exc_type.__name__}")
            print(f"Exception value: {exc_value}")

        print("Cleanup complete.")
        return False
```

Successful block:

```
with DebugContext():
    print("Everything is fine.")
```

Output:

```
Entering.
Everything is fine.
Block completed successfully.
Cleanup complete.
```

Failing block:

```
with DebugContext():
    raise ValueError("Something went wrong.")
```

Output:

```
Entering.
Exception type: ValueError
Exception value: Something went wrong.
Cleanup complete.
```

The error continues after `__exit__()` because it returned:

```
False
```

# 6. Suppressing exceptions

If `__exit__()` returns `True`, it suppresses the exception.

```
class IgnoreValueErrors:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        return exc_type is ValueError
```

```
with IgnoreValueErrors():
    raise ValueError("This error is ignored.")

print("The program continues.")
```

Output:

```
The program continues.
```

This is equivalent to saying:

```
If the exception is ValueError, consider it handled.
```

## Be careful

Do not suppress errors without a strong reason.

Dangerous:

```
class BadContext:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        return True
```

This hides every exception:

```
with BadContext():
    1 / 0
```

The division error disappears, making debugging extremely difficult.

Usually write:

```
return False
```

or simply:

```
return None
```

to allow exceptions to propagate normally.

# 7. A practical file-like context manager

Let’s create one that opens and closes a file.

```
class ManagedFile:
    def __init__(self, filename, mode="r", encoding="utf-8"):
        self.filename = filename
        self.mode = mode
        self.encoding = encoding
        self._file = None

    def __enter__(self):
        self._file = open(
            self.filename,
            self.mode,
            encoding=self.encoding,
        )

        return self._file

    def __exit__(self, exc_type, exc_value, traceback):
        if self._file is not None:
            self._file.close()

        return False
```

Use it:

```
with ManagedFile("notes.txt", "w") as file:
    file.write("Python context managers.")
```

The sequence is:

```
ManagedFile created
        ↓
__enter__ opens file
        ↓
file object returned as file
        ↓
write operation runs
        ↓
__exit__ closes file
```

In practice, use Python’s built-in `open()` directly. This example is for understanding the protocol.

# 8. Database transaction example

A transaction context manager can commit when everything succeeds and roll back when something fails.

```
class DatabaseTransaction:
    def __init__(self, connection):
        self.connection = connection

    def __enter__(self):
        print("Transaction started.")
        return self.connection

    def __exit__(self, exc_type, exc_value, traceback):
        if exc_type is None:
            self.connection.commit()
            print("Transaction committed.")
        else:
            self.connection.rollback()
            print("Transaction rolled back.")

        return False
```

Usage:

```
with DatabaseTransaction(connection) as database:
    database.execute(
        "INSERT INTO tickets (title) VALUES (?)",
        ("Cannot log in",),
    )
```

If the block succeeds:

```
Transaction committed.
```

If the block raises an exception:

```
Transaction rolled back.
```

This pattern is valuable because database consistency becomes automatic.

For TrustDesk or Burvex, you could use this pattern around:

- Creating a ticket and an audit record.
- Updating a user and permission record.
- Saving an AI classification and its explanation.
- Recording payment state and subscription state.
- Updating multiple related tables.

# 9. Lock context managers

Locks protect shared resources in concurrent programs.

```
from threading import Lock
```

```
lock = Lock()

with lock:
    # Only one thread at a time executes this block.
    print("Working with shared data.")
```

The lock is acquired when entering and released when leaving—even if the block raises an exception.

You can write your own wrapper:

```
class LockedCounter:
    def __init__(self):
        self._value = 0
        self._lock = Lock()

    def increment(self):
        with self._lock:
            self._value += 1

    @property
    def value(self):
        with self._lock:
            return self._value
```

The `with` statement makes the critical section visually obvious:

```
with self._lock:
    self._value += 1
```

# 10. `contextlib.contextmanager`

Writing a class with `__enter__()` and `__exit__()` is useful, but Python offers a simpler approach for many cases:

```
from contextlib import contextmanager
```

You write a generator function and place the managed block around `yield`.

```
@contextmanager
def simple_context():
    print("Setup.")
    yield
    print("Cleanup.")
```

Use it:

```
with simple_context():
    print("Inside.")
```

Output:

```
Setup.
Inside.
Cleanup.
```

The structure is:

```
@contextmanager
def context_manager():
    # Code before yield: setup
    yield value
    # Code after yield: cleanup
```

The `@contextmanager` decorator converts the generator into a context manager. The `contextlib` module provides this utility specifically so you can define context managers without writing a class with separate `__enter__()` and `__exit__()` methods.[[docs.python](https://docs.python.org/3/library/contextlib.html)]

---

# 11. `@contextmanager` with `as`

```
from contextlib import contextmanager
```

```
@contextmanager
def temporary_message(message):
    print("Preparing context.")

    try:
        yield message
    finally:
        print("Cleaning up context.")
```

Use it:

```
with temporary_message("Hello, Toussaint") as value:
    print(value)
```

Output:

```
Preparing context.
Hello, Toussaint
Cleaning up context.
```

The value after `yield` becomes the value after `as`.

```
yield message
    ↓
as value
```

# 12. Why `try/finally` is essential

Always put cleanup after `yield` inside `finally`.

Weak version:

```
@contextmanager
def unsafe_context():
    print("Setup.")
    yield
    print("Cleanup.")
```

If the block raises an exception, execution may not reach the cleanup line.

Safer version:

```
@contextmanager
def safe_context():
    print("Setup.")

    try:
        yield
    finally:
        print("Cleanup.")
```

Now cleanup happens on both success and failure:

```
with safe_context():
    raise ValueError("Failure inside block.")
```

Output:

```
Setup.
Cleanup.
```

Then the `ValueError` continues normally.

# 13. Handling exceptions with `@contextmanager`

Exceptions from the `with` block are thrown back into the generator at the `yield` point.

```
from contextlib import contextmanager
```

```
@contextmanager
def handle_value_error():
    try:
        yield
    except ValueError as error:
        print(f"Handled: {error}")
```

Use it:

```
with handle_value_error():
    raise ValueError("Invalid value.")
```

Output:

```
Handled: Invalid value.
```

The exception is suppressed because it was caught and not re-raised.

To allow it to continue:

```
@contextmanager
def log_errors():
    try:
        yield
    except Exception as error:
        print(f"Logging error: {error}")
        raise
```

The `raise` is important:

```
raise
```

re-raises the same exception with its traceback.

# 14. Temporary configuration context

A useful example is temporarily changing a setting and restoring it afterward.

```
from contextlib import contextmanager
```

```
@contextmanager
def temporary_setting(settings, key, value):
    old_value = settings.get(key)

    settings[key] = value

    try:
        yield settings
    finally:
        if old_value is None:
            settings.pop(key, None)
        else:
            settings[key] = old_value
```

Use it:

```
settings = {
    "debug": False,
    "model": "production",
}

with temporary_setting(settings, "debug", True):
    print(settings)
```

Output:

```
{'debug': True, 'model': 'production'}
```

After the block:

```
print(settings)
```

Output:

```
{'debug': False, 'model': 'production'}
```

This pattern is useful for:

- Temporarily enabling debug mode.
- Changing model temperature during a test.
- Temporarily switching a database schema.
- Overriding environment-like settings.
- Using a temporary API endpoint in tests.

# 15. Timing context manager

```
from contextlib import contextmanager
from time import perf_counter
```

```
@contextmanager
def timer(label):
    start = perf_counter()

    try:
        yield
    finally:
        elapsed = perf_counter() - start
        print(f"{label}: {elapsed:.6f} seconds")
```

Use it:

```
with timer("Ticket processing"):
    result = [
        value * 2
        for value in range(100_000)
    ]
```

Possible output:

```
Ticket processing: 0.008421 seconds
```

This is useful for measuring:

- Model inference.
- Embedding generation.
- Vector search.
- Database queries.
- API calls.
- Data preprocessing.
- Agent tool execution.

You can also expose timing information:

```
@contextmanager
def measured_block():
    result = {}

    start = perf_counter()

    try:
        yield result
    finally:
        result["elapsed"] = perf_counter() - start
```

```
with measured_block() as metrics:
    sum(range(1_000_000))

print(metrics["elapsed"])
```

# 16. `contextlib.closing`

Some third-party resources have a `.close()` method but do not implement the context-manager protocol.

`contextlib.closing()` adapts them:

```
from contextlib import closing
```

```
class ExternalResource:
    def use(self):
        return "Resource used."

    def close(self):
        print("Resource closed.")
```

```
resource = ExternalResource()

with closing(resource) as item:
    print(item.use())
```

Output:

```
Resource used.
Resource closed.
```

`closing()` is conceptually similar to:

```
@contextmanager
def closing(thing):
    try:
        yield thing
    finally:
        thing.close()
```

The standard library notes that `closing()` is most useful for third-party objects that provide `.close()` but do not support `with` themselves.[[docs.python](https://docs.python.org/3/library/contextlib.html)]

# 17. `contextlib.suppress`

If you deliberately want to ignore a specific exception, use:

```
from contextlib import suppress
```

```
with suppress(FileNotFoundError):
    remove_file("temporary.txt")
```

This is equivalent to:

```
try:
    remove_file("temporary.txt")
except FileNotFoundError:
    pass
```

Use it only for expected, harmless errors.

Good:

```
with suppress(FileNotFoundError):
    os.remove("temporary_cache.json")
```

Bad:

```
with suppress(Exception):
    run_important_database_operation()
```

Never suppress broad exceptions around critical work.

# 18. Multiple context managers

You can use multiple resources in one `with` statement:

```
with open("input.txt", encoding="utf-8") as source, \
     open("output.txt", "w", encoding="utf-8") as destination:
    content = source.read()
    destination.write(content.upper())
```

Both files are closed automatically.

This is equivalent in spirit to nested contexts:

```
with open("input.txt", encoding="utf-8") as source:
    with open(
        "output.txt",
        "w",
        encoding="utf-8",
    ) as destination:
        content = source.read()
        destination.write(content.upper())
```

Cleanup happens in reverse order:

```
output file closes first
input file closes second
```

This reverse-order cleanup is important when resources depend on one another.

# 19. `ExitStack`

Sometimes you do not know in advance how many resources you need.

For example:

```
filenames = [
    "part1.txt",
    "part2.txt",
    "part3.txt",
]
```

You can use `ExitStack`:

```
from contextlib import ExitStack
```

```
with ExitStack() as stack:
    files = [
        stack.enter_context(
            open(filename, encoding="utf-8")
        )
        for filename in filenames
    ]

    contents = [
        file.read()
        for file in files
    ]
```

All opened files are closed automatically when the `ExitStack` exits.

`ExitStack` is designed for dynamically combining context managers and cleanup callbacks, especially when resources are optional or determined at runtime. Cleanup occurs in reverse registration order.[[docs.python](https://docs.python.org/3/library/contextlib.html)]

## Dynamic resource example

```
from contextlib import ExitStack
```

```
def read_many_files(filenames):
    with ExitStack() as stack:
        files = [
            stack.enter_context(
                open(filename, encoding="utf-8")
            )
            for filename in filenames
        ]

        return [
            file.read()
            for file in files
        ]
```

This is cleaner than manually creating a different nested `with` structure for every possible number of files.

# 20. Registering cleanup callbacks

`ExitStack` can also manage arbitrary cleanup functions.

```
from contextlib import ExitStack
```

```
def cleanup_temp_directory():
    print("Temporary directory deleted.")
```

```
with ExitStack() as stack:
    stack.callback(cleanup_temp_directory)

    print("Doing work.")
```

Output:

```
Doing work.
Temporary directory deleted.
```

The callback runs when the stack exits, including when an exception occurs.

This is useful when setup creates resources that do not all have a standard `__exit__()` method.

# 21. Class versus `@contextmanager`

Use a class when:

- The context manager has substantial state.
- You need several helper methods.
- The lifecycle is complex.
- You want to inherit from a context-manager base class.
- You need fine-grained control over exception handling.

```
class DatabaseTransaction:
    def __enter__(self):
        ...
    
    def __exit__(self, exc_type, exc_value, traceback):
        ...
```

Use `@contextmanager` when:

- Setup and cleanup are short.
- The logic is linear.
- A generator makes the lifecycle easier to read.
- You do not need a large stateful object.

```
@contextmanager
def timer():
    start = perf_counter()

    try:
        yield
    finally:
        ...
```

Both approaches implement the same conceptual protocol.

# 22. `AbstractContextManager`

The `contextlib` module also provides an abstract base class for context managers.

```
from contextlib import AbstractContextManager
```

```
class Timer(AbstractContextManager):
    def __enter__(self):
        self._start = perf_counter()
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        elapsed = perf_counter() - self._start
        print(f"Elapsed: {elapsed:.6f} seconds")

        return False
```

`AbstractContextManager` provides a default `__enter__()` that returns `self`, while requiring an implementation of `__exit__()`.[[docs.python](https://docs.python.org/3/library/contextlib.html)]

For normal Python applications, you do not need to inherit from it. Implementing `__enter__()` and `__exit__()` directly is enough.

# 23. Asynchronous context managers

For asynchronous code, use:

```
async with
```

The protocol changes to:

```
__aenter__()
__aexit__()
```

Example:

```
class AsyncSession:
    async def __aenter__(self):
        print("Opening async session.")
        return self

    async def __aexit__(
        self,
        exc_type,
        exc_value,
        traceback,
    ):
        print("Closing async session.")

    async def fetch(self, url):
        return f"Fetched {url}"
```

Usage:

```
async def main():
    async with AsyncSession() as session:
        result = await session.fetch(
            "https://example.com"
        )

        print(result)
```

For asynchronous context managers:

```
with       → __enter__, __exit__
async with → __aenter__, __aexit__
```

Use `async with` when setup or cleanup itself requires `await`, such as:

- Async database connections
- Async HTTP clients
- WebSocket sessions
- Async locks
- Streaming resources
- Async message queues

The `contextlib` module also provides `AbstractAsyncContextManager` and `asynccontextmanager` for asynchronous resource management.[[docs.python](https://docs.python.org/3/library/contextlib.html)]

# 24. AI/API client example

Here is a simplified client context manager.

```
class ModelSession:
    def __init__(self, model_name):
        self.model_name = model_name
        self._connected = False

    def __enter__(self):
        print(f"Connecting to {self.model_name}.")
        self._connected = True

        return self

    def generate(self, prompt):
        if not self._connected:
            raise RuntimeError(
                "Model session is not connected."
            )

        return f"Generated response to: {prompt}"

    def __exit__(self, exc_type, exc_value, traceback):
        print(f"Disconnecting from {self.model_name}.")
        self._connected = False

        return False
```

Usage:

```
with ModelSession("trustdesk-support-model") as model:
    response = model.generate(
        "Explain how to reset a password."
    )

    print(response)
```

Output:

```
Connecting to trustdesk-support-model.
Generated response to: Explain how to reset a password.
Disconnecting from trustdesk-support-model.
```

In a real implementation, `__enter__()` might:

- Create an HTTP client.
- Authenticate.
- Open a database connection.
- Initialize a model runtime.
- Start tracing.
- Acquire a rate-limit resource.

`__exit__()` might:

- Close the HTTP client.
- Release the database connection.
- Flush metrics.
- End a tracing span.
- Release a lock.
- Commit or roll back a transaction.

# 25. Context managers and exceptions

A reliable context manager should clean up even if the business operation fails.

```
class TemporaryModelSession:
    def __enter__(self):
        print("Loading model.")
        self.model = "loaded-model"
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        print("Unloading model.")

        if exc_type is not None:
            print(f"Operation failed: {exc_value}")

        return False
```

```
with TemporaryModelSession() as session:
    raise RuntimeError("Inference failed.")
```

Output:

```
Loading model.
Unloading model.
Operation failed: Inference failed.
```

The exception still propagates, but cleanup occurs first.

This is one of the main reasons context managers are preferable to:

```
session = create_session()

try:
    run_inference(session)
except Exception:
    ...
finally:
    destroy_session(session)
```

The context-manager abstraction keeps resource lifecycle next to the resource itself.

# 26. Common mistakes

## Forgetting `return self`

Incorrect:

```
class Connection:
    def __enter__(self):
        self.connect()
        # No return
```

Then:

```
with Connection() as connection:
    connection.query()
```

`connection` becomes `None`.

Correct:

```
class Connection:
    def __enter__(self):
        self.connect()
        return self
```

---

## Cleaning up only on success

Incorrect:

```
@contextmanager
def resource():
    setup()
    yield
    cleanup()
```

If the block raises an exception, cleanup may not run.

Correct:

```
@contextmanager
def resource():
    setup()

    try:
        yield
    finally:
        cleanup()
```

---

## Accidentally suppressing errors

Avoid:

```
def __exit__(self, exc_type, exc_value, traceback):
    return True
```

unless suppression is specifically part of the design.

Usually:

```
return False
```

is safer.

---

## Closing a resource too early

Incorrect:

```
def get_file():
    with open("data.txt", encoding="utf-8") as file:
        return file
```

The returned file is already closed after leaving the function.

Better:

```
def read_file():
    with open("data.txt", encoding="utf-8") as file:
        return file.read()
```

Return the data, not the closed resource.

---

## Performing unrelated work in cleanup

Keep `__exit__()` focused on:

- Closing
- Releasing
- Rolling back
- Restoring
- Flushing
- Removing temporary resources

Avoid putting major business operations inside cleanup because cleanup should remain predictable.

from contextlib import contextmanager

```
@contextmanager
def temporary_debug(settings):
    had_debug = "debug" in settings
    old_value = settings.get("debug")

    settings["debug"] = True

    try:
        yield settings
    finally:
        if had_debug:
            settings["debug"] = old_value
        else:
            settings.pop("debug", None)
```

    print(settings)

## Exercise 4 answer

```
class Transaction:
    def __enter__(self):
        print("BEGIN")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        if exc_type is None:
            print("COMMIT")
        else:
            print("ROLLBACK")

        return False
```

Success:

```
with Transaction():
    print("Saving ticket.")
```

Output:

```

Saving ticket.
COMMIT
```

Failure:

```
with Transaction():
    print("Saving ticket.")
    raise ValueError("Invalid ticket.")
```

Output:

```
BEGIN
Saving ticket.
ROLLBACK
```

The `ValueError` still propagates because `__exit__()` returns `False`.

# 29. Final mental model

A context manager gives you this structure:

```
with resource as value:
    use(value)
```

Behind the scenes:

```
resource.__enter__()
```

runs before the block, and:

```
resource.__exit__(...)
```

runs afterward.

Use a class when lifecycle logic is substantial:

```
class Resource:
    def __enter__(self):
        ...

    def __exit__(self, exc_type, exc_value, traceback):
        ...
```

Use `@contextmanager` when setup and cleanup are simple:

```
@contextmanager
def resource():
    setup()

    try:
        yield value
    finally:
        cleanup()
```

Remember these rules:

```
__enter__() prepares and returns the usable value.
__exit__() cleans up.
Use finally for guaranteed cleanup.
Return False to propagate exceptions.
Return True only to deliberately suppress an exception.
Use async with for asynchronous resources.
Use ExitStack for dynamic groups of resources.
```

For your AI-engineering projects, context managers are particularly useful for database transactions, model sessions, API clients, locks, temporary configuration, timing, tracing, and controlled cleanup.
