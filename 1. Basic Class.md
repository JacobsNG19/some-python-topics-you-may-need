A Python **class** is a blueprint for creating objects. **Inheritance** lets one class reuse or specialize another class, while **composition** builds a class by giving it other objects as components. Use inheritance for a genuine “is-a” relationship; use composition for a “has-a” or “uses-a” relationship. Python classes bundle data and behavior, and `super()` helps a child class reuse parent behavior.[[docs.python](https://docs.python.org/3/tutorial/classes.html)]

# 1. Classes from scratch

A class defines the structure and behavior of objects.

```
class Student:
    pass
```

Create an object:

```
student = Student()

print(student)
```

An object is an instance of a class:

```
isinstance(student, Student)
```

Output:

```
True
```

A class becomes useful when it contains:

- Attributes: data belonging to an object.
- Methods: functions belonging to a class.
- Initialization logic: usually written in `__init__`.
- Rules that protect valid object state.

---

# 2. `__init__` and `self`

```
class Student:
    def __init__(self, name, field):
        self.name = name
        self.field = field
```

Create objects:

```
student_a = Student(
    "Toussaint",
    "AI Engineering",
)

student_b = Student(
    "Aline",
    "Computer Science",
)
```

Each object has independent instance attributes:

```
print(student_a.name)
print(student_b.name)
```

Output:

```
Toussaint
Aline
```

## What is `self`?

In:

```
student_a.name
```

Python looks up the `name` attribute on `student_a`.

In:

```
student_a.describe()
```

Python effectively passes `student_a` as the first argument:

```
Student.describe(student_a)
```

That is why instance methods need:

```
self
```

The name `self` is conventional; technically, another name would work, but always use `self`.

# 3. Instance methods

```
class Student:
    def __init__(self, name, field):
        self.name = name
        self.field = field

    def introduce(self):
        return (
            f"My name is {self.name}. "
            f"I study {self.field}."
        )
```

Use:

```
student = Student(
    "Toussaint",
    "AI Engineering",
)

print(student.introduce())
```

Output:

```
My name is Toussaint. I study AI Engineering.
```

An instance method can access:

```
self.name
self.field
```

because it receives a specific object.

# 4. Class attributes

A class attribute belongs to the class and is normally shared by instances.

```
class Student:
    school = "Gitega Technology Academy"

    def __init__(self, name):
        self.name = name
```

```
student_a = Student("Toussaint")
student_b = Student("Aline")

print(student_a.school)
print(student_b.school)
print(Student.school)
```

Output:

```
Gitega Technology Academy
Gitega Technology Academy
Gitega Technology Academy
```

Instance-specific data:

```
self.name
```

Class-wide data:

```
Student.school
```

Use class attributes for:

- Constants.
- Shared configuration.
- Counters.
- Metadata.
- Default behavior shared by all instances.

Be careful with mutable class attributes:

```
class BadProject:
    tasks = []
```

Every instance shares the same list.

Better:

```
class Project:
    def __init__(self):
        self.tasks = []
```

# 5. Methods and class responsibilities

A good class should represent a meaningful concept.

```
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError(
                "Deposit must be positive."
            )

        self.balance += amount

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError(
                "Withdrawal must be positive."
            )

        if amount > self.balance:
            raise ValueError(
                "Insufficient funds."
            )

        self.balance -= amount
```

The class combines:

```
data     → owner, balance
behavior → deposit(), withdraw()
rules    → amount validation, balance protection
```

This is more meaningful than storing data in unrelated dictionaries and changing it everywhere manually.

# 6. Inheritance

Inheritance allows a child class to receive behavior from a parent class.

```
class Animal:
    def eat(self):
        return "The animal is eating."
```

```
class Dog(Animal):
    def bark(self):
        return "Woof!"
```

Create a child object:

```
dog = Dog()

print(dog.eat())
print(dog.bark())
```

Output:

```
The animal is eating.
Woof!
```

`Dog` inherits:

```
eat()
```

from `Animal` and defines its own:

```
bark()
```

The syntax is:

```
class Child(Parent):
    ...
```

---

# 7. The “is-a” test

Inheritance usually represents an “is-a” relationship.

```
A dog is an animal.
A car is a vehicle.
An administrator is a user.
A cloud provider is an LLM provider.
```

Examples:

```
class Dog(Animal):
    ...
```

```
class Car(Vehicle):
    ...
```

```
class AdminUser(User):
    ...
```

Do not use inheritance merely because two classes share some code.

This is usually wrong:

```
class EmailSender(DatabaseConnection):
    ...
```

An email sender is not a database connection.

Use composition instead:

```
class EmailSender:
    def __init__(self, database_connection):
        self.database_connection = database_connection
```

# 8. Method overriding

A child class can provide a different implementation of a parent method.

```
class Animal:
    def speak(self):
        return "Some animal sound."
```

```
class Dog(Animal):
    def speak(self):
        return "Woof!"
```

```
class Cat(Animal):
    def speak(self):
        return "Meow!"
```

Use polymorphically:

```
animals = [
    Dog(),
    Cat(),
]

for animal in animals:
    print(animal.speak())
```

Output:

```
Woof!
Meow!
```

The same method call:

```
animal.speak()
```

has different behavior depending on the actual object.

This connects inheritance to polymorphism.

# 9. `super()`

`super()` lets a child class access behavior from its parent class.

```
class Employee:
    def __init__(self, name):
        self.name = name

    def describe(self):
        return f"Employee: {self.name}"
```

```
class AIEngineer(Employee):
    def __init__(self, name, specialization):
        super().__init__(name)
        self.specialization = specialization
```

Use:

```
engineer = AIEngineer(
    "Toussaint",
    "AI agents",
)

print(engineer.name)
print(engineer.specialization)
```

Output:

```
Toussaint
AI agents
```

Without:

```
super().__init__(name)
```

the parent’s initialization would not run automatically.

---

# 10. `super()` in methods

```
class Employee:
    def describe(self):
        return "Works for the organization."
```

```
class AIEngineer(Employee):
    def describe(self):
        parent_description = super().describe()

        return (
            f"{parent_description} "
            "Builds AI systems."
        )
```

```
engineer = AIEngineer()

print(engineer.describe())
```

Output:

```
Works for the organization. Builds AI systems.
```

Use `super()` when the child wants to:

- Extend parent behavior.
- Reuse parent validation.
- Reuse parent initialization.
- Add logging around parent behavior.
- Preserve a framework lifecycle.
- Cooperate with multiple inheritance.

---

# 11. Why not call the parent directly?

You could write:

```
Employee.__init__(self, name)
```

But prefer:

```
super().__init__(name)
```

`super()` is more flexible because it follows Python’s method-resolution order and works better with inheritance hierarchies, especially multiple inheritance.

Direct parent calls can become fragile:

```
ParentClass.method(self)
```

If the class hierarchy changes, those hardcoded calls may no longer cooperate correctly.

# 12. Inheritance with validation

```
class User:
    def __init__(self, username):
        if not username.strip():
            raise ValueError(
                "Username cannot be empty."
            )

        self.username = username.strip()

    def describe(self):
        return f"User: {self.username}"
```

```
class AdminUser(User):
    def __init__(self, username, permissions):
        super().__init__(username)

        self.permissions = set(permissions)

    def describe(self):
        base = super().describe()

        return (
            f"{base}; "
            f"permissions={self.permissions}"
        )
```

Usage:

```
admin = AdminUser(
    "toussaint",
    ["read", "write", "delete"],
)

print(admin.describe())
```

Output:

```
User: toussaint; permissions={'read', 'write', 'delete'}
```

The child reuses the parent’s username validation and description.

# 13. Abstract base classes and inheritance

For a formal interface, combine inheritance with an abstract base class.

```
from abc import ABC, abstractmethod
```

```
class ModelProvider(ABC):

    @abstractmethod
    def generate(self, prompt):
        pass
```

```
class LocalModelProvider(ModelProvider):
    def generate(self, prompt):
        return f"Local response to: {prompt}"
```

```
class CloudModelProvider(ModelProvider):
    def generate(self, prompt):
        return f"Cloud response to: {prompt}"
```

The parent defines the contract:

```
generate(prompt)
```

The children provide implementations.

This is useful when all classes are deliberately part of one formal family.

# 14. Multiple inheritance

Python allows a class to inherit from more than one parent.

```
class Logger:
    def log(self, message):
        print(f"LOG: {message}")
```

```
class Validator:
    def validate(self, value):
        return bool(value)
```

```
class Service(Logger, Validator):
    pass
```

```
service = Service()

service.log("Service started.")
print(service.validate("data"))
```

Output:

```
LOG: Service started.
True
```

Multiple inheritance can be useful for small, independent mixins:

```
class SerializableMixin:
    ...


class LoggingMixin:
    ...


class Ticket(SerializableMixin, LoggingMixin):
    ...
```

But complex multiple-inheritance hierarchies can be difficult to understand.

Prefer composition when several independent components need to be combined.

# 15. Method Resolution Order (MRO)

Python needs to decide which method to call when multiple classes define the same method.

```
class A:
    def describe(self):
        return "A"
```

```
class B(A):
    def describe(self):
        return "B"
```

```
class C(A):
    def describe(self):
        return "C"
```

```
class D(B, C):
    pass
```

```
object_d = D()

print(object_d.describe())
print(D.mro())
```

Output begins with:

```
B
[
    <class '__main__.D'>,
    <class '__main__.B'>,
    <class '__main__.C'>,
    <class '__main__.A'>,
    <class 'object'>
]
```

Python searches according to the Method Resolution Order.

`super()` follows this order.

You usually do not need to calculate MRO manually, but understand:

```
super() does not simply mean “my direct parent.”
It means “the next class in the method-resolution order.”
```

# 16. Composition

Composition means a class contains or uses objects of other classes.

It represents a “has-a” or “uses-a” relationship.

```
A car has an engine.
A computer has a processor.
An assistant has a model provider.
A ticket service has a repository.
An agent has tools.
```

Example:

```
class Engine:
    def start(self):
        return "Engine started."
```

```
class Car:
    def __init__(self):
        self.engine = Engine()

    def start(self):
        return self.engine.start()
```

Use:

```
car = Car()

print(car.start())
```

Output:

```
Engine started.
```

`Car` does not inherit from `Engine`.

A car is not an engine.

A car **has** an engine.

That is composition.

---

# 17. Dependency injection

Instead of creating the component inside the class, pass it in.

```
class Car:
    def __init__(self, engine):
        self.engine = engine

    def start(self):
        return self.engine.start()
```

Now define engines:

```
class PetrolEngine:
    def start(self):
        return "Petrol engine started."
```

```
class ElectricEngine:
    def start(self):
        return "Electric motor started."
```

Use either:

```
petrol_car = Car(PetrolEngine())
electric_car = Car(ElectricEngine())

print(petrol_car.start())
print(electric_car.start())
```

Output:

```
Petrol engine started.
Electric motor started.
```

This is **dependency injection**:

```
The Car receives its engine from outside.
```

Benefits:

- Easy replacement.
- Easier testing.
- Less coupling.
- Flexible configuration.
- Works naturally with protocols and duck typing.

---

# 18. Composition with a protocol

```
from typing import Protocol
```

```
class Engine(Protocol):
    def start(self) -> str:
        ...
```

Implementations do not need inheritance:

```
class ElectricEngine:
    def start(self) -> str:
        return "Electric motor started."
```

```
class Car:
    def __init__(self, engine: Engine):
        self.engine = engine

    def start(self) -> str:
        return self.engine.start()
```

Use:

```
car = Car(ElectricEngine())

print(car.start())
```

The `Car` only requires:

```
engine.start()
```

This is a powerful combination:

```
Composition → class uses another object
Protocol    → documents the required behavior
Duck typing → implementation does not need inheritance
```

# 19. Composition in an AI application

Suppose you are building a support assistant.

The assistant needs:

- An LLM provider.
- A memory store.
- A classifier.
- Tools.

Do not create one enormous inheritance hierarchy:

```
class CloudSupportAssistantWithRedisAndSearchTool(...):
    ...
```

Use composition:

```
class SupportAssistant:
    def __init__(
        self,
        model,
        memory,
        tools,
    ):
        self.model = model
        self.memory = memory
        self.tools = tools

    def answer(self, question):
        context = self.memory.search(question)

        prompt = (
            f"Context: {context}\n"
            f"Question: {question}"
        )

        return self.model.generate(prompt)
```

Define interchangeable components:

```
class SimpleModel:
    def generate(self, prompt):
        return f"Model response to: {prompt}"
```

```
class InMemoryMemory:
    def search(self, query):
        return "Relevant support context."
```

```
assistant = SupportAssistant(
    model=SimpleModel(),
    memory=InMemoryMemory(),
    tools=[],
)

print(
    assistant.answer(
        "How do I reset my password?"
    )
)
```

Later, replace:

```
SimpleModel()
```

with:

```
CloudModel()
```

and:

```
InMemoryMemory()
```

with:

```
VectorDatabaseMemory()
```

The assistant’s main logic remains the same.

# 20. Composition versus inheritance

|Question|Inheritance|Composition|
|---|---|---|
|Relationship|“Is-a”|“Has-a” or “uses-a”|
|Main mechanism|Parent-child class hierarchy|Objects stored as attributes|
|Coupling|Usually tighter|Usually looser|
|Reuse|Inherited behavior|Delegated behavior|
|Flexibility|Less flexible at runtime|Easy to replace components|
|Testing|Can require subclassing|Easy dependency injection|
|Best for|Genuine taxonomy and shared contract|Services, components, interchangeable strategies|
|Example|`AdminUser(User)`|`TicketService(repository)`|

## Inheritance example

```
class AdminUser(User):
    ...
```

An admin user is a user.

## Composition example

```
class TicketService:
    def __init__(self, repository):
        self.repository = repository
```

A ticket service uses a repository.

# 21. The fragile base-class problem

Inheritance creates dependency between child classes and parent implementation.

```
class BaseService:
    def run(self):
        self.prepare()
        self.execute()

    def prepare(self):
        print("Preparing.")

    def execute(self):
        print("Executing.")
```

```
class ChildService(BaseService):
    def prepare(self):
        print("Child preparation.")
```

If you later change the parent lifecycle:

```
class BaseService:
    def run(self):
        self.prepare()
        self.validate()
        self.execute()
```

all child classes may be affected.

This is called the **fragile base-class problem**: changes to a parent can unexpectedly break or alter child behavior.

Composition reduces this risk because components communicate through smaller interfaces:

```
service = Service(
    preparer=Preparer(),
    validator=Validator(),
    executor=Executor(),
)
```

Each part is more independent.

# 22. When inheritance is appropriate

Use inheritance when:

- There is a genuine “is-a” relationship.
- The parent and child share a stable conceptual contract.
- Subclasses should be substitutable for the parent.
- The child naturally extends or specializes the parent.
- You want shared implementation and polymorphism.
- You control the hierarchy.
- The hierarchy is not unnecessarily deep.

Good examples:

```
class AdminUser(User):
    ...
```

```
class CloudProvider(LLMProvider):
    ...
```

```
class CSVExporter(Exporter):
    ...
```

Avoid inheritance when the only reason is:

```
“These classes share some code.”
```

Shared code can often be extracted into:

- A helper function.
- A utility module.
- A component.
- A mixin.
- A service object.
- Composition.

---

# 23. When composition is appropriate

Use composition when:

- A class uses another class.
- You want to swap implementations.
- You need dependency injection.
- You want easy testing with fake objects.
- Components may vary independently.
- The relationship is “has-a” or “uses-a.”
- Inheritance would create a large or rigid hierarchy.

Good examples:

```
class Agent:
    def __init__(self, model, tools, memory):
        ...
```

```
class TicketService:
    def __init__(self, repository):
        ...
```

```
class ReportService:
    def __init__(self, generator, sender):
        ...
```

# 24. Strategy pattern with composition

Composition is ideal for selecting algorithms.

```
class AccuracyStrategy:
    def evaluate(self, predictions, labels):
        correct = sum(
            prediction == label
            for prediction, label in zip(
                predictions,
                labels,
            )
        )

        return correct / len(labels)
```

```
class ExactMatchStrategy:
    def evaluate(self, predictions, labels):
        return sum(
            prediction == label
            for prediction, label in zip(
                predictions,
                labels,
            )
        )
```

```
class Evaluator:
    def __init__(self, strategy):
        self.strategy = strategy

    def evaluate(self, predictions, labels):
        return self.strategy.evaluate(
            predictions,
            labels,
        )
```

Use:

```
evaluator = Evaluator(AccuracyStrategy())

score = evaluator.evaluate(
    [1, 0, 1],
    [1, 0, 0],
)

print(score)
```

Replace the strategy:

```
evaluator.strategy = ExactMatchStrategy()
```

This is more flexible than creating a separate subclass for every possible combination of evaluator behavior.

# 25. Composition and testing

```
class FakeRepository:
    def __init__(self):
        self.saved = []

    def save(self, ticket):
        self.saved.append(ticket)
```

```
class TicketService:
    def __init__(self, repository):
        self.repository = repository

    def create_ticket(self, ticket):
        self.repository.save(ticket)
        return ticket
```

Test:

```
repository = FakeRepository()
service = TicketService(repository)

service.create_ticket({
    "id": "T-001",
    "title": "Cannot log in",
})

print(repository.saved)
```

You can test `TicketService` without:

- A real database.
- Network access.
- Cloud credentials.
- Production data.
- External side effects.

This is one of the strongest reasons composition is common in production software.

# 26. Deep inheritance is usually a warning

This hierarchy may become difficult:

```
class Object:
    ...


class User(Object):
    ...


class Employee(User):
    ...


class Engineer(Employee):
    ...


class AIEngineer(Engineer):
    ...


class SeniorAIEngineer(AIEngineer):
    ...
```

Deep hierarchies make it harder to understand:

- Where a method comes from.
- Which method `super()` calls.
- Which parent controls an attribute.
- What changing one class will affect.
- Whether all subclasses remain substitutable.

Prefer shallow inheritance and composition:

```
class User:
    ...


class AIEngineer(User):
    def __init__(self, model, tools):
        self.model = model
        self.tools = tools
```

The engineer is a user, but model and tools are components.

# 27. Mixins

A mixin is a small class intended to provide one focused capability through inheritance.

```
class JsonSerializableMixin:
    def to_json(self):
        import json

        return json.dumps(self.to_dict())
```

```
class LoggingMixin:
    def log(self, message):
        print(f"LOG: {message}")
```

```
class Ticket(
    JsonSerializableMixin,
    LoggingMixin,
):
    def __init__(self, ticket_id, title):
        self.ticket_id = ticket_id
        self.title = title

    def to_dict(self):
        return {
            "id": self.ticket_id,
            "title": self.title,
        }
```

Use:

```
ticket = Ticket(
    "T-001",
    "Cannot log in",
)

ticket.log("Ticket created.")
print(ticket.to_json())
```

Mixins should be:

- Small.
- Focused.
- Stateless or minimally stateful.
- Designed for cooperative inheritance.
- Not treated as complete standalone domain objects.

If a mixin grows too large, composition may be clearer.

# 28. Common mistakes

## Inheriting from unrelated classes

Incorrect:

```
class EmailSender(Database):
    ...
```

An email sender and database are separate concepts.

Use composition:

```
class EmailSender:
    def __init__(self, database):
        self.database = database
```

---

## Forgetting `super().__init__()`

```
class Parent:
    def __init__(self):
        self.ready = True


class Child(Parent):
    def __init__(self):
        self.name = "Child"
```

Now:

```
child = Child()
print(child.ready)
```

fails because the parent initialization never ran.

Correct:

```
class Child(Parent):
    def __init__(self):
        super().__init__()
        self.name = "Child"
```

---

## Calling `super()` when the parent has no useful behavior

You do not need to write:

```
super().some_method()
```

automatically everywhere.

Use it when you genuinely want to preserve or extend parent behavior.

---

## Exposing internal components unnecessarily

Composition does not mean every component must be publicly mutable.

Instead of:

```
assistant.model = another_model
```

you may use:

```
self._model = model
```

and provide controlled methods or properties.

---

## Using inheritance only for convenience

Avoid:

```
class MyService(SomeUnrelatedService):
    ...
```

just to reuse one method.

Prefer:

```
from helper_module import useful_function
```

or:

```
self.helper = Helper()
```

---

## Creating too many tiny classes

Composition is powerful, but do not make every two-line function a class.

This may be excessive:

```
class StringStripper:
    def run(self, value):
        return value.strip()
```

A normal function may be clearer:

```
def strip_text(value):
    return value.strip()
```

Use classes when the component has:

- State.
- A meaningful identity.
- Several related operations.
- A replaceable strategy.
- A clear interface.
- Lifecycle behavior.

# 29. A complete comparison example

## Inheritance design

```
class EmailReportService:
    def generate_and_send(self, data):
        report = self.generate(data)
        return self.send(report)

    def generate(self, data):
        return f"Report: {data}"

    def send(self, report):
        return f"Email sent: {report}"
```

```
class SlackReportService(EmailReportService):
    def send(self, report):
        return f"Slack sent: {report}"
```

This works, but inheritance says:

```
SlackReportService is an EmailReportService
```

That is conceptually false.

## Composition design

```
class ReportGenerator:
    def generate(self, data):
        return f"Report: {data}"
```

```
class EmailSender:
    def send(self, report):
        return f"Email sent: {report}"
```

```
class SlackSender:
    def send(self, report):
        return f"Slack sent: {report}"
```

```
class ReportService:
    def __init__(self, generator, sender):
        self.generator = generator
        self.sender = sender

    def generate_and_send(self, data):
        report = self.generator.generate(data)
        return self.sender.send(report)
```

Use:

```
email_service = ReportService(
    ReportGenerator(),
    EmailSender(),
)

slack_service = ReportService(
    ReportGenerator(),
    SlackSender(),
)
```

Now:

```
ReportService has a generator.
ReportService has a sender.
```

This relationship is accurate and flexible.

# 30. Decision tree

Ask these questions:

## Question 1

Is the relationship genuinely:

```
Child is a specialized Parent?
```

If yes, inheritance may be appropriate.

Example:

```
AdminUser is a User
```

## Question 2

Does the class merely need another object to perform work?

If yes, use composition.

Example:

```
TicketService uses a Repository
```

## Question 3

Do you want to swap implementations?

If yes, composition is usually better.

```
Agent(model=LocalModel())
```

# 31. Final project example

Here is a clean AI-service design using inheritance only where it makes sense and composition for replaceable components.

```
from typing import Protocol
```

Model interface:

```
class LLMProvider(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

Memory interface:

```
class Memory(Protocol):
    def search(self, query: str) -> str:
        ...
```

Concrete model:

```
class LocalModel:
    def generate(self, prompt: str) -> str:
        return f"Local response to: {prompt}"
```

Concrete memory:

```
class InMemorySearch:
    def search(self, query: str) -> str:
        return f"Context related to: {query}"
```

Composed assistant:

```
class SupportAssistant:
    def __init__(
        self,
        model: LLMProvider,
        memory: Memory,
    ):
        self._model = model
        self._memory = memory

    def answer(self, question: str) -> str:
        context = self._memory.search(question)

        prompt = (
            f"Context: {context}\n"
            f"Question: {question}"
        )

        return self._model.generate(prompt)
```

Use:

```
assistant = SupportAssistant(
    model=LocalModel(),
    memory=InMemorySearch(),
)

print(
    assistant.answer(
        "How do I reset my password?"
    )
)
```

The assistant does not inherit from the model or memory.

It **uses** them.

That gives you:

- Replaceable model providers.
- Replaceable memory systems.
- Easy testing.
- Clear responsibilities.
- A small interface.
- Low coupling.
- A strong foundation for agents and APIs.

# 32. Final cheat sheet

## Basic class

```
class User:
    def __init__(self, name):
        self.name = name

    def greet(self):
        return f"Hello, {self.name}"
```

## Inheritance

```
class AdminUser(User):
    def delete_user(self):
        ...
```

## `super()`

```
class AdminUser(User):
    def __init__(self, name, permissions):
        super().__init__(name)
        self.permissions = permissions
```

## Method overriding

```
class Dog(Animal):
    def speak(self):
        return "Woof!"
```

## Composition

```
class Service:
    def __init__(self, repository):
        self.repository = repository
```

## Dependency injection

```
service = Service(
    repository=InMemoryRepository()
)
```

## Main rule

```
Inheritance: “is-a”
Composition: “has-a” or “uses-a”
```

## Practical recommendation

```
Use classes to model meaningful objects.
Use inheritance for genuine specialization.
Use super() to cooperate with parent behavior.
Use composition for interchangeable components.
Use protocols to describe component interfaces.
Prefer shallow hierarchies and clear dependencies.
```

For your AI and startup systems, a strong architecture is usually:

```
Small inheritance hierarchy for domain categories
+
Protocols for interfaces
+
Composition for providers, tools, memory, repositories, and services
```

Python’s class system supports inheritance and method resolution, while composition lets you build flexible objects by delegating work to other objects. The best design usually combines both rather than treating them as mutually exclusive choices.[[docs.python](https://docs.python.org/3/tutorial/classes.html)]
