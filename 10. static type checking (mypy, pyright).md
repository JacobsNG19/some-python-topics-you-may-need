Static type checking analyzes your Python code **without running it** and reports likely type mistakes before they reach production. `mypy` and `pyright` both check Python annotations, but for your AI-engineering path, the most important skill is learning to annotate functions, run a checker, understand errors, and gradually make your project stricter. [typing.python](https://typing.python.org/)

# 1. Static versus dynamic checking

Python normally checks many things at runtime:

```python
def add(a, b):
    return a + b
```

This runs:

```python
print(add(2, 3))
```

But this may fail at runtime:

```python
print(add("two", 3))
```

Output:

```text
TypeError
```

Static type checking tries to detect the problem before execution:

```python
def add(a: int, b: int) -> int:
    return a + b
```

A checker can warn about:

```python
add("two", 3)
```

The program still remains Python. Type hints and checkers do not convert Python into Java or automatically enforce types at runtime.

## The workflow

```text
Write annotations
        ↓
Run mypy or pyright
        ↓
Read diagnostic
        ↓
Fix code or improve annotation
        ↓
Run tests
```

Mypy explicitly analyzes code statically, without executing it, and needs annotations to provide the most useful diagnostics. [mypy.readthedocs](https://mypy.readthedocs.io/en/stable/getting_started.html)

# 4. Mypy and Pyright differences

Both tools understand common Python typing features:

```python
list[str]
dict[str, int]
TypedDict
Protocol
Literal
Optional
Union
Generic types
```

| Feature | Mypy | Pyright |
|---|---|---|
| Static Python type checker | Yes | Yes |
| Works from terminal | Yes | Yes |
| Strong editor integration | Good | Excellent, especially with Pylance |
| Strictness configurable | Yes | Yes |
| Fast large-project analysis | Good | Especially strong |
| Common with Python projects | Very common | Very common |
| Main configuration | `mypy.ini`, `pyproject.toml` | `pyrightconfig.json`, `pyproject.toml` |

There is no universal winner. Use one consistently first. For your VS Code-based development, Pyright through Pylance is very convenient; for CI and explicit command-line checking, mypy is also an excellent choice.

Do not run both immediately and try to satisfy two different rule systems while learning. Start with one, then compare later.

# 5. Type inference

You do not need to annotate every local variable.

```python
name = "Toussaint"
age = 20
scores = [0.8, 0.9, 0.95]
```

A checker can infer:

```text
name   → str
age    → int
scores → list[float]
```

Then this error may be detected:

```python
age = "twenty"
```

A variable inferred as `int` should not later become a `str`.

## Explicit annotation

You can annotate when it improves clarity:

```python
name: str = "Toussaint"
age: int = 20
scores: list[float] = [0.8, 0.9, 0.95]
```

Use annotations especially for:

- Function parameters.
- Return values.
- Public class attributes.
- Complex dictionaries.
- Empty collections.
- Variables whose type is not obvious.
- Values that may be several types.

# 6. Untyped functions

Consider:

```python
def add(a, b):
    return a + b
```

Mypy may treat this function as dynamically typed and perform limited checking because the parameters and return value are unannotated. [mypy.readthedocs](https://mypy.readthedocs.io/en/stable/getting_started.html)

Add annotations:

```python
def add(a: int, b: int) -> int:
    return a + b
```

Now the checker can analyze calls:

```python
result = add(10, 20)
wrong = add("10", 20)
```

## Important principle

Type checking improves as annotations increase.

```text
No annotations → little useful checking
Some annotations → partial checking
Complete public interfaces → much stronger checking
Strict configuration → stronger project-wide guarantees
```

# 7. Checking return types

```python
def get_username() -> str:
    return "Toussaint"
```

Incorrect:

```python
def get_username() -> str:
    return 42
```

The checker reports that the function returns `int` instead of `str`.

Another example:

```python
def calculate_average(
    scores: list[float],
) -> float:
    return sum(scores) / len(scores)
```

Potential issue:

```python
calculate_average([])
```

The type is correct, but the value causes a runtime `ZeroDivisionError`.

This shows an important limitation:

```text
Static typing checks types, not every possible runtime condition.
```

You still need validation and tests:

```python
def calculate_average(
    scores: list[float],
) -> float:
    if not scores:
        raise ValueError("Scores cannot be empty.")

    return sum(scores) / len(scores)
```

# 8. `None` and type narrowing

```python
def find_username(user_id: str) -> str | None:
    if user_id == "U-001":
        return "Toussaint"

    return None
```

This is unsafe:

```python
username = find_username("U-999")

print(username.upper())
```

The result might be `None`.

Correct:

```python
username = find_username("U-999")

if username is None:
    print("User not found.")
else:
    print(username.upper())
```

The checker understands that inside the `else` branch:

```python
username
```

is definitely a `str`.

This process is called **type narrowing**.

## Other narrowing tools

```python
isinstance(value, str)
```

```python
if isinstance(value, str):
    print(value.upper())
```

```python
if value is not None:
    print(value)
```

```python
if isinstance(result, dict):
    ...
```

Good type checkers follow these conditions and narrow the possible type.

***

# 9. Unions and narrowing

```python
def format_value(value: int | str) -> str:
    if isinstance(value, int):
        return f"Number: {value}"

    return f"Text: {value}"
```

The checker knows:

```text
if branch → int
else branch → str
```

Another example:

```python
def parse_id(value: int | str) -> str:
    if isinstance(value, int):
        return f"ID-{value}"

    return value.upper()
```

Without narrowing, this may be unsafe:

```python
def uppercase(value: int | str) -> str:
    return value.upper()
```

Integers do not have `.upper()`.

# 10. `TypedDict` checking

```python
from typing import Literal, TypedDict
```

```python
class Ticket(TypedDict):
    id: str
    title: str
    priority: Literal["low", "normal", "high"]
```

Correct:

```python
ticket: Ticket = {
    "id": "T-001",
    "title": "Cannot log in",
    "priority": "high",
}
```

Incorrect priority:

```python
ticket: Ticket = {
    "id": "T-001",
    "title": "Cannot log in",
    "priority": "urgent",
}
```

Missing field:

```python
ticket: Ticket = {
    "id": "T-001",
    "title": "Cannot log in",
}
```

Wrong field type:

```python
ticket: Ticket = {
    "id": "T-001",
    "title": "Cannot log in",
    "priority": 10,
}
```

A static checker can detect all three categories of mistake.

Remember:

```text
TypedDict provides static structure.
It does not validate arbitrary runtime JSON automatically.
```

# 11. `Protocol` checking

```python
from typing import Protocol
```

```python
class LLMProvider(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

Compatible class:

```python
class LocalProvider:
    def generate(self, prompt: str) -> str:
        return f"Local response to: {prompt}"
```

Use it:

```python
def answer(
    provider: LLMProvider,
    question: str,
) -> str:
    return provider.generate(question)
```

```python
answer(LocalProvider(), "What is Python?")
```

Incompatible class:

```python
class BrokenProvider:
    def complete(self, prompt: str) -> str:
        return "Response"
```

This fails static checking:

```python
answer(BrokenProvider(), "What is Python?")
```

because the protocol requires:

```python
generate()
```

not:

```python
complete()
```

This is exactly where static type checking makes duck typing safer for AI architecture.

# 12. `Any` and type-checking escape hatches

```python
from typing import Any
```

```python
def process(data: Any) -> str:
    return data.some_method()
```

The checker usually allows this because `Any` disables many checks.

This is convenient:

```python
raw_data: Any = load_json()
```

But it spreads uncertainty:

```python
def step_one(data: Any) -> Any:
    ...


def step_two(data: Any) -> Any:
    ...


def step_three(data: Any) -> Any:
    ...
```

Now the checker provides little protection.

## Better boundary pattern

```python
from typing import Any
```

```python
def parse_category(data: Any) -> str:
    if not isinstance(data, dict):
        raise ValueError("Expected an object.")

    category = data.get("category")

    if not isinstance(category, str):
        raise ValueError(
            "Category must be a string."
        )

    return category
```

Use `Any` only at the raw boundary:

```text
raw external data → Any
                     ↓
                 validation
                     ↓
             precise internal type
```

# 13. Type errors versus runtime errors

Static checking catches things such as:

```python
name: str = 123
```

```python
items: list[int] = ["wrong"]
```

```python
user["missing_key"]
```

when the dictionary structure is known.

But it may not catch:

```python
items[0]
```

when `items` is empty.

It may not know that:

```python
api_response["user"]
```

is missing at runtime if the data was untyped.

It may not detect incorrect business logic:

```python
discount = price * 2
```

if both values are correctly typed as numbers.

Use three layers:

```text
Static checker → type consistency
Runtime validation → external and business rules
Tests → actual behavior
```

Static typing is not a replacement for tests.

# 16. The most useful errors to learn

## Incompatible argument

```python
def greet(name: str) -> str:
    return f"Hello {name}"


greet(123)
```

Fix:

```python
greet("123")
```

or change the function contract if integers are genuinely valid.

***

## Incompatible assignment

```python
count: int = "10"
```

Fix:

```python
count: int = 10
```

or:

```python
count = int("10")
```

***

## Missing return

```python
def find_user(user_id: str) -> dict[str, str]:
    if user_id == "U-001":
        return {"name": "Toussaint"}
```

Some execution paths return nothing.

Fix:

```python
def find_user(
    user_id: str,
) -> dict[str, str] | None:
    if user_id == "U-001":
        return {"name": "Toussaint"}

    return None
```

***

## Returning `None` incorrectly

```python
def get_name() -> str:
    return None
```

Fix the annotation:

```python
def get_name() -> str | None:
    return None
```

or return a string.

***

## Missing dictionary key

With:

```python
class Ticket(TypedDict):
    id: str
    title: str
```

this is likely detected:

```python
ticket["priority"]
```

because `priority` is not part of the declared structure.

***

## Attribute does not exist

```python
class User:
    name: str


user = User()
print(user.email)
```

The checker reports that `User` has no attribute `email`.

***

## Protocol mismatch

```python
class Provider(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

```python
class WrongProvider:
    def complete(self, prompt: str) -> str:
        return "Response"
```

Passing `WrongProvider()` where `Provider` is expected produces an interface error.

# 18. Generics

A generic function preserves the relationship between input and output types.

```python
from typing import TypeVar
```

```python
T = TypeVar("T")
```

```python
def first_item(items: list[T]) -> T:
    return items[0]
```

The checker understands:

```python
number = first_item([1, 2, 3])
```

as:

```text
number → int
```

and:

```python
name = first_item(["A", "B"])
```

as:

```text
name → str
```

Without a generic type variable, you might write:

```python
def first_item(items: list[Any]) -> Any:
    ...
```

which loses the relationship.

For your current level, understand the basic pattern:

```python
T = TypeVar("T")

def function(items: list[T]) -> T:
    ...
```

You can study advanced generics later.

class Arguments:

def render_result(

# 21. Type checking decorators

Decorators are more advanced because a decorator must preserve the parameter and return types of the wrapped function.

A simple decorator:

```python
from collections.abc import Callable
from functools import wraps
from typing import Any
```

```python
def log_call(
    function: Callable[..., Any],
) -> Callable[..., Any]:
    @wraps(function)
    def wrapper(*args: Any, **kwargs: Any) -> Any:
        print(f"Calling {function.__name__}")
        return function(*args, **kwargs)

    return wrapper
```

This works, but `Any` weakens type checking.

A more precise generic decorator requires `ParamSpec` and `TypeVar`:

```python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar
```

```python
P = ParamSpec("P")
R = TypeVar("R")
```

```python
def log_call(
    function: Callable[P, R],
) -> Callable[P, R]:
    @wraps(function)
    def wrapper(
        *args: P.args,
        **kwargs: P.kwargs,
    ) -> R:
        print(f"Calling {function.__name__}")

        return function(*args, **kwargs)

    return wrapper
```

Use it:

```python
@log_call
def add(first: int, second: int) -> int:
    return first + second
```

The checker preserves:

```text
add(int, int) → int
```

This is the advanced, production-quality decorator typing pattern.

For now, understand:

```text
Any-based decorator → easier, less precise
ParamSpec-based decorator → harder, preserves exact function signature
```

# 22. Suppressing an error intentionally

Sometimes a checker is wrong, incomplete, or unable to understand a dynamic library.

Mypy:

```python
value = dynamic_library_call()  # type: ignore
```

Better:

```python
value = dynamic_library_call()  # type: ignore[no-any-return]
```

Pyright:

```python
value = dynamic_library_call()  # pyright: ignore[reportUnknownVariableType]
```

Use suppression only when:

- You understand the error.
- You have verified the code is safe.
- The library is dynamically typed.
- You cannot immediately improve the annotation.

Avoid:

```python
# type: ignore
```

everywhere.

Configure warnings for unused suppressions:

```ini
[mypy]
warn_unused_ignores = True
```

That helps remove old workarounds when the code improves.

# 23. Third-party libraries

A type checker needs type information about imported libraries.

Some packages include type hints directly.

Others provide separate stub packages:

```bash
python -m pip install types-requests
```

For a library without type information, the checker may report:

```text
Skipping analyzing ...
```

or treat it as:

```python
Any
```

This reduces checking inside the affected area.

Practical choices:

```text
Install official type stubs.
Use a typed alternative.
Write a small local protocol.
Add a narrow type ignore.
Wrap the library behind a typed adapter.
```

For example, instead of allowing an untyped cloud SDK throughout your application, create:

```python
class ModelClient(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

Then isolate the third-party integration in one module.

# 24. A typed project example

Project:

```text
trustdesk/
├── src/
│   └── trustdesk/
│       ├── __init__.py
│       ├── models.py
│       ├── providers.py
│       └── service.py
└── pyproject.toml
```

`models.py`:

```python
from typing import Literal, TypedDict


Category = Literal[
    "billing",
    "account_access",
    "technical_issue",
    "general",
]
```

```python
class ClassificationResult(TypedDict):
    category: Category
    confidence: float
```

`providers.py`:

```python
from typing import Protocol

from .models import ClassificationResult
```

```python
class Classifier(Protocol):
    def classify(
        self,
        text: str,
    ) -> ClassificationResult:
        ...
```

`service.py`:

```python
from .models import ClassificationResult
from .providers import Classifier
```

```python
class TicketService:
    def __init__(self, classifier: Classifier):
        self._classifier = classifier

    def classify_ticket(
        self,
        text: str,
    ) -> ClassificationResult:
        return self._classifier.classify(text)
```

Implementation:

```python
from .models import ClassificationResult
```

```python
class KeywordClassifier:
    def classify(
        self,
        text: str,
    ) -> ClassificationResult:
        normalized = text.lower()

        if "payment" in normalized:
            return {
                "category": "billing",
                "confidence": 0.96,
            }

        return {
            "category": "general",
            "confidence": 0.55,
        }
```

Usage:

```python
from trustdesk.providers import Classifier
from trustdesk.service import TicketService
```

```python
service = TicketService(KeywordClassifier())

result = service.classify_ticket(
    "My payment failed."
)
```

A checker verifies:

- `KeywordClassifier` satisfies `Classifier`.
- The returned dictionary matches `ClassificationResult`.
- Categories use allowed literal values.
- `TicketService` receives a compatible classifier.
- Method arguments and return values are consistent.

This is a strong architecture for gradually building typed AI systems.

# 25. Recommended workflow for you

## Step 1: Annotate public functions

Start here:

```python
def classify_ticket(
    text: str,
) -> ClassificationResult:
    ...
```

Do not begin by annotating every local variable.

## Step 2: Add structured types

Use:

```python
TypedDict
Literal
Protocol
```

for API payloads, model outputs, and interchangeable services.

## Step 3: Run a checker

```bash
mypy src/
```

or:

```bash
pyright
```

## Step 4: Fix high-value errors first

Prioritize:

- Wrong function arguments.
- Wrong return values.
- Missing `None` handling.
- Incorrect dictionary keys.
- Protocol mismatches.
- Unchecked external data.
- Accidental `Any`.

## Step 5: Configure gradually

Begin with basic or moderate checking.

Then increase toward:

```text
strict
```

after your project’s type quality improves.

## Step 6: Add checking to CI

Example GitHub Actions command:

```bash
python -m mypy src/
python -m pytest
```

A pull request should fail if type checking or tests fail.

# 26. Mypy or Pyright: recommendation

For you, use **Pyright first if you work primarily in VS Code**, because its editor integration gives immediate feedback while writing code. Use **mypy if you prefer a command-line-centered workflow or want to follow projects that already standardize on it**.

A practical setup:

```text
Editor feedback → Pyright/Pylance
CI command      → Pyright or mypy
Tests           → pytest
Formatting      → Ruff formatter or Black
Linting         → Ruff
```

Do not confuse these tools:

| Tool | Main purpose |
|---|---|
| Pyright/mypy | Type checking |
| pytest | Testing behavior |
| Ruff | Linting and many code-quality checks |
| Black/Ruff formatter | Formatting |
| Pylance | VS Code language server, commonly powered by Pyright |

Mypy and Pyright are both legitimate choices; consistency within a project matters more than constantly comparing them. Pyright describes itself as standards-compliant and designed for high-performance checking of large Python source bases, while mypy is widely used for gradual static typing. [mypy.readthedocs](https://mypy.readthedocs.io/en/stable/getting_started.html)

# 27. Practice exercise

Create `typed_ticket.py`:

```python
from typing import Literal, TypedDict


Priority = Literal["low", "normal", "high"]


class Ticket(TypedDict):
    id: str
    title: str
    priority: Priority


def create_ticket(
    ticket_id: str,
    title: str,
    priority: Priority,
) -> Ticket:
    return {
        "id": ticket_id,
        "title": title,
        "priority": priority,
    }


ticket = create_ticket(
    "T-001",
    "Cannot log in",
    "high",
)

print(ticket)
```

The key distinction is:

```text
Type hints describe your intended contracts.
Mypy and Pyright inspect those contracts statically.
Runtime validation protects real external data.
Tests verify actual behavior.
```

For your TrustDesk and Burvex projects, a very useful combination is:

```text
Protocol       → model providers, repositories, tools
TypedDict      → API payloads and structured results
Literal        → statuses, modes, categories, priorities
Optional       → operations that may return no result
Any            → raw external data only, before validation
Pyright/mypy   → detect inconsistent usage before execution
```
