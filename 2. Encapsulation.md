Encapsulation in Python means designing an object so that its **public interface** is simple and safe, while its internal data and implementation details remain controlled and interchangeable. In Python, this is based more on conventions and managed attributes than on strict `private` keywords as in Java or C++.

# 1. The core idea

Imagine a bank-account object.

Users of your class should be able to do this:

```
account.deposit(50)
account.withdraw(20)
print(account.balance)
```

But they should _not_ need to know:

- How the balance is stored internally
- How you prevent negative deposits
- How transactions are recorded
- Whether balance is stored as an integer, a decimal value, or calculated from transactions

That separation is encapsulation.

> **Public interface:** what other code is allowed and expected to use.  
> **Internal implementation:** how the object actually works behind the interface.

A good rule:

```
Expose what users need.
Hide what users should not depend on.
Validate values at the boundary.
```

Python classes bundle data and functionality together, which is the foundation for encapsulation.

---

# 2. Why encapsulation matters

Encapsulation is not only “hiding variables.” Its real purpose is protecting the **rules** of an object.

For example, a bank balance should never become invalid because someone accidentally writes:

```
account.balance = -1_000_000
```

Or a user age should not accept:

```
user.age = -10
```

Encapsulation lets the class control these changes.

## Main benefits

- **Validation:** reject invalid data before it damages the object’s state.
- **Safer code:** prevent accidental modification of internal details.
- **Cleaner APIs:** users call meaningful methods such as `deposit()` rather than manually changing internal values.
- **Flexibility:** you can change internal storage later without forcing all code that uses your class to change.
- **Maintainability:** implementation details stay in one place.
- **Debugging:** validation and logging logic can be centralized.
- **Backward compatibility:** a plain attribute can later become a managed property while preserving the external API.

# 3. Python access levels

Languages such as Java have explicit access modifiers:

```
public
private
protected
```

Python deliberately works differently. It has no truly enforced private instance variables in the normal sense. Instead, it relies on naming conventions and a feature called **name mangling**.

|Style|Example|Meaning|Enforcement|
|---|---|---|---|
|Public|`name`|Part of the intended public API|Fully accessible|
|Internal / non-public|`_name`|“Do not use directly outside this class/module”|Convention only|
|Name-mangled|`__name`|Avoid accidental access and subclass naming conflicts|Limited language support|
|Special / dunder|`__init__`|Python’s special protocol methods|Do not invent casually|

## 3.1 Public attributes

A public attribute is meant to be used directly:

```
class Student:
    def __init__(self, name):
        self.name = name


student = Student("Toussaint")
print(student.name)

student.name = "Aline"
print(student.name)
```

Output:

```
Toussaint
Aline
```

This is acceptable when there are no special rules around the value.

For example, an immutable ID or a simple display label may reasonably be public.

---

## 3.2 Single underscore: `_name`

A single leading underscore signals:

> “This is internal. You technically can access it, but you should not depend on it.”

```
class BankAccount:
    def __init__(self, owner, initial_balance):
        self.owner = owner           # Public
        self._balance = initial_balance  # Internal by convention


account = BankAccount("Toussaint", 100)

print(account.owner)      # Intended public use
print(account._balance)   # Works, but should be avoided externally
```

Python will not block this:

```
account._balance = -500
```

But it is poor design because it bypasses the class’s rules.

The official Python documentation describes names beginning with one underscore as non-public implementation details that may change without notice.[[docs.python](https://docs.python.org/3/tutorial/classes.html)]

### When to use `_attribute`

Use it for internal storage:

```
self._balance
self._password_hash
self._database_connection
self._transaction_history
self._model
self._api_key
```

This is the most common Python convention for encapsulation.

---

## 3.3 Double underscore: `__name`

A double leading underscore triggers **name mangling**.

```
class Example:
    def __init__(self):
        self.__secret = "Hidden value"

    def reveal_secret(self):
        return self.__secret


obj = Example()

print(obj.reveal_secret())
```

This works:

```
Hidden value
```

But direct access fails:

```
print(obj.__secret)
```

You will get something like:

```
AttributeError: 'Example' object has no attribute '__secret'
```

Python internally changes the name:

```
obj._Example__secret
```

So this will still work:

```
print(obj._Example__secret)
```

Therefore, `__secret` is **not real security**. It is not an unbreakable private variable. Its primary purpose is to reduce accidental access and avoid naming conflicts in subclasses.[[docs.python](https://docs.python.org/3/tutorial/classes.html)]

## Important rule

Do not use double underscores merely because you want everything to be “private.”

Prefer:

```
self._balance
```

Use:

```
self.__balance
```

only when you specifically need to avoid accidental override or collision in inheritance hierarchies.

# 4. The problem with direct attributes

Start with a simple class:

```
class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius
```

Use it:

```
weather = Temperature(25)
print(weather.celsius)

weather.celsius = -500
print(weather.celsius)
```

The object accepts an unrealistic value because there is no validation.

A beginner might try Java-style getters and setters:

```
class Temperature:
    def __init__(self, celsius):
        self._celsius = celsius

    def get_celsius(self):
        return self._celsius

    def set_celsius(self, value):
        if value < -273.15:
            raise ValueError("Temperature cannot be below absolute zero.")
        self._celsius = value
```

Usage:

```
temp = Temperature(20)

temp.set_celsius(30)
print(temp.get_celsius())
```

This works, but it is usually not the most Pythonic design.

Python prefers **properties**.

---

# 5. Properties: Python’s main tool

A property lets you write methods that behave like attributes.

Instead of this:

```
temp.set_celsius(25)
print(temp.get_celsius())
```

You can write this:

```
temp.celsius = 25
print(temp.celsius)
```

But Python runs validation logic behind the scenes.

Properties are managed attributes: they can define custom behavior when an attribute is read, assigned, or deleted.[[realpython](https://realpython.com/python-property/)]

## 5.1 Read-only property

```
class BankAccount:
    def __init__(self, owner, initial_balance=0):
        self.owner = owner
        self._balance = initial_balance

    @property
    def balance(self):
        return self._balance
```

Usage:

```
account = BankAccount("Toussaint", 500)

print(account.balance)
```

Output:

```
500
```

Now try to modify it:

```
account.balance = 1000
```

This raises an error:

```
AttributeError: property 'balance' of 'BankAccount' object has no setter
```

The public can read `balance`, but only the class controls how it changes.

This is excellent for values that should be changed only through business methods such as `deposit()` and `withdraw()`.

---

## 5.2 Property with a setter

Here is a complete temperature example:

```
class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        if not isinstance(value, (int, float)):
            raise TypeError("Celsius must be a number.")

        if value < -273.15:
            raise ValueError(
                "Temperature cannot be below absolute zero."
            )

        self._celsius = value
```

Usage:

```
temp = Temperature(25)

print(temp.celsius)

temp.celsius = 30
print(temp.celsius)
```

Output:

```
25
30
```

Invalid input:

```
temp.celsius = -500
```

Output:

```
ValueError: Temperature cannot be below absolute zero.
```

## What happens internally?

When Python sees:

```
temp.celsius = 30
```

it calls:

```
temp.celsius.setter(30)
```

Conceptually, it executes:

```
self._celsius = value
```

only after validation succeeds.

When Python sees:

```
print(temp.celsius)
```

it calls the getter:

```
@property
def celsius(self):
    return self._celsius
```

# 6. Full property structure

A property can have three parts:

1. Getter: controls reading.
2. Setter: controls assignment.
3. Deleter: controls `del object.attribute`.

```
class UserProfile:
    def __init__(self, username):
        self.username = username

    @property
    def username(self):
        return self._username

    @username.setter
    def username(self, value):
        if not isinstance(value, str):
            raise TypeError("Username must be a string.")

        cleaned = value.strip()

        if len(cleaned) < 3:
            raise ValueError("Username must have at least 3 characters.")

        self._username = cleaned

    @username.deleter
    def username(self):
        print("Removing username.")
        del self._username
```

Usage:

```
user = UserProfile("  toussaint_ai  ")

print(user.username)
```

Output:

```
toussaint_ai
```

Delete it:

```
del user.username
```

Output:

```
Removing username.
```

Usually, you do **not** need a deleter. Use one only if deletion is meaningful and safe in your domain model.

# 7. Encapsulation with business methods

The strongest encapsulation does not expose every field for arbitrary modification. It exposes actions that match the real-world domain.

For a bank account, users should deposit or withdraw—not directly set a balance.

```
class BankAccount:
    def __init__(self, owner, initial_balance=0):
        if initial_balance < 0:
            raise ValueError("Initial balance cannot be negative.")

        self.owner = owner
        self._balance = initial_balance
        self._transactions = []

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        self._validate_positive_amount(amount)

        self._balance += amount
        self._transactions.append(f"Deposit: +{amount}")

    def withdraw(self, amount):
        self._validate_positive_amount(amount)

        if amount > self._balance:
            raise ValueError("Insufficient funds.")

        self._balance -= amount
        self._transactions.append(f"Withdrawal: -{amount}")

    def transaction_history(self):
        return self._transactions.copy()

    def _validate_positive_amount(self, amount):
        if not isinstance(amount, (int, float)):
            raise TypeError("Amount must be numeric.")

        if amount <= 0:
            raise ValueError("Amount must be greater than zero.")
```

Usage:

```
account = BankAccount("Toussaint", 1_000)

account.deposit(250)
account.withdraw(400)

print(account.balance)
print(account.transaction_history())
```

Possible output:

```
850
['Deposit: +250', 'Withdrawal: -400']
```

## Why return `.copy()`?

This is a subtle but important encapsulation detail.

Bad version:

```
def transaction_history(self):
    return self._transactions
```

External code could change your internal list:

```
history = account.transaction_history()
history.clear()
```

Now the bank account’s internal history is destroyed.

Better version:

```
def transaction_history(self):
    return self._transactions.copy()
```

Or return an immutable tuple:

```
def transaction_history(self):
    return tuple(self._transactions)
```

Then external code cannot modify the account’s actual internal list.

# 8. Protecting mutable data

Encapsulation is especially important when attributes contain mutable objects such as:

- Lists
- Dictionaries
- Sets
- Nested data structures
- DataFrames
- Configuration dictionaries
- API request histories

Consider this weak design:

```
class StartupProject:
    def __init__(self):
        self.tasks = []
```

Someone can do:

```
project = StartupProject()

project.tasks.append("Build MVP")
project.tasks = "Not a list anymore"
```

Now your object is in an invalid state.

A safer design:

```
class StartupProject:
    def __init__(self, name):
        self.name = name
        self._tasks = []

    @property
    def tasks(self):
        return tuple(self._tasks)

    def add_task(self, task):
        if not isinstance(task, str):
            raise TypeError("Task must be a string.")

        task = task.strip()

        if not task:
            raise ValueError("Task cannot be empty.")

        self._tasks.append(task)

    def remove_task(self, task):
        if task not in self._tasks:
            raise ValueError("Task does not exist.")

        self._tasks.remove(task)
```

Usage:

```
project = StartupProject("TrustDesk MVP")

project.add_task("Define customer problem")
project.add_task("Build authentication API")

print(project.tasks)
```

Output:

```
('Define customer problem', 'Build authentication API')
```

This is a better startup-product model: the class guards the integrity of its task list.

# 9. Computed properties

A property does not have to return a stored attribute. It can calculate a value.

```
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    @property
    def area(self):
        return self.width * self.height

    @property
    def perimeter(self):
        return 2 * (self.width + self.height)
```

Usage:

```
rectangle = Rectangle(10, 5)

print(rectangle.area)
print(rectangle.perimeter)
```

Output:

```
50
30
```

Notice that you access them like attributes:

```
rectangle.area
```

not like methods:

```
rectangle.area()
```

Because `area` and `perimeter` represent information _about the object_, not actions the user is asking it to perform.

## Computed property with validation

```
class Product:
    def __init__(self, price, discount_percent=0):
        self.price = price
        self.discount_percent = discount_percent

    @property
    def price(self):
        return self._price

    @price.setter
    def price(self, value):
        if value < 0:
            raise ValueError("Price cannot be negative.")

        self._price = value

    @property
    def discount_percent(self):
        return self._discount_percent

    @discount_percent.setter
    def discount_percent(self, value):
        if not 0 <= value <= 100:
            raise ValueError("Discount must be between 0 and 100.")

        self._discount_percent = value

    @property
    def final_price(self):
        return self.price * (1 - self.discount_percent / 100)
```

Usage:

```
product = Product(price=100, discount_percent=20)

print(product.final_price)
```

Output:

```
80.0
```

`final_price` should usually be read-only because it is derived from other controlled values.

# 10. Property with `property()`

The decorator form is best in most cases:

```
@property
def name(self):
    ...
```

But Python also provides the built-in `property()` function.

```
class Person:
    def __init__(self, name):
        self._name = name

    def get_name(self):
        return self._name

    def set_name(self, value):
        if not value.strip():
            raise ValueError("Name cannot be empty.")

        self._name = value.strip()

    name = property(get_name, set_name)
```

Usage:

```
person = Person("Toussaint")
print(person.name)

person.name = "Jacobs"
print(person.name)
```

The decorator version is clearer and more common:

```
class Person:
    def __init__(self, name):
        self.name = name

    @property
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        if not value.strip():
            raise ValueError("Name cannot be empty.")

        self._name = value.strip()
```

Properties are descriptors: special class-level objects that customize attribute access.[[realpython](https://realpython.com/python-property/)][[docs.python](https://docs.python.org/3/reference/datamodel.html)]

# 11. A professional example: secure user account

For an AI product, SaaS application, or platform like TrustDesk, you may need an account model that protects sensitive fields and exposes safe operations.

```
from hashlib import sha256


class UserAccount:
    def __init__(self, email, password):
        self.email = email
        self._password_hash = None
        self.set_password(password)

    @property
    def email(self):
        return self._email

    @email.setter
    def email(self, value):
        if not isinstance(value, str):
            raise TypeError("Email must be a string.")

        value = value.strip().lower()

        if "@" not in value:
            raise ValueError("Email must contain '@'.")

        self._email = value

    @property
    def password_hash(self):
        raise AttributeError(
            "Password hashes are not available through the public API."
        )

    def set_password(self, password):
        if not isinstance(password, str):
            raise TypeError("Password must be a string.")

        if len(password) < 12:
            raise ValueError(
                "Password must contain at least 12 characters."
            )

        self._password_hash = sha256(
            password.encode()
        ).hexdigest()

    def verify_password(self, password):
        candidate_hash = sha256(
            password.encode()
        ).hexdigest()

        return candidate_hash == self._password_hash
```

Usage:

```
user = UserAccount(
    email="TOUSSAINT@EXAMPLE.COM",
    password="strong-password-2026"
)

print(user.email)
print(user.verify_password("strong-password-2026"))
print(user.verify_password("wrong-password"))
```

Output:

```
toussaint@example.com
True
False
```

Trying this:

```
print(user.password_hash)
```

raises:

```
AttributeError: Password hashes are not available through the public API.
```

## Security note

The example uses `sha256` only to demonstrate encapsulation. In a real application, do **not** store passwords with plain SHA-256. Use a password-hashing algorithm designed for passwords, such as Argon2, bcrypt, or scrypt, with an established security library. Encapsulation helps protect the interface, but it does not replace sound cryptographic design.

# 12. Name mangling and inheritance

Double underscores are most useful when inheritance could create accidental name collisions.

```
class Parent:
    def __init__(self):
        self.__value = "Parent value"

    def get_parent_value(self):
        return self.__value


class Child(Parent):
    def __init__(self):
        super().__init__()
        self.__value = "Child value"

    def get_child_value(self):
        return self.__value
```

Usage:

```
child = Child()

print(child.get_parent_value())
print(child.get_child_value())
```

Output:

```
Parent value
Child value
```

Why does this work?

Python turns these into different names:

```
self._Parent__value
self._Child__value
```

So the child does not accidentally overwrite the parent’s internal value.

You can inspect this:

```
print(child.__dict__)
```

Possible output:

```
{
    '_Parent__value': 'Parent value',
    '_Child__value': 'Child value'
}
```

That is the real value of name mangling: avoiding unintended clashes, not hiding secrets.[[docs.python](https://docs.python.org/3/tutorial/classes.html)]

# 13. Encapsulation and inheritance

When you create a class that may be extended by subclasses, think about three categories of methods and attributes.

|Category|Naming|Intended users|
|---|---|---|
|Public API|`predict()`, `save()`, `name`|Everyone using the object|
|Internal implementation|`_load_model()`, `_cache`|The class and advanced subclasses|
|Collision-protected internal detail|`__token`, `__state`|Primarily the defining class|

Example:

```
class BaseModelService:
    def predict(self, text):
        cleaned_text = self._clean_text(text)
        return self._run_inference(cleaned_text)

    def _clean_text(self, text):
        return text.strip().lower()

    def _run_inference(self, text):
        raise NotImplementedError(
            "Subclasses must implement _run_inference()."
        )
```

A subclass:

```
class SentimentService(BaseModelService):
    def _run_inference(self, text):
        if "good" in text:
            return "positive"

        return "neutral"
```

Usage:

```
service = SentimentService()
print(service.predict(" This product is good "))
```

Output:

```
positive
```

This is a clean design:

- `predict()` is public.
- `_clean_text()` is an internal reusable helper.
- `_run_inference()` has one underscore because it is intended as an extension point for subclasses.

Do not use double underscores for methods you intentionally expect subclasses to override. Name mangling makes overriding more difficult and confusing.

# 14. Properties versus methods

A common design question is:

> Should this be a property or a method?

Use a **property** when retrieving a value is simple, expected, and does not create surprising side effects.

```
user.full_name
account.balance
product.final_price
model.is_ready
rectangle.area
```

Use a **method** when the operation:

- Performs an action
- Has significant side effects
- May take noticeable time
- Makes a network/database request
- Requires arguments
- Is computationally expensive
- Changes state

```
account.deposit(100)
account.withdraw(50)
model.train(dataset)
model.save("model.pkl")
agent.run(task)
database.connect()
```

## Example: bad and good API design

Less clear:

```
account.get_balance()
account.set_balance(500)
```

More Pythonic:

```
account.balance
```

But for an operation that changes business state:

```
account.deposit(500)
```

is much clearer than:

```
account.balance = account.balance + 500
```

# 15. Avoid this common bug

A frequent beginner mistake is creating infinite recursion inside a property.

## Incorrect

```
class Person:
    @property
    def name(self):
        return self.name
```

When Python evaluates `self.name`, it calls `name()` again, forever.

This results in:

```
RecursionError
```

## Correct

Use a separate internal attribute:

```
class Person:
    def __init__(self, name):
        self._name = name

    @property
    def name(self):
        return self._name
```

The pattern is:

```
public property: name
internal storage: _name
```

Another common mistake:

```
class Person:
    @property
    def age(self):
        return self._age

    @age.setter
    def age(self, value):
        self.age = value  # Wrong: recursive call
```

Correct version:

```
class Person:
    @property
    def age(self):
        return self._age

    @age.setter
    def age(self, value):
        self._age = value
```

# 16. Validation in `__init__`

A clean pattern is to route initialization through your property setter.

```
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

    @property
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        value = value.strip()

        if not value:
            raise ValueError("Name cannot be empty.")

        self._name = value

    @property
    def salary(self):
        return self._salary

    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Salary cannot be negative.")

        self._salary = value
```

This is better than duplicating validation:

```
# Avoid repeating the same rules in __init__ and in setters.
```

Usage:

```
employee = Employee("Toussaint", 1_500)

employee.salary = 2_000
print(employee.salary)
```

Both initial creation and later changes follow the same validation rules.

# 17. Read-only objects and immutable views

Sometimes you want an object’s value to be readable but not replaceable.

```
class APIResponse:
    def __init__(self, request_id, status_code, data):
        self._request_id = request_id
        self._status_code = status_code
        self._data = dict(data)

    @property
    def request_id(self):
        return self._request_id

    @property
    def status_code(self):
        return self._status_code

    @property
    def data(self):
        return self._data.copy()
```

Usage:

```
response = APIResponse(
    request_id="req_123",
    status_code=200,
    data={"result": "approved"}
)

print(response.data)
```

This protects `_data` from external mutation:

```
external_data = response.data
external_data["result"] = "changed"

print(response.data)
```

Output remains:

```
{'result': 'approved'}
```

because `response.data` gives a copy, not the actual internal dictionary.

## Shallow versus deep copy

A normal `.copy()` is a **shallow copy**.

```
data = {
    "user": {
        "name": "Toussaint"
    }
}
```

If nested dictionaries or lists must also be protected, use `copy.deepcopy()`:

```
from copy import deepcopy


@property
def data(self):
    return deepcopy(self._data)
```

Use deep copies carefully: they can be expensive for large or complex data structures.

# 18. `__slots__` and encapsulation

`__slots__` is an advanced feature that restricts which instance attributes can normally exist. It can reduce memory use when you create many objects, and it can prevent accidental creation of misspelled attributes.

```
class Point:
    __slots__ = ("_x", "_y")

    def __init__(self, x, y):
        self._x = x
        self._y = y

    @property
    def x(self):
        return self._x

    @property
    def y(self):
        return self._y
```

Usage:

```
point = Point(3, 4)

print(point.x)
print(point.y)
```

This is not allowed:

```
point.z = 10
```

You will get an `AttributeError` because `z` is not listed in `__slots__`.

## Important limitations

`__slots__` does **not** make attributes private.

This still works:

```
point._x = 100
```

So use `__slots__` for memory optimization and controlled object shape—not as a security mechanism. Python implements slots through descriptors created at the class level.[[docs.python](https://docs.python.org/3/reference/datamodel.html)]

# 19. Descriptors: advanced encapsulation

A descriptor is an object that controls attribute access through special methods:

```
__get__()
__set__()
__delete__()
```

Properties themselves are descriptors.[[realpython](https://realpython.com/python-property/)][[docs.python](https://docs.python.org/3/reference/datamodel.html)]

Descriptors become useful when you want to reuse the same validation behavior across many classes.

## Example: reusable positive-number validator

```
class PositiveNumber:
    def __set_name__(self, owner, name):
        self.public_name = name
        self.private_name = f"_{name}"

    def __get__(self, instance, owner):
        if instance is None:
            return self

        return getattr(instance, self.private_name)

    def __set__(self, instance, value):
        if not isinstance(value, (int, float)):
            raise TypeError(
                f"{self.public_name} must be a number."
            )

        if value <= 0:
            raise ValueError(
                f"{self.public_name} must be greater than zero."
            )

        setattr(instance, self.private_name, value)
```

Use it in multiple classes:

```
class Subscription:
    monthly_price = PositiveNumber()
    duration_months = PositiveNumber()

    def __init__(self, monthly_price, duration_months):
        self.monthly_price = monthly_price
        self.duration_months = duration_months

    @property
    def total_price(self):
        return self.monthly_price * self.duration_months
```

Usage:

```
subscription = Subscription(
    monthly_price=15,
    duration_months=12
)

print(subscription.total_price)
```

Output:

```
180
```

Invalid input:

```
subscription.monthly_price = -10
```

Output:

```
ValueError: monthly_price must be greater than zero.
```

## How it works

When you write:

```
subscription.monthly_price = 15
```

Python calls:

```
PositiveNumber.__set__(subscription, 15)
```

When you write:

```
subscription.monthly_price
```

Python calls:

```
PositiveNumber.__get__(subscription, Subscription)
```

Descriptors let you build reusable rules for:

- Positive values
- Email validation
- Typed fields
- Range checking
- Lazy loading
- ORM model fields
- Configuration settings
- Access logging
- Permission-controlled values

# 20. `@dataclass` and encapsulation

Dataclasses reduce boilerplate, but you still need deliberate encapsulation.

## Basic dataclass

```
from dataclasses import dataclass


@dataclass
class User:
    name: str
    age: int
```

This is convenient, but it accepts invalid values:

```
user = User("Toussaint", -5)
```

For validation and protected storage, use `field(init=False)` plus properties.

```
from dataclasses import dataclass, field


@dataclass
class User:
    name: str
    _age: int = field(init=False, repr=False)

    def __init__(self, name, age):
        self.name = name
        self.age = age

    @property
    def age(self):
        return self._age

    @age.setter
    def age(self, value):
        if not isinstance(value, int):
            raise TypeError("Age must be an integer.")

        if value < 0:
            raise ValueError("Age cannot be negative.")

        self._age = value
```

In real projects, choose the simplest design that preserves your rules. Do not add properties for every attribute automatically.

# 21. Encapsulation for AI applications

As you build AI agents, APIs, and startup products, encapsulation becomes very practical.

Imagine an AI model service. Users should ask it to predict, but they should not need direct access to model-loading, tokenization, cache management, or API keys.

```
class AIModelService:
    def __init__(self, model_name):
        self.model_name = model_name
        self._model = None
        self._is_loaded = False
        self._request_count = 0

    @property
    def is_loaded(self):
        return self._is_loaded

    @property
    def request_count(self):
        return self._request_count

    def load(self):
        if self._is_loaded:
            return

        self._model = f"Loaded model: {self.model_name}"
        self._is_loaded = True

    def predict(self, prompt):
        if not self._is_loaded:
            raise RuntimeError(
                "Model is not loaded. Call load() first."
            )

        if not isinstance(prompt, str) or not prompt.strip():
            raise ValueError(
                "Prompt must be a non-empty string."
            )

        self._request_count += 1

        return {
            "model": self.model_name,
            "response": f"Processed: {prompt.strip()}",
        }
```

Usage:

```
service = AIModelService("trustdesk-classifier")

service.load()

result = service.predict(
    "Classify this support request."
)

print(result)
print(service.request_count)
```

The public API is small and understandable:

```
service.load()
service.predict(prompt)
service.is_loaded
service.request_count
```

The internal implementation remains replaceable:

```
service._model
service._request_count
```

Later, you could replace local inference with an external model API, Redis caching, rate limiting, telemetry, or a queue—without changing how the rest of your application calls `predict()`.

That is the business value of encapsulation: internal change without breaking external users.

# 22. Encapsulation mistakes to avoid

## Making every variable “private”

Not every attribute needs a property.

This is often unnecessary:

```
class Book:
    def __init__(self, title):
        self._title = title

    @property
    def title(self):
        return self._title

    @title.setter
    def title(self, value):
        self._title = value
```

If there is no validation, transformation, computed logic, or future need for control, a public attribute can be fine:

```
class Book:
    def __init__(self, title):
        self.title = title
```

Use properties because you need behavior—not automatically.

---

## Directly changing internal state

Avoid:

```
account._balance = -1_000
```

Prefer:

```
account.withdraw(1_000)
```

The method can validate the action and preserve the object’s invariants.

---

## Treating `__name` as security

This is not secure:

```
self.__api_key = "secret"
```

The value can still be found through name mangling, debugging, object inspection, logs, memory, or source code.

Never put secrets directly in source code. Use environment variables, secret managers, access controls, and secure server-side architecture.

---

## Returning internal mutable objects

Avoid:

```
@property
def users(self):
    return self._users
```

Prefer:

```
@property
def users(self):
    return tuple(self._users)
```

or:

```
from copy import deepcopy

@property
def users(self):
    return deepcopy(self._users)
```

depending on your data structure and performance requirements.

---

## Side effects in a property

Avoid a property that silently makes a network request:

```
@property
def customer_data(self):
    return requests.get("...").json()
```

This looks cheap but may be slow, fail, cost money, or have side effects.

Prefer an explicit method:

```
def fetch_customer_data(self):
    ...
```

A property should generally behave like information retrieval, not a hidden expensive action.

# 23. Testing encapsulation

You should test that invalid states are rejected and public behavior works.

```
import pytest


def test_deposit_increases_balance():
    account = BankAccount("Toussaint", 100)

    account.deposit(50)

    assert account.balance == 150


def test_negative_deposit_is_rejected():
    account = BankAccount("Toussaint", 100)

    with pytest.raises(ValueError):
        account.deposit(-20)


def test_withdrawal_cannot_exceed_balance():
    account = BankAccount("Toussaint", 100)

    with pytest.raises(ValueError):
        account.withdraw(200)
```

A useful testing mindset:

- Test the **public API**: methods and public properties.
- Test invalid inputs and boundary cases.
- Avoid depending heavily on `_internal_attributes` in tests.
- If tests rely on private details, refactoring becomes difficult.

# 24. Encapsulation checklist

Before finalizing a Python class, ask:

- What should users of this class be allowed to do?
- What data should be readable?
- What data should not be changed directly?
- Which values have rules or valid ranges?
- Which operations should be methods rather than direct assignment?
- Am I exposing mutable lists or dictionaries?
- Do I need a read-only property?
- Could internal storage change later?
- Is `_name` enough, or is `__name` genuinely needed for inheritance collision avoidance?
- Does a property hide expensive or surprising work?
- Are secrets and credentials kept outside code and public interfaces?

# 25. Final example: well-encapsulated class

Here is a complete example that combines the main lessons.

```
class ProjectBudget:
    def __init__(self, project_name, total_budget):
        self.project_name = project_name
        self.total_budget = total_budget
        self._spent = 0
        self._expenses = []

    @property
    def total_budget(self):
        return self._total_budget

    @total_budget.setter
    def total_budget(self, value):
        if not isinstance(value, (int, float)):
            raise TypeError("Budget must be a number.")

        if value <= 0:
            raise ValueError("Budget must be greater than zero.")

        self._total_budget = value

    @property
    def spent(self):
        return self._spent

    @property
    def remaining_budget(self):
        return self._total_budget - self._spent

    @property
    def expenses(self):
        return tuple(self._expenses)

    def add_expense(self, description, amount):
        if not isinstance(description, str) or not description.strip():
            raise ValueError("Expense description cannot be empty.")

        if not isinstance(amount, (int, float)):
            raise TypeError("Expense amount must be a number.")

        if amount <= 0:
            raise ValueError("Expense amount must be greater than zero.")

        if amount > self.remaining_budget:
            raise ValueError(
                "Expense exceeds the remaining project budget."
            )

        self._spent += amount

        self._expenses.append({
            "description": description.strip(),
            "amount": amount,
        })
```

Usage:

```
budget = ProjectBudget(
    project_name="TrustDesk MVP",
    total_budget=5_000
)

budget.add_expense("Cloud hosting", 120)
budget.add_expense("Domain registration", 20)

print(budget.spent)
print(budget.remaining_budget)
print(budget.expenses)
```

Expected output:

```
140
4860
(
    {'description': 'Cloud hosting', 'amount': 120},
    {'description': 'Domain registration', 'amount': 20}
)
```

The design is strong because:

- `total_budget` is validated.
- `spent` is read-only from outside.
- `remaining_budget` is computed automatically.
- Expenses cannot exceed available budget.
- The external user cannot directly modify the original expense list.
- The class exposes a domain action: `add_expense()`.

# 26. The key takeaway

In Python, encapsulation is not about creating an impenetrable wall around variables. It is about designing a clean, reliable contract for your objects.

Use this practical hierarchy:

```
# Public: safe for normal users
self.name

# Internal: do not use outside the class unless necessary
self._balance

# Name-mangled: avoid accidental collision in inheritance
self.__internal_state
```

And use these tools:

```
@property                 # Controlled reading
@attribute.setter     # Controlled writing and validation
@attribute.deleter    # Controlled deletion
methods                # Meaningful actions that preserve rules
tuple/copy/deepcopy    # Protect internal mutable data
descriptors            # Reusable advanced validation logic
__slots__              # Restricted instance shape and possible memory savings
```

The most Pythonic approach is usually:

```
class Example:
    def __init__(self, value):
        self.value = value

    @property
    def value(self):
        return self._value

    @value.setter
    def value(self, new_value):
        if new_value < 0:
            raise ValueError("Value cannot be negative.")

        self._value = new_value
```

This gives you a clean public attribute:

```
example.value
```

while retaining full control over how that value is stored and validated.
