`@classmethod`, `@staticmethod`, and decorators are closely connected: `@classmethod` and `@staticmethod` are themselves built-in decorators that change how a function behaves inside a class. The most important question is: **does the function need an object (`self`), the class (`cls`), or neither?**[[docs.python](https://docs.python.org/3/library/functions.html)][[peps.python](https://peps.python.org/pep-0318/)]

# 1. Foundation: functions and methods

Before decorators, understand the three kinds of functions you may put inside a class.

```
class Example:
    def instance_method(self):
        return "I work with one specific object."
```

Create an object:

```
obj = Example()

print(obj.instance_method())
```

Output:

```
I work with one specific object.
```

The first parameter:

```
self
```

refers to the specific object calling the method.

For example:

```
class Student:
    def __init__(self, name):
        self.name = name

    def introduce(self):
        return f"My name is {self.name}."
```

```
student_a = Student("Toussaint")
student_b = Student("Aline")

print(student_a.introduce())
print(student_b.introduce())
```

Output:

```
My name is Toussaint.
My name is Aline.
```

Each object has its own value of `self.name`.

## Three method types

|Method type|First parameter|Can access instance data?|Can access class data?|Typical use|
|---|---|---|---|---|
|Instance method|`self`|Yes|Yes|Normal object behavior|
|Class method|`cls`|Not directly|Yes|Alternative constructors, class-wide configuration|
|Static method|None automatically|No|No|Related helper/utility logic|

The built-in documentation states that a class method receives the class as its implicit first argument, while a static method receives no implicit first argument. Both can be called through either the class or an instance.[[docs.python](https://docs.python.org/3/library/functions.html)]

# 2. What is a decorator?

A **decorator** is a callable that takes a function or class, transforms or wraps it, and returns a replacement.

The `@decorator_name` syntax is convenient shorthand.

```
@decorator
def greet():
    return "Hello"
```

means:

```
def greet():
    return "Hello"

greet = decorator(greet)
```

With multiple decorators:

```
@dec2
@dec1
def greet():
    return "Hello"
```

Python evaluates it from the inside out:

```
greet = dec2(dec1(greet))
```

This exact equivalence is specified in PEP 318, which introduced decorator syntax for functions and methods.[[peps.python](https://peps.python.org/pep-0318/)]

## Mental model

Think of a function as a gift:

```
original function = gift
decorator = wrapping paper that adds behavior
decorated function = gift with added behavior
```

A decorator can add:

- Logging
- Authentication and authorization
- Timing
- Input validation
- Caching
- Retry logic
- Rate limiting
- Error handling
- Metrics and observability
- Access control
- Function registration
- API routing

For an AI service, a decorator could measure LLM latency, verify authentication, enforce rate limits, retry transient requests, or log model usage.

# 3. First decorator from scratch

Here is a simple function:

```
def greet():
    return "Hello, Toussaint!"
```

Now create a decorator:

```
def make_louder(function):
    def wrapper():
        message = function()
        return message.upper()

    return wrapper
```

Apply it:

```
@make_louder
def greet():
    return "Hello, Toussaint!"
```

Use it:

```
print(greet())
```

Output:

```
HELLO, TOUSSAINT!
```

## What happened?

Python effectively ran this:

```
def greet():
    return "Hello, Toussaint!"

greet = make_louder(greet)
```

The name `greet` now refers to `wrapper`.

The sequence is:

1. Python creates the original `greet` function.
2. Python passes `greet` into `make_louder`.
3. `make_louder` creates `wrapper`.
4. `make_louder` returns `wrapper`.
5. Python replaces `greet` with `wrapper`.
6. Calling `greet()` actually calls `wrapper()`.
7. `wrapper()` calls the original function.

# 4. Decorators with arguments

The first decorator works only for functions with zero parameters.

```
@make_louder
def greet(name):
    return f"Hello, {name}!"
```

This causes an error because `wrapper()` accepts no argument.

Use `*args` and `**kwargs`.

```
def make_louder(function):
    def wrapper(*args, **kwargs):
        message = function(*args, **kwargs)
        return message.upper()

    return wrapper
```

Now it works:

```
@make_louder
def greet(name):
    return f"Hello, {name}!"
```

```
print(greet("Toussaint"))
```

Output:

```
HELLO, TOUSSAINT!
```

## Meaning of `*args` and `**kwargs`

```
def wrapper(*args, **kwargs):
    ...
```

- `*args` collects positional arguments into a tuple.
- `**kwargs` collects keyword arguments into a dictionary.

Example:

```
def demo(*args, **kwargs):
    print(args)
    print(kwargs)
```

```
demo(10, 20, name="Toussaint", topic="Python")
```

Output:

```
(10, 20)
{'name': 'Toussaint', 'topic': 'Python'}
```

The robust decorator pattern is:

```
def decorator(function):
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs)

    return wrapper
```

# 5. Decorators that add behavior before and after

Decorators often run code before and after the original function.

```
def log_call(function):
    def wrapper(*args, **kwargs):
        print(f"Calling: {function.__name__}")

        result = function(*args, **kwargs)

        print(f"Finished: {function.__name__}")

        return result

    return wrapper
```

```
@log_call
def calculate_total(price, quantity):
    return price * quantity
```

```
total = calculate_total(50, 3)

print(total)
```

Output:

```
Calling: calculate_total
Finished: calculate_total
150
```

The original result is preserved because the wrapper returns it:

```
return result
```

A common bug is forgetting that return statement:

```
def broken_log_call(function):
    def wrapper(*args, **kwargs):
        function(*args, **kwargs)
        # Missing: return function result

    return wrapper
```

Then the decorated function returns `None`.

# 6. `functools.wraps`: essential best practice

Consider this decorator:

```
def log_call(function):
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs)

    return wrapper
```

Now inspect a decorated function:

```
@log_call
def create_ticket(title):
    """Create a customer-support ticket."""
    return {"title": title}
```

```
print(create_ticket.__name__)
print(create_ticket.__doc__)
```

Without help, Python sees the function as:

```
wrapper
None
```

That is bad for:

- Debugging
- Documentation generation
- Error messages
- Frameworks such as FastAPI
- Testing
- Introspection
- Logging
- Tool registration systems
- AI-agent tool metadata

Use `functools.wraps`.

```
from functools import wraps
```

```
def log_call(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        print(f"Calling {function.__name__}")
        return function(*args, **kwargs)

    return wrapper
```

Now:

```
@log_call
def create_ticket(title):
    """Create a customer-support ticket."""
    return {"title": title}
```

```
print(create_ticket.__name__)
print(create_ticket.__doc__)
```

Output:

```
create_ticket
Create a customer-support ticket.
```

Always use `@wraps(function)` inside function wrappers unless you have a deliberate reason not to. Decorators, including `classmethod` and `staticmethod`, are built on Python’s descriptor machinery, which controls behavior during attribute lookup.[[docs.python](https://docs.python.org/3/howto/descriptor.html)]

# 7. Decorator flow, visually

Take this code:

```
@log_call
def train_model(dataset_name):
    return f"Training on {dataset_name}"
```

Think of it as:

```
def train_model(dataset_name):
    return f"Training on {dataset_name}"

train_model = log_call(train_model)
```

When you run:

```
train_model("support_tickets")
```

the flow is:

```
train_model("support_tickets")
        ↓
wrapper("support_tickets")
        ↓
print log message
        ↓
original train_model("support_tickets")
        ↓
return original result
```

That is the core mechanism behind all decorators.

# 8. `@staticmethod`

A static method belongs inside a class namespace, but does not automatically receive:

```
self
```

or:

```
cls
```

The official Python documentation defines a static method as a transformed method that receives no implicit first argument. It can be called through the class or through an instance.[[docs.python](https://docs.python.org/3/library/functions.html)]

## Basic example

```
class TextUtils:

    @staticmethod
    def normalize(text):
        return text.strip().lower()
```

Call it from the class:

```
print(TextUtils.normalize("  HELLO TRUSTDESK  "))
```

Output:

```
hello trustdesk
```

You can also call it from an object:

```
utils = TextUtils()

print(utils.normalize("  PYTHON  "))
```

Output:

```
python
```

But class-level calling is clearer:

```
TextUtils.normalize("  PYTHON  ")
```

## Equivalent old-style form

This:

```
class TextUtils:

    @staticmethod
    def normalize(text):
        return text.strip().lower()
```

is conceptually similar to:

```
class TextUtils:

    def normalize(text):
        return text.strip().lower()

    normalize = staticmethod(normalize)
```

The decorator syntax puts the transformation next to the function definition, which was a key goal of the decorator proposal.[[peps.python](https://peps.python.org/pep-0318/)]

---

# 9. When to use `@staticmethod`

Use a static method when all of these are true:

- The logic is strongly related to the class.
- The method does not need instance data.
- The method does not need class data.
- Keeping it in the class improves organization and discoverability.

Example:

```
class PasswordValidator:

    @staticmethod
    def is_strong(password):
        has_minimum_length = len(password) >= 12
        has_digit = any(char.isdigit() for char in password)
        has_uppercase = any(char.isupper() for char in password)

        return (
            has_minimum_length
            and has_digit
            and has_uppercase
        )
```

Usage:

```
password = "TrustDesk2026"

print(PasswordValidator.is_strong(password))
```

Output:

```
True
```

No object needs to be created:

```
# Not necessary
validator = PasswordValidator()
```

## Static method versus normal function

Sometimes this is better:

```
def normalize_text(text):
    return text.strip().lower()
```

A module-level function is usually preferable if the behavior is not specifically tied to the class.

Use:

```
TextUtils.normalize(text)
```

when the class gives useful conceptual grouping.

Use:

```
normalize_text(text)
```

when it is general-purpose functionality.

Do not put every helper into a class merely because other languages often do that.

# 10. `@classmethod`

A class method receives the class itself as its first automatic argument.

```
class Example:

    @classmethod
    def describe_class(cls):
        return f"This class is {cls.__name__}."
```

Call it:

```
print(Example.describe_class())
```

Output:

```
This class is Example.
```

Here:

```
cls
```

refers to:

```
Example
```

Compare:

```
self  # a specific object
cls   # the class object
```

## Instance method versus class method

```
class Student:
    school_name = "Gitega Tech Academy"

    def __init__(self, name):
        self.name = name

    def introduce(self):
        return f"My name is {self.name}."

    @classmethod
    def school(cls):
        return cls.school_name
```

Usage:

```
student = Student("Toussaint")

print(student.introduce())
print(Student.school())
print(student.school())
```

Output:

```
My name is Toussaint.
Gitega Tech Academy
Gitega Tech Academy
```

Both calls are valid:

```
Student.school()
student.school()
```

But the class-oriented form is usually clearer:

```
Student.school()
```

A class method invoked on a derived class receives that derived class as `cls`, rather than always receiving the parent class.[[docs.python](https://docs.python.org/3/library/functions.html)]

# 11. Class attributes and class methods

A class attribute is shared by all instances unless an instance overrides it.

```
class User:
    platform_name = "TrustDesk"

    def __init__(self, username):
        self.username = username
```

```
user_a = User("toussaint")
user_b = User("aline")

print(user_a.platform_name)
print(user_b.platform_name)
print(User.platform_name)
```

Output:

```
TrustDesk
TrustDesk
TrustDesk
```

Use a class method to safely modify class-wide state.

```
class User:
    platform_name = "TrustDesk"

    @classmethod
    def set_platform_name(cls, new_name):
        if not isinstance(new_name, str):
            raise TypeError("Platform name must be a string.")

        new_name = new_name.strip()

        if not new_name:
            raise ValueError("Platform name cannot be empty.")

        cls.platform_name = new_name
```

```
User.set_platform_name("TrustDesk AI")

print(User.platform_name)
```

Output:

```
TrustDesk AI
```

## Important distinction

```
self.attribute
```

usually refers to instance-specific data.

```
cls.attribute
```

refers to class-level shared data.

# 12. Best use case: alternative constructors

The most important practical use of `@classmethod` is an **alternative constructor**.

The normal constructor is:

```
__init__
```

For example:

```
class User:
    def __init__(self, username, email):
        self.username = username
        self.email = email
```

Normally:

```
user = User("toussaint", "toussaint@example.com")
```

But perhaps an API returns a dictionary:

```
api_data = {
    "username": "toussaint",
    "email": "toussaint@example.com",
}
```

Create an alternative constructor:

```
class User:
    def __init__(self, username, email):
        self.username = username
        self.email = email

    @classmethod
    def from_dict(cls, data):
        return cls(
            username=data["username"],
            email=data["email"],
        )
```

Usage:

```
api_data = {
    "username": "toussaint",
    "email": "toussaint@example.com",
}

user = User.from_dict(api_data)

print(user.username)
print(user.email)
```

Output:

```
toussaint
toussaint@example.com
```

The important line is:

```
return cls(...)
```

not:

```
return User(...)
```

Why? Because `cls(...)` supports inheritance correctly.

# 13. Why `cls(...)` is better than class name

Consider this parent class.

```
class User:
    def __init__(self, username):
        self.username = username

    @classmethod
    def from_dict(cls, data):
        return cls(data["username"])
```

Now create a child class:

```
class Admin(User):
    pass
```

Call:

```
admin = Admin.from_dict({"username": "toussaint_admin"})

print(type(admin))
print(admin.username)
```

Output:

```
<class '__main__.Admin'>
toussaint_admin
```

Because the method was called on `Admin`:

```
cls
```

became:

```
Admin
```

Therefore:

```
return cls(...)
```

created an `Admin` object.

If you wrote:

```
return User(...)
```

then this would always create a `User`, even when called through `Admin`.

That would weaken polymorphism and inheritance.

# 14. Alternative constructors in real work

## Create an object from JSON-like API data

```
class SupportTicket:
    def __init__(self, ticket_id, title, priority):
        self.ticket_id = ticket_id
        self.title = title
        self.priority = priority

    @classmethod
    def from_api_response(cls, data):
        return cls(
            ticket_id=data["id"],
            title=data["subject"],
            priority=data.get("priority", "normal"),
        )
```

```
response = {
    "id": "T-1024",
    "subject": "Unable to reset password",
    "priority": "high",
}

ticket = SupportTicket.from_api_response(response)

print(ticket.ticket_id)
print(ticket.title)
print(ticket.priority)
```

Output:

```
T-1024
Unable to reset password
high
```

## Create an object from CSV data

```
class Product:
    def __init__(self, name, price):
        self.name = name
        self.price = price

    @classmethod
    def from_csv_row(cls, row):
        name, price = row.split(",")

        return cls(
            name=name.strip(),
            price=float(price.strip()),
        )
```

```
product = Product.from_csv_row("AI Agent Subscription, 29.99")

print(product.name)
print(product.price)
```

Output:

```
AI Agent Subscription
29.99
```

## Create an object from an ISO date string

```
from datetime import datetime
```

```
class Event:
    def __init__(self, name, start_time):
        self.name = name
        self.start_time = start_time

    @classmethod
    def from_iso_string(cls, name, iso_time):
        parsed_time = datetime.fromisoformat(iso_time)

        return cls(name, parsed_time)
```

```
event = Event.from_iso_string(
    "Python class",
    "2026-09-02T20:00:00"
)

print(event.name)
print(event.start_time)
```

# 15. Class methods as factory methods

A **factory method** is a method that creates and returns an object.

A class method is often used as a factory because it can choose which object to create.

```
class Notification:
    def __init__(self, channel, recipient, message):
        self.channel = channel
        self.recipient = recipient
        self.message = message

    @classmethod
    def email(cls, recipient, message):
        return cls(
            channel="email",
            recipient=recipient,
            message=message,
        )

    @classmethod
    def sms(cls, recipient, message):
        return cls(
            channel="sms",
            recipient=recipient,
            message=message,
        )
```

Usage:

```
email_notification = Notification.email(
    recipient="user@example.com",
    message="Your support ticket was updated."
)

sms_notification = Notification.sms(
    recipient="+25700000000",
    message="Your verification code is 123456."
)

print(email_notification.channel)
print(sms_notification.channel)
```

Output:

```
email
sms
```

This can make object creation more expressive than long constructor calls.

```
Notification(
    "email",
    "user@example.com",
    "Your support ticket was updated."
)
```

versus:

```
Notification.email(
    "user@example.com",
    "Your support ticket was updated."
)
```

# 16. Class methods for shared counters

Class methods can manage information shared by every object.

```
class User:
    total_users = 0

    def __init__(self, username):
        self.username = username
        type(self).total_users += 1

    @classmethod
    def count(cls):
        return cls.total_users
```

```
User("toussaint")
User("aline")
User("kevin")

print(User.count())
```

Output:

```
3
```

## Why `type(self)`?

Inside `__init__`, this:

```
type(self).total_users += 1
```

can be more inheritance-friendly than:

```
User.total_users += 1
```

It updates the count associated with the actual object’s class.

However, counter design in inheritance can become subtle. For beginner and many normal cases, this is enough:

```
class User:
    total_users = 0

    def __init__(self, username):
        self.username = username
        User.total_users += 1
```

Use the simplest version that matches your intended class hierarchy.

# 17. `@staticmethod` versus `@classmethod`

Here is the difference in one example.

```
class Temperature:
    unit = "Celsius"

    def __init__(self, value):
        self.value = value

    @classmethod
    def from_fahrenheit(cls, fahrenheit):
        celsius = (fahrenheit - 32) * 5 / 9

        return cls(celsius)

    @staticmethod
    def is_valid_celsius(value):
        return value >= -273.15
```

Usage:

```
temperature = Temperature.from_fahrenheit(68)

print(temperature.value)
print(Temperature.is_valid_celsius(-300))
```

Output:

```
20.0
False
```

Why use each one?

```
@classmethod
def from_fahrenheit(cls, fahrenheit):
```

The method must create and return an instance:

```
return cls(celsius)
```

So it needs access to the class.

```
@staticmethod
def is_valid_celsius(value):
```

This is only a calculation based on its argument. It needs neither instance state nor class state.

## Decision rule

```
Need self?       → instance method
Need cls?        → class method
Need neither?    → static method or module-level function
```

# 18. `self`, `cls`, and no automatic parameter

```
class MethodTypes:
    class_name = "MethodTypes"

    def instance_method(self):
        return f"Instance method: {self}"

    @classmethod
    def class_method(cls):
        return f"Class method: {cls.__name__}"

    @staticmethod
    def static_method(value):
        return f"Static method received: {value}"
```

Usage:

```
obj = MethodTypes()

print(obj.instance_method())
print(MethodTypes.class_method())
print(MethodTypes.static_method("Hello"))
```

Possible output:

```
Instance method: <__main__.MethodTypes object at 0x...>
Class method: MethodTypes
Static method received: Hello
```

|Definition|Python automatically gives you|You can access naturally|
|---|---|---|
|`def method(self):`|Current object|Object state and class state|
|`def method(cls):` with `@classmethod`|Current class|Class state and constructors|
|`def method(...):` with `@staticmethod`|Nothing|Only passed arguments and global/module names|

# 19. Under the hood: functions become bound methods

This is an advanced but important concept.

```
class Greeter:
    def greet(self, name):
        return f"Hello, {name}!"
```

When you access a method through an instance:

```
greeter = Greeter()

greeter.greet("Toussaint")
```

Python effectively binds the object to the function.

Conceptually:

```
Greeter.greet(greeter, "Toussaint")
```

So:

```
self
```

is not magic. Python automatically supplies it when you access a normal function through an instance.

## Accessing from the class

```
Greeter.greet(greeter, "Toussaint")
```

also works, but you must provide the instance yourself.

This automatic binding behavior is implemented through Python’s **descriptor protocol**. Functions stored in a class are descriptors; accessing them from an instance produces a bound method.[[docs.python](https://docs.python.org/3/howto/descriptor.html)]

# 20. Under the hood: class methods

```
class Greeter:
    @classmethod
    def describe(cls):
        return cls.__name__
```

When you call:

```
Greeter.describe()
```

Python conceptually supplies the class:

```
Greeter.describe(Greeter)
```

If you subclass:

```
class FriendlyGreeter(Greeter):
    pass
```

then:

```
FriendlyGreeter.describe()
```

receives:

```
FriendlyGreeter
```

as `cls`.

That inheritance-aware binding is why class methods are ideal for alternative constructors and class-aware factory methods.[[docs.python](https://docs.python.org/3/library/functions.html)]

# 21. Under the hood: static methods

```
class Greeter:
    @staticmethod
    def format_name(name):
        return name.strip().title()
```

When you call:

```
Greeter.format_name("  toussaint jacobs ")
```

Python does not add:


or:


Conceptually, it behaves like:


but remains stored under the `Greeter` class namespace.

Python documents that static methods can be called from the class or an instance and receive no implicit first argument.[[docs.python](https://docs.python.org/3/library/functions.html)]

# 22. Decorators with parameters

Sometimes you want to configure a decorator.

For example, define how many times a function should run.

```
from functools import wraps
```

```
def repeat(times):
    def decorator(function):
        @wraps(function)
        def wrapper(*args, **kwargs):
            result = None

            for _ in range(times):
                result = function(*args, **kwargs)

            return result

        return wrapper

    return decorator
```

Use it:

```
@repeat(3)
def greet(name):
    print(f"Hello, {name}!")
```

```
greet("Toussaint")
```

Output:

```
Hello, Toussaint!
Hello, Toussaint!
Hello, Toussaint!
```

## What is happening?

This:

```
@repeat(3)
def greet(name):
    ...
```

means:

```
greet = repeat(3)(greet)
```

Break it down:

1. `repeat(3)` runs first.
2. It returns `decorator`.
3. Python passes `greet` into `decorator`.
4. `decorator(greet)` returns `wrapper`.
5. Python replaces `greet` with `wrapper`.

The structure is always:

```
def decorator_factory(configuration):
    def actual_decorator(function):
        def wrapper(*args, **kwargs):
```

# 26. Retry decorator

External APIs, databases, and LLM providers may occasionally fail temporarily.

```
from functools import wraps
from time import sleep
```

```
def retry(max_attempts, delay_seconds=1):
    def decorator(function):
        @wraps(function)
        def wrapper(*args, **kwargs):
            last_error = None

            for attempt in range(1, max_attempts + 1):
                try:
                    return function(*args, **kwargs)

                except ConnectionError as error:
                    last_error = error

                    print(
                        f"Attempt {attempt}/{max_attempts} failed: "
                        f"{error}"
                    )

                    if attempt < max_attempts:
                        sleep(delay_seconds)

            raise last_error

        return wrapper

    return decorator
```

```
@retry(max_attempts=3, delay_seconds=1)
def call_model_api():
    raise ConnectionError("Temporary provider outage.")
```

This retries the operation up to three times before raising the final `ConnectionError`.

## Production improvements

For production API calls, consider:

- Exponential backoff instead of a fixed delay.
- Random jitter to avoid synchronized retry spikes.
- Retry only transient errors.
- Timeouts.
- Maximum total retry time.
- Idempotency keys for write operations.
- Structured logs and observability.
- Circuit breakers for persistent outages.

# 27. Caching decorator

Caching stores a previous result so repeated calls can return faster.

Python provides `functools.cache` and `functools.lru_cache` for common in-memory caching cases.

```
from functools import lru_cache
```

```
@lru_cache(maxsize=128)
def expensive_embedding_lookup(text):
    print(f"Computing result for: {text}")

    return {
        "text": text,
        "embedding_id": hash(text),
    }
```

```
print(expensive_embedding_lookup("What is encapsulation?"))
print(expensive_embedding_lookup("What is encapsulation?"))
```

The “Computing result” message appears only on the first call for the same input.

## Important cache rule

Arguments must be hashable.

This works:

```
expensive_embedding_lookup("hello")
```

This does not work directly:

```
# A list is mutable and unhashable
expensive_embedding_lookup(["hello", "world"])
```

For AI and web systems, in-memory caching is only one small layer. Distributed applications often need Redis or another shared cache, plus careful cache expiration, user isolation, invalidation strategy, and privacy protection.

# 28. Decorator order

When you stack decorators, order matters.

```
@decorator_a
@decorator_b
def function():
    ...
```

means:

```
function = decorator_a(decorator_b(function))
```

The decorator nearest to the function runs first during decoration.

Example:

```
from functools import wraps
```

```
def add_stars(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        return f"*** {function(*args, **kwargs)} ***"

    return wrapper
```

```
def make_uppercase(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs).upper()

    return wrapper
```

```
@add_stars
@make_uppercase
def message():
    return "Hello"
```

This means:

```
message = add_stars(make_uppercase(message))
```

Call:

```
print(message())
```

Output:

```
*** HELLO ***
```

Try the reverse order:

```
@make_uppercase
@add_stars
def message():
    return "Hello"
```

It produces:

```
*** HELLO ***
```

This particular example looks similar, but decorators can differ significantly when they validate, log, cache, retry, authenticate, transform arguments, or handle errors.

## Example where order changes behavior

```
def require_login(function):
    @wraps(function)
    def wrapper(user, *args, **kwargs):
        if not user["logged_in"]:
            raise PermissionError("Log in first.")

        return function(user, *args, **kwargs)

    return wrapper
```

```
def log_access(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        print("Access attempt recorded.")
        return function(*args, **kwargs)

    return wrapper
```

```
@log_access
@require_login
def view_dashboard(user):
    return "Dashboard data"
```

Here, logging happens even when login fails.

If you reverse them:

```
@require_login
@log_access
def view_dashboard(user):
    return "Dashboard data"
```

authentication runs first, so unauthorized access attempts are not logged by `log_access`.

In real systems, choose order intentionally.

# 30. Decorators with `@classmethod`

A class method can have another decorator, but order matters.

A clear pattern is:

```
class Example:

    @classmethod
    @some_decorator
    def method(cls):
        ...
```

Why?

Decorators apply bottom-up:

```
method = classmethod(some_decorator(method))
```

So `some_decorator` receives a normal function, then `classmethod` turns the result into a class method.

Example:

```
from functools import wraps
```

```
def log_call(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        print(f"Calling {function.__name__}")
        return function(*args, **kwargs)

    return wrapper
```

```
class User:

    @classmethod
    @log_call
    def from_username(cls, username):
        return cls(username)

    def __init__(self, username):
        self.username = username
```

```
user = User.from_username("toussaint")

print(user.username)
```

Output:

```
Calling from_username
toussaint
```

## Avoid reversing the order casually

This can be confusing:

```
class User:

    @log_call
    @classmethod
    def from_username(cls, username):
        return cls(username)
```

Now `log_call` receives a `classmethod` object rather than a plain function. Some decorators may work accidentally; many wrappers and inspection tools will not behave as expected.

Use:

```
@classmethod
@your_decorator
def method(cls):
    ...
```

unless you understand exactly why a different order is needed.

# 32. `@property` is also a decorator

You learned `@property` in encapsulation. It is another important built-in decorator.

```
class Product:
    def __init__(self, price):
        self._price = price

    @property
    def price(self):
        return self._price
```

Usage:

```
product = Product(100)

print(product.price)
```

You write:

```
product.price
```

but Python runs a method.

Add a setter:

```
class Product:
    def __init__(self, price):
        self.price = price

    @property
    def price(self):
        return self._price

    @price.setter
    def price(self, value):
        if value < 0:
            raise ValueError("Price cannot be negative.")

        self._price = value
```

This works because decorators transform the original function into a `property` object that controls attribute access. Python’s descriptor system is the mechanism behind properties, normal methods, static methods, and class methods.[[docs.python](https://docs.python.org/3/howto/descriptor.html)]

# 35. Decorators as classes

A decorator does not have to be a function. It can be a callable object.

```
from functools import wraps
```

```
class CountCalls:
    def __init__(self, function):
        wraps(function)(self)

        self.function = function
        self.calls = 0

    def __call__(self, *args, **kwargs):
        self.calls += 1

        return self.function(*args, **kwargs)
```

Use it:

```
@CountCalls
def classify_message(text):
    return f"Classified: {text}"
```

```
print(classify_message("Cannot log in"))
print(classify_message("Payment failed"))

print(classify_message.calls)
```

Output:

```
Classified: Cannot log in
Classified: Payment failed
2
```

This is useful when a decorator needs to store state:

- Number of calls
- Rate-limit counters
- Cached values
- Configuration
- Metrics
- Per-function monitoring settings

However, function-based decorators are often simpler. Prefer them unless you truly need object state.

# 36. Decorators and closures

A decorator works because Python functions are first-class objects and because Python supports **closures**.

A closure is an inner function that remembers values from its enclosing function even after the outer function has finished.

```
def make_multiplier(multiplier):
    def multiply(number):
        return number * multiplier

    return multiply
```

```
double = make_multiplier(2)
triple = make_multiplier(3)

print(double(10))
print(triple(10))
```

Output:

```
20
30
```

Even after `make_multiplier()` returns, the returned `multiply()` function remembers its own `multiplier`.

Decorators use the same principle:

```
def decorator(function):
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs)

    return wrapper
```

The inner `wrapper()` remembers `function`.

That remembered outer value is a closure.

# 37. Decorators and object-oriented design

Use decorators for **cross-cutting concerns**: behavior that applies across many unrelated functions or methods.

Good decorator responsibilities:

- Logging
- Timing
- Validation
- Authentication
- Authorization
- Caching
- Retry handling
- Tracing
- Rate limiting
- Auditing
- Transaction boundaries

Poor decorator responsibilities:

- Large core business workflows
- Complicated application logic
- Hidden database writes
- Secretly changing return types
- Heavy network activity that callers cannot see
- Complex state changes that would be clearer in a normal method

A decorator should usually make behavior more reusable and less repetitive—not hide essential application logic.

# 38. Real AI-service example

Here is a small, structured example for an AI-ticket classifier.

```
from functools import wraps
from time import perf_counter
```

```
def measure_time(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        start = perf_counter()

        result = function(*args, **kwargs)

        elapsed = perf_counter() - start

        print(
            f"[METRIC] {function.__name__} "
            f"took {elapsed:.6f} seconds"
        )

        return result

    return wrapper
```

```
def validate_non_empty_prompt(function):
    @wraps(function)
    def wrapper(self, prompt, *args, **kwargs):
        if not isinstance(prompt, str):
            raise TypeError("Prompt must be a string.")

        prompt = prompt.strip()

        if not prompt:
            raise ValueError("Prompt cannot be empty.")

        return function(self, prompt, *args, **kwargs)

    return wrapper
```

```
class TicketClassifier:
    supported_categories = {
        "account_access",
        "billing",
        "technical_issue",
    }

    def __init__(self, model_name):
        self.model_name = model_name

    @classmethod
    def default(cls):
        return cls(model_name="trustdesk-ticket-classifier-v1")

    @staticmethod
    def normalize_text(text):
        return text.strip().lower()

    @measure_time
    @validate_non_empty_prompt
    def classify(self, prompt):
        normalized = self.normalize_text(prompt)

        if "password" in normalized or "login" in normalized:
            return "account_access"

        if "payment" in normalized or "invoice" in normalized:
            return "billing"

        return "technical_issue"
```

Usage:

```
classifier = TicketClassifier.default()

category = classifier.classify(
    " I cannot reset my password. "
)

print(category)
```

Possible output:

```
[METRIC] classify took 0.000010 seconds
account_access
```

## What each tool does

|Code|Role|
|---|---|
|`default()`|`@classmethod` alternative constructor that creates a standard configured object|
|`normalize_text()`|`@staticmethod` because it needs neither `self` nor `cls`|
|`classify()`|Instance method because it logically belongs to a particular classifier object and may later use `self.model_name` or `self.model`|
|`@validate_non_empty_prompt`|Ensures valid input before classification|
|`@measure_time`|Measures the duration of classification|
|`@wraps`|Preserves method metadata through wrappers|

## Decorator order in this example

```
@measure_time
@validate_non_empty_prompt
def classify(...):
```

means:

```
classify = measure_time(
    validate_non_empty_prompt(classify)
)
```

Execution order:

```
measure_time wrapper starts timer
        ↓
validate_non_empty_prompt validates input
        ↓
original classify method runs
        ↓
measure_time prints duration
```

# 39. Common mistakes

## Forgetting `self`

Incorrect:

```
class User:
    def introduce():
        return "Hello"
```

```
user = User()
user.introduce()
```

Error:

```
TypeError: introduce() takes 0 positional arguments but 1 was given
```

Correct:

```
class User:
    def introduce(self):
        return "Hello"
```

Python passes the object automatically.

---

## Forgetting `cls`

Incorrect:

```
class User:
    @classmethod
    def create():
        return User()
```

This might work in a simple class, but it is not inheritance-friendly.

Better:

```
class User:
    @classmethod
    def create(cls):
        return cls()
```

---

## Using `self` in a static method

Incorrect:

```
class Example:

    @staticmethod
    def show_name():
        return self.name
```

There is no `self`.

Use an instance method:

```
class Example:
    def show_name(self):
        return self.name
```

Or pass the value explicitly:

```
class Example:

    @staticmethod
    def format_name(name):
        return name.strip().title()
```

---

## Using `cls` in a static method

Incorrect:

```
class Example:

    @staticmethod
    def create():
        return cls()
```

There is no `cls`.

Use:

```
@classmethod
def create(cls):
    return cls()
```

---

## Using `@staticmethod` where a module function is clearer

This is not always wrong:

```
class AppUtils:

    @staticmethod
    def convert_to_json(data):
        ...
```

But this may be clearer:

```
def convert_to_json(data):
    ...
```

A static method should have a meaningful conceptual relationship with the class.

---

## Losing metadata without `@wraps`

Avoid:

```
def decorator(function):
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs)

    return wrapper
```

Prefer:

```
from functools import wraps
```

```
def decorator(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs)

    return wrapper
```

---

## Catching every error in a decorator

Avoid:

```
def bad_error_handler(function):
    def wrapper(*args, **kwargs):
        try:
            return function(*args, **kwargs)
        except Exception:
            return None

    return wrapper
```

This hides bugs and makes debugging much harder.

Better:

```
def handle_connection_error(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        try:
            return function(*args, **kwargs)
        except ConnectionError as error:
            raise RuntimeError(
                "The external service could not be reached."
            ) from error

    return wrapper
```

Catch only errors you genuinely expect and can handle correctly.

```
from functools import wraps
```

```
def retry(times):
    def decorator(function):
        @wraps(function)
        def wrapper(*args, **kwargs):
            last_error = None

            for _ in range(times):
                try:
                    return function(*args, **kwargs)
                except ValueError as error:
                    last_error = error

            raise last_error

        return wrapper

    return decorator
```

```
@retry(times=3)
def unstable_function():
    global attempts

    attempts += 1

    if attempts < 3:
        raise ValueError("Temporary problem.")

    return "Success!"
```

```
from functools import wraps
```

```
def add_prefix(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        return "Result: " + function(*args, **kwargs)

    return wrapper
```

```
def make_uppercase(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs).upper()

    return wrapper
```

First order:

```
@add_prefix
@make_uppercase
def message_one():
    return "python decorators"
```

```
print(message_one())
```

Output:

```
Result: PYTHON DECORATORS
```

Reverse order:

```
@make_uppercase
@add_prefix
def message_two():
    return "python decorators"
```

```
print(message_two())
```

Output:

```
RESULT: PYTHON DECORATORS
```

Why?

First version:

```
message_one = add_prefix(make_uppercase(message_one))
```

The text becomes uppercase first, then `"Result: "` is added.

Second version:

```
message_two = make_uppercase(add_prefix(message_two))
```

The prefix is added first, then the whole result is uppercased.

# 42. Final cheat sheet

```
class Example:
    shared_value = "I belong to the class"

    def instance_method(self):
        # Use self when behavior needs one object.
        return self.shared_value

    @classmethod
    def class_method(cls):
        # Use cls when behavior needs the class itself.
        return cls.shared_value

    @staticmethod
    def static_method(value):
        # Use when behavior needs neither self nor cls.
        return value.strip().lower()
```

```
Need data from one particular object?     Use an instance method: self
Need class-wide state or create objects?  Use a class method: cls
Need neither self nor cls?                Use a static method—or a module function
Need reusable behavior around functions?  Use a decorator
```

## Most important patterns to remember

```
# Alternative constructor
@classmethod
def from_dict(cls, data):
    return cls(...)
```

```
# Related pure helper
@staticmethod
def validate(value):
    return ...
```

```
# Safe general-purpose decorator
from functools import wraps

def decorator(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs)

    return wrapper
```

```
# Parameterized decorator
def decorator_factory(option):
    def decorator(function):
        @wraps(function)
        def wrapper(*args, **kwargs):
            return function(*args, **kwargs)

        return wrapper

    return decorator
```

The deep idea is that decorators alter or enrich behavior without changing the original function’s source code, while `@classmethod` and `@staticmethod` alter how a class-level function is bound and called. Python’s descriptor protocol is the machinery behind these features, including regular methods and `@property`.[[docs.python](https://docs.python.org/3/library/functions.html)][[docs.python](https://docs.python.org/3/howto/descriptor.html)]
