Abstract Base Classes (ABCs) and protocols are two ways to define the **expected interface** of an object. You only need to learn enough to choose correctly:

- Use an **ABC** when you want a formal parent class that enforces required methods at runtime.
- Use a **Protocol** when you want flexible duck typing with type-checker support.
- Use plain duck typing when the interface is small and obvious.

# 1. The problem they solve

Suppose you build a service that sends notifications:

```
def send_alert(sender, message):
    return sender.send(message)
```

This function assumes that `sender` has:

```
send(message)
```

But without documentation, another developer may write:

```
class BrokenSender:
    def deliver(self, message):
        return message
```

Then:

```
send_alert(BrokenSender(), "System down")
```

fails at runtime because there is no `.send()` method.

ABCs and protocols make the expected interface clearer:

```
Any sender must provide send(message).
```

This is especially useful for your AI and startup systems, where you may have interchangeable:

- LLM providers
- Vector databases
- Payment services
- Notification channels
- Model evaluators
- Storage repositories
- Agent tools

---

# 2. What is an interface?

An interface is a description of what an object can do.

For a notification sender:

```
send(message) → result
```

The interface focuses on behavior, not implementation.

An interface does not need to explain whether the sender uses:

- SMTP
- SMS
- Slack
- WhatsApp
- A third-party API
- A local test object

It only defines the operation the rest of your application needs.

```
sender.send(message)
```

This is the foundation of polymorphism and duck typing. Python’s glossary describes duck typing as using an object based on whether it supports the required interface rather than checking its exact type.[[docs.python](https://docs.python.org/3/glossary.html)]

---

# 3. Abstract Base Classes

An **Abstract Base Class**, or ABC, is a parent class that defines required methods for its subclasses.

Use:

```
from abc import ABC, abstractmethod
```

Example:

```
class NotificationSender(ABC):

    @abstractmethod
    def send(self, message):
        pass
```

Now create an implementation:

```
class EmailSender(NotificationSender):

    def send(self, message):
        return f"Email sent: {message}"
```

Another implementation:

```
class SMSSender(NotificationSender):

    def send(self, message):
        return f"SMS sent: {message}"
```

Use them:

```
senders = [
    EmailSender(),
    SMSSender(),
]

for sender in senders:
    print(sender.send("Your ticket was updated."))
```

Output:

```
Email sent: Your ticket was updated.
SMS sent: Your ticket was updated.
```

The ABC declares:

```
send(message)
```

as a required method.

Python’s `abc` module provides the infrastructure for defining abstract base classes, and a class with unimplemented abstract methods cannot normally be instantiated.[[docs.python](https://docs.python.org/3/library/abc.html)]

---

# 4. Why the ABC cannot be instantiated

This class is incomplete:

```
class NotificationSender(ABC):

    @abstractmethod
    def send(self, message):
        pass
```

This fails:

```
sender = NotificationSender()
```

You get an error similar to:

```
TypeError: Can't instantiate abstract class NotificationSender
with abstract method send
```

That is useful because the class represents an idea or contract, not a complete implementation.

You should instantiate:

```
EmailSender()
```

or:

```
SMSSender()
```

not:

```
NotificationSender()
```

---

# 5. What happens when a subclass forgets a method?

```
class BrokenSender(NotificationSender):
    pass
```

This also fails:

```
sender = BrokenSender()
```

Output:

```
TypeError: Can't instantiate abstract class BrokenSender
with abstract method send
```

The ABC catches the design problem before you use the object.

Compare this with plain duck typing:

```
class BrokenSender:
    pass
```

The class can be instantiated successfully, but it fails later when some code calls:

```
broken_sender.send("Hello")
```

ABCs move the failure earlier and make the contract more explicit.

# 6. ABC with multiple abstract methods

An interface may require more than one operation.

```
class TicketRepository(ABC):

    @abstractmethod
    def save(self, ticket):
        pass

    @abstractmethod
    def get_by_id(self, ticket_id):
        pass

    @abstractmethod
    def delete(self, ticket_id):
        pass
```

Implementation:

```
class InMemoryTicketRepository(TicketRepository):

    def __init__(self):
        self._tickets = {}

    def save(self, ticket):
        self._tickets[ticket["id"]] = ticket.copy()

    def get_by_id(self, ticket_id):
        ticket = self._tickets.get(ticket_id)

        if ticket is None:
            return None

        return ticket.copy()

    def delete(self, ticket_id):
        if ticket_id in self._tickets:
            del self._tickets[ticket_id]
```

Now the service can depend on the abstract interface:

```
class TicketService:
    def __init__(self, repository):
        self.repository = repository

    def create_ticket(self, ticket):
        self.repository.save(ticket)

        return ticket
```

Use it:

```
repository = InMemoryTicketRepository()
service = TicketService(repository)

service.create_ticket({
    "id": "T-001",
    "title": "Cannot log in",
})

print(repository.get_by_id("T-001"))
```

The service does not need to know how the repository stores data.

# 7. Abstract methods can have shared behavior

An abstract method can contain implementation that subclasses extend with `super()`.

```
class DataProcessor(ABC):

    def process(self, data):
        cleaned_data = self.clean(data)
        return self.transform(cleaned_data)

    def clean(self, data):
        return data.strip()

    @abstractmethod
    def transform(self, data):
        pass
```

Subclass:

```
class UppercaseProcessor(DataProcessor):

    def transform(self, data):
        return data.upper()
```

Usage:

```
processor = UppercaseProcessor()

print(processor.process("  hello trustdesk  "))
```

Output:

```
HELLO TRUSTDESK
```

The parent class provides the general workflow:

```
clean → transform
```

The subclass provides the variable step:

```
transform()
```

This design is often called the **template method pattern**.

# 8. Abstract properties

An ABC can require a property too.

```
class ModelProvider(ABC):

    @property
    @abstractmethod
    def model_name(self):
        pass

    @abstractmethod
    def generate(self, prompt):
        pass
```

Implementation:

```
class LocalModelProvider(ModelProvider):

    def __init__(self, model_name):
        self._model_name = model_name

    @property
    def model_name(self):
        return self._model_name

    def generate(self, prompt):
        return f"{self.model_name} generated: {prompt}"
```

Usage:

```
provider = LocalModelProvider("local-support-model")

print(provider.model_name)
print(provider.generate("Explain this ticket."))
```

An abstract property is useful when every implementation must expose a value.

Examples:

```
model_name
provider_name
supported_format
version
capabilities
```

# 9. Abstract class methods and static methods

You can also require class methods and static methods.

The order is important: `@abstractmethod` should be placed inside the other descriptor decorator. Python’s ABC documentation gives these forms for abstract class methods, static methods, and properties.[[docs.python](https://docs.python.org/3/library/abc.html)]

## Abstract class method

```
class User(ABC):

    @classmethod
    @abstractmethod
    def from_dict(cls, data):
        pass
```

Implementation:

```
class AdminUser(User):

    def __init__(self, username):
        self.username = username

    @classmethod
    def from_dict(cls, data):
        return cls(data["username"])
```

## Abstract static method

```
class Validator(ABC):

    @staticmethod
    @abstractmethod
    def validate(value):
        pass
```

Implementation:

```
class PositiveNumberValidator(Validator):

    @staticmethod
    def validate(value):
        return value > 0
```

## Important order

Correct:

```
@classmethod
@abstractmethod
def from_dict(cls, data):
    ...
```

Correct:

```
@staticmethod
@abstractmethod
def validate(value):
    ...
```

Correct:

```
@property
@abstractmethod
def name(self):
    ...
```

Do not use deprecated specialized decorators such as `@abstractclassmethod` or `@abstractstaticmethod`; modern Python combines `@classmethod` or `@staticmethod` with `@abstractmethod`.[[docs.python](https://docs.python.org/3/library/abc.html)]

# 10. Virtual subclasses with `register`

An ABC can recognize a class as a virtual subclass.

```
from abc import ABC, abstractmethod
```

```
class Exportable(ABC):

    @abstractmethod
    def export(self):
        pass
```

Register another class:

```
class ExternalReport:
    def export(self):
        return "External report exported."
```

```
Exportable.register(ExternalReport)
```

Now:

```
report = ExternalReport()

print(isinstance(report, Exportable))
```

Output:

```
True
```

However, `register()` does not add methods to `ExternalReport` and does not verify that the class actually implements the required method correctly.

```
class EmptyClass:
    pass

Exportable.register(EmptyClass)

print(isinstance(EmptyClass(), Exportable))
```

This may return:

```
True
```

even though `EmptyClass` has no `.export()` method.

For most application code, prefer:

- Normal inheritance for ABCs.
- Protocols for structural typing.
- Simple duck typing for very small interfaces.

Do not use ABC registration casually.

# 11. ABC versus duck typing

## Duck typing

```
def export_report(exporter, data):
    return exporter.export(data)
```

Any compatible object works:

```
class PDFExporter:
    def export(self, data):
        return f"PDF: {data}"


class MarkdownExporter:
    def export(self, data):
        return f"Markdown: {data}"
```

Advantages:

- Very flexible
- Minimal code
- No forced inheritance
- Natural Python style
- Works with third-party classes

Disadvantages:

- Mistakes may be detected only at runtime.
- The expected interface may be unclear.
- Static analysis has less information unless you add type hints.

## ABC

```
class Exporter(ABC):

    @abstractmethod
    def export(self, data):
        pass
```

Advantages:

- Explicit contract
- Missing implementations fail early
- Can share parent behavior
- Works well for controlled class hierarchies

Disadvantages:

- Classes usually need to inherit from the ABC.
- More rigid than duck typing.
- Third-party classes may not fit naturally.
- Interfaces can become unnecessarily complicated.

---

# 12. Protocols

A `Protocol` describes an interface structurally.

```
from typing import Protocol
```

```
class Exporter(Protocol):
    def export(self, data: str) -> str:
        ...
```

Now create classes that do not inherit from `Exporter`:

```
class PDFExporter:
    def export(self, data: str) -> str:
        return f"PDF: {data}"
```

```
class MarkdownExporter:
    def export(self, data: str) -> str:
        return f"Markdown: {data}"
```

Use the protocol as a type annotation:

```
def export_report(
    exporter: Exporter,
    data: str,
) -> str:
    return exporter.export(data)
```

Both classes are compatible because they provide:

```
export(data: str) -> str
```

The Python typing documentation describes protocols as a way to express structural subtyping—static duck typing—so a class can satisfy the interface without explicitly inheriting from the protocol.[[docs.python](https://docs.python.org/3/library/typing.html)]

---

# 13. Protocols do not normally enforce runtime inheritance

This works:

```
class EmailExporter:
    def export(self, data: str) -> str:
        return f"Email: {data}"
```

There is no inheritance:

```
class EmailExporter(Exporter):
    ...
```

Yet a static type checker can recognize it as compatible with:

```
Exporter
```

because its structure matches.

This is the key difference:

```
ABC: nominal typing
Protocol: structural typing
```

## Nominal typing

The relationship is declared explicitly:

```
class EmailExporter(Exporter):
    ...
```

## Structural typing

The relationship is inferred from behavior:

```
class EmailExporter:
    def export(self, data):
        ...
```

No explicit inheritance is required.

---

# 14. Static type checking

Protocols are most valuable when using a static type checker such as:

- mypy
- pyright
- Pylance
- IDE type analysis

Example:

```
from typing import Protocol
```

```
class LLMClient(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

```
def answer_question(
    client: LLMClient,
    question: str,
) -> str:
    return client.generate(question)
```

Compatible implementation:

```
class LocalLLM:
    def generate(self, prompt: str) -> str:
        return f"Local answer: {prompt}"
```

Incompatible implementation:

```
class BrokenLLM:
    def complete(self, prompt: str) -> str:
        return "Answer"
```

A static type checker can report that `BrokenLLM` does not satisfy `LLMClient` because it has:

```
complete()
```

instead of:

```
generate()
```

At runtime, Python may not complain until the function actually calls:

```
client.generate(question)
```

Therefore:

```
Protocols help catch interface mistakes before runtime.
```

# 15. Protocol with attributes

A protocol can require attributes as well as methods.

```
class ModelProvider(Protocol):
    name: str

    def generate(self, prompt: str) -> str:
        ...
```

Compatible class:

```
class LocalModel:
    name = "local-model-v1"

    def generate(self, prompt: str) -> str:
        return f"Response from {self.name}: {prompt}"
```

Use it:

```
def describe_provider(provider: ModelProvider):
    return f"{provider.name}: ready"
```

```
model = LocalModel()

print(describe_provider(model))
```

Output:

```
local-model-v1: ready
```

Protocols are useful for describing lightweight components:

```
class Cache(Protocol):
    def get(self, key: str):
        ...

    def set(self, key: str, value) -> None:
        ...
```

```
class Tool(Protocol):
    name: str

    def run(self, input_text: str) -> str:
        ...
```

```
class VectorStore(Protocol):
    def search(self, query: str, limit: int) -> list[str]:
        ...
```

# 16. `@runtime_checkable`

By default, a protocol is mainly for static analysis.

If you want to use:

```
isinstance(obj, ProtocolName)
```

add:

```
from typing import Protocol, runtime_checkable
```

```
@runtime_checkable
class Closable(Protocol):
    def close(self) -> None:
        ...
```

Compatible class:

```
class FileLikeResource:
    def close(self) -> None:
        print("Resource closed.")
```

```
resource = FileLikeResource()

print(isinstance(resource, Closable))
```

Output:

```
True
```

## Important limitation

Runtime-checkable protocols check only whether the required attribute or method exists. They do **not** verify the method’s type signature or whether it actually works correctly.[[docs.python](https://docs.python.org/3/library/typing.html)]

For example:

```
class WrongClosable:
    def close(self, password, token):
        pass
```

This may still pass the runtime attribute check because `.close` exists, even though calling it without arguments fails.

So:

```
@runtime_checkable
```

does not replace testing or static type checking.

Use it for simple capability checks, such as:

```
if isinstance(resource, Closable):
    resource.close()
```

Do not treat it as full runtime validation.

# 17. Protocol versus ABC

|Feature|ABC|Protocol|
|---|---|---|
|Requires inheritance|Usually yes|No|
|Enforces missing methods at instantiation|Yes|No|
|Supports shared implementation|Yes|Can provide limited default behavior, but mainly describes interfaces|
|Main typing style|Nominal|Structural|
|Best for|Controlled class families|Independent interchangeable implementations|
|Works naturally with third-party classes|Less flexible|More flexible|
|Static type-checker support|Yes|Excellent|
|Runtime interface enforcement|Stronger|Limited|
|Typical example|`PaymentProcessor` hierarchy|`LLMClient`, `Cache`, `Tool`|

## Simple rule

Use an **ABC** when you want to say:

```
These classes are members of one formal family and must implement these methods.
```

Use a **Protocol** when you want to say:

```
Any object with this shape can be used here.
```

# 18. Which should you choose?

## Choose plain duck typing when

Your interface is tiny and the code is simple:

```
def send_message(sender, message):
    return sender.send(message)
```

This is perfectly reasonable.

## Choose a Protocol when

You want:

- Type hints
- IDE assistance
- Static error detection
- Flexible third-party implementations
- Dependency injection
- Test doubles
- Plugin interfaces
- AI provider interfaces

Example:

```
class LLMProvider(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

This is probably the best default for many modern Python application architectures.

## Choose an ABC when

You want:

- A formal parent class
- Runtime prevention of incomplete subclasses
- Shared implementation
- Common class-level behavior
- A controlled plugin hierarchy
- Explicit inheritance-based architecture

Example:

```
class ModelEvaluator(ABC):
    @abstractmethod
    def evaluate(self, predictions, labels):
        ...
```

# 19. AI architecture example

Suppose your assistant should work with different model providers.

## Protocol version

```
from typing import Protocol
```

```
class LLMProvider(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

Implementations:

```
class LocalProvider:
    def generate(self, prompt: str) -> str:
        return f"Local response to: {prompt}"
```

```
class CloudProvider:
    def generate(self, prompt: str) -> str:
        return f"Cloud response to: {prompt}"
```

Service:

```
class SupportAssistant:
    def __init__(self, provider: LLMProvider):
        self._provider = provider

    def answer(self, question: str) -> str:
        prompt = (
            "Answer this customer support question clearly: "
            f"{question}"
        )

        return self._provider.generate(prompt)
```

Usage:

```
assistant = SupportAssistant(LocalProvider())

print(
    assistant.answer(
        "How can I reset my password?"
    )
)
```

Switch providers:

```
assistant = SupportAssistant(CloudProvider())
```

No change to `SupportAssistant` is needed.

## ABC version

```
from abc import ABC, abstractmethod
```

```
class LLMProvider(ABC):

    @abstractmethod
    def generate(self, prompt: str) -> str:
        pass
```

```
class LocalProvider(LLMProvider):

    def generate(self, prompt: str) -> str:
        return f"Local response to: {prompt}"
```

```
class CloudProvider(LLMProvider):

    def generate(self, prompt: str) -> str:
        return f"Cloud response to: {prompt}"
```

The service is almost identical:

```
class SupportAssistant:
    def __init__(self, provider: LLMProvider):
        self._provider = provider

    def answer(self, question: str) -> str:
        return self._provider.generate(question)
```

The difference is architectural:

- The ABC requires providers to inherit from `LLMProvider`.
- The Protocol allows any compatible provider without inheritance.

# 20. Testing with protocols

Protocols make dependency replacement easy.

Production provider:

```
class RealLLMProvider:
    def generate(self, prompt: str) -> str:
        return "Response from a real model."
```

Test provider:

```
class FakeLLMProvider:
    def generate(self, prompt: str) -> str:
        return "Fixed test response."
```

The assistant works with both:

```
test_assistant = SupportAssistant(
    FakeLLMProvider()
)

print(test_assistant.answer("Test question"))
```

Output:

```
Fixed test response.
```

This avoids making tests depend on:

- Network access
- Cloud credentials
- Model availability
- API cost
- Nondeterministic model output
- Long inference time

That is one of the most valuable practical uses of protocols and interfaces.

# 21. Small interfaces are better

Avoid huge interfaces:

```
class AIPlatform(Protocol):
    def generate(self, prompt): ...
    def embed(self, text): ...
    def search(self, query): ...
    def save_user(self, user): ...
    def send_email(self, message): ...
    def process_payment(self, amount): ...
```

Most implementations will not logically support everything.

Prefer focused protocols:

```
class Generator(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

```
class Embedder(Protocol):
    def embed(self, text: str) -> list[float]:
        ...
```

```
class Searcher(Protocol):
    def search(self, query: str, limit: int) -> list[str]:
        ...
```

```
class Notifier(Protocol):
    def send(self, message: str) -> None:
        ...
```

Small interfaces:

- Are easier to implement.
- Are easier to test.
- Reduce coupling.
- Improve substitution.
- Make dependencies clearer.
- Prevent classes from becoming bloated.

This connects directly to the Interface Segregation Principle from SOLID design.

# 22. Common mistakes

## Using an ABC when plain duck typing is enough

This may be unnecessary:

```
class HasName(ABC):
    @abstractmethod
    def get_name(self):
        pass
```

If your function only needs:

```
obj.name
```

a protocol or duck typing may be simpler.

---

## Using a Protocol expecting runtime enforcement

This does not prevent incomplete classes from being created:

```
class Tool(Protocol):
    def run(self, command: str) -> str:
        ...
```

A broken class can still be instantiated:

```
class BrokenTool:
    pass
```

The error appears only when code calls:

```
broken_tool.run("test")
```

Use an ABC if you specifically need runtime prevention of incomplete subclasses.

---

## Confusing `Protocol` with an actual implementation

This:

```
class Tool(Protocol):
    def run(self, command):
        ...
```

describes expected behavior. It is not normally a concrete tool you instantiate.

Create:

```
class SearchTool:
    def run(self, command):
        return "Search result"
```

---

## Making protocols too large

A protocol should describe what a consumer needs, not every capability an object might have.

If a service only calls:

```
provider.generate(prompt)
```

then its protocol should probably only require:

```
generate()
```

---

## Incorrect abstract-decorator order

Use:

```
class Example(ABC):

    @classmethod
    @abstractmethod
    def create(cls):
        pass
```

not:

```
class Example(ABC):

    @abstractmethod
    @classmethod
    def create(cls):
        pass
```

For abstract properties:

```
@property
@abstractmethod
def name(self):
    ...
```

Python’s `abc` documentation specifically describes `abstractmethod` as the innermost decorator when combined with method descriptors.[[docs.python](https://docs.python.org/3/library/abc.html)]

# 23. Recommended learning level

For your current Python and AI-engineering path, learn these parts thoroughly:

## Must know

```
from abc import ABC, abstractmethod
```

```
class Storage(ABC):
    @abstractmethod
    def save(self, data):
        pass
```

Understand:

- Why abstract classes cannot be instantiated.
- Why child classes must implement abstract methods.
- How polymorphic code uses the abstract interface.

Also learn:

```
from typing import Protocol
```

```
class Storage(Protocol):
    def save(self, data) -> None:
        ...
```

Understand:

- Protocols use structural typing.
- Implementations do not need inheritance.
- Type checkers can verify compatibility.
- Protocols are excellent for dependency injection and testing.

## Learn later

You do not need to master these immediately:

- Custom ABC metaclasses
- `__subclasshook__`
- Virtual subclass registration
- Generic protocols with type variables
- Recursive protocols
- Runtime protocol internals
- Complex multiple inheritance with ABCs
- Descriptor implementation details

These are useful in frameworks and library design, but they are not necessary for normal AI application development.

# 24. Final decision guide

```
# Small and simple:
def process(tool):
    return tool.run()
```

Use plain duck typing when this is clear enough.

```
from typing import Protocol

class Tool(Protocol):
    def run(self, command: str) -> str:
        ...
```

Use a protocol when you want a flexible, typed interface.

```
from abc import ABC, abstractmethod

class Tool(ABC):

    @abstractmethod
    def run(self, command: str) -> str:
        pass
```

Use an ABC when you want a formal inheritance hierarchy and runtime enforcement.

## The shortest memory rule

```
Duck typing: “Can it do this?”
Protocol: “Does its shape satisfy this interface?”
ABC: “Is it an official member of this class family?”
```

For your projects, a strong default is:

```
Plain duck typing for tiny internal functions.
Protocols for application architecture and dependency injection.
ABCs for formal class families, frameworks, and enforced plugin systems.
```

In a TrustDesk-style AI application, you might use:

```
class LLMProvider(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

for interchangeable model providers, and an ABC when you want to enforce a formal hierarchy of model evaluators or plugin implementations. Protocols primarily support static structural subtyping, while ABCs provide runtime abstract-class machinery.[[docs.python](https://docs.python.org/3/library/abc.html)][[docs.python](https://docs.python.org/3/library/typing.html)]
