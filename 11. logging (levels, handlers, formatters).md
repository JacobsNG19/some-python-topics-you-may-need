Python’s `logging` system records what your program is doing and sends those records to destinations such as the terminal or a file. The four core ideas are: **loggers create records, levels classify importance, handlers choose destinations, and formatters control appearance**.[[docs.python](https://docs.python.org/3/howto/logging.html)][[docs.python](https://docs.python.org/3/library/logging.html)]

# 1. Why logging instead of `print()`?

You can debug with:

```
print("Model loaded")
print("User created")
print("Something went wrong")
```

But `print()` has limitations:

- No standard severity levels.
- No timestamps automatically.
- No logger/module names.
- Difficult to send messages to both terminal and file.
- Hard to disable or filter in production.
- Poor support for exception tracebacks.
- Difficult to configure consistently across a large project.

Logging gives you:

```
logger.info("Model loaded")
logger.warning("Disk space is low")
logger.error("Database request failed")
```

A logging event contains information such as:

```
time
logger name
severity level
message
module
function
line number
exception information
```

The standard logging architecture contains loggers, handlers, filters, and formatters. Loggers expose the interface used by application code; handlers send records to destinations; formatters define output layout; and filters provide more precise control.[[docs.python](https://docs.python.org/3/howto/logging.html)]

# 2. Your first logging program

```
import logging


logging.basicConfig(
    level=logging.INFO,
)

logging.info("Application started.")
logging.warning("Configuration file is missing.")
logging.error("Could not connect to database.")
```

Output:

```
WARNING:root:Configuration file is missing.
ERROR:root:Could not connect to database.
```

Why is the `INFO` message missing?

The default logging threshold is usually:

```
WARNING
```

Only messages at `WARNING` level or above are shown unless you configure another level.[[docs.python](https://docs.python.org/3/howto/logging.html)]

Set the level to `INFO`:

```
import logging


logging.basicConfig(
    level=logging.INFO,
)

logging.debug("Detailed debugging information.")
logging.info("Application started.")
logging.warning("Configuration file is missing.")
logging.error("Database connection failed.")
logging.critical("Application cannot continue.")
```

Output:

```
INFO:root:Application started.
WARNING:root:Configuration file is missing.
ERROR:root:Database connection failed.
CRITICAL:root:Application cannot continue.
```

`DEBUG` is hidden because it is less severe than `INFO`.

# 3. Logging levels

Python provides five commonly used levels.

|Level|Numeric value|Use it for|
|---|---|---|
|`DEBUG`|10|Detailed information for diagnosing problems|
|`INFO`|20|Normal confirmation that the application is working|
|`WARNING`|30|Unexpected situation, but the program can continue|
|`ERROR`|40|A serious operation failed|
|`CRITICAL`|50|The application or major component may not continue|

These are the standard levels and numeric values defined by Python’s logging module.[[docs.python](https://docs.python.org/3/library/logging.html)]

## `DEBUG`

Use for detailed developer information:

```
logger.debug(
    "Received request with user_id=%s",
    user_id,
)
```

Examples:

```
Loaded 250 rows.
Using model version ticket-classifier-v1.
Cache lookup returned a miss.
Prompt length: 342 tokens.
```

Do not normally display `DEBUG` logs in production.

---

## `INFO`

Use for normal important events:

```
logger.info("Application started.")
logger.info("Ticket %s created.", ticket_id)
logger.info("Model loaded successfully.")
```

Examples:

```
Server started.
Database connection established.
Training completed.
User logged in.
```

---

## `WARNING`

Use when something unexpected happened but the program can continue:

```
logger.warning(
    "Model response took longer than expected: %.2f seconds",
    elapsed,
)
```

Examples:

```
Configuration value is missing; using default.
Retrying API request.
Disk space is low.
Cache is unavailable; continuing without cache.
```

---

## `ERROR`

Use when a specific operation fails:

```
logger.error(
    "Could not save ticket %s.",
    ticket_id,
)
```

The program may continue handling other work.

Examples:

```
Failed to process one input file.
Database query failed.
Could not send notification.
Model request failed.
```

---

## `CRITICAL`

Use for severe failures that may stop the application:

```
logger.critical(
    "No valid model provider is available."
)
```

Examples:

```
Database credentials are missing.
The application cannot start.
A required security service is unavailable.
```

Do not use `CRITICAL` for ordinary errors.

---

# 4. Logging with a named logger

Avoid using the root logger directly in application modules.

Instead:

```
import logging


logger = logging.getLogger(__name__)
```

Then:

```
logger.info("Ticket service started.")
logger.warning("No tickets found.")
```

If the file is called:

```
services/tickets.py
```

then:

```
__name__
```

may become:

```
services.tickets
```

This tells you which module produced the message.

Example:

```
import logging


logger = logging.getLogger(__name__)


def create_ticket(title):
    logger.info("Creating ticket with title=%r", title)

    return {
        "id": "T-001",
        "title": title,
    }
```

The recommended pattern is:

```
logger = logging.getLogger(__name__)
```

inside each module, while configuration is performed centrally by the application entry point.[[docs.python](https://docs.python.org/3/howto/logging.html)][[docs.python](https://docs.python.org/3/library/logging.html)]

# 5. Logger, handler, formatter

The logging flow is:

```
Your code
   ↓
Logger creates a LogRecord
   ↓
Logger checks level
   ↓
Handler sends the record somewhere
   ↓
Formatter converts it into text
   ↓
Terminal, file, or another destination
```

## Logger

Your application uses the logger:

```
logger.info("Application started.")
```

The logger determines whether the record should continue through the logging system.

## Handler

A handler chooses where the record goes:

```
terminal
file
rotating file
email
network service
custom destination
```

Common handlers include:

```
logging.StreamHandler()
logging.FileHandler("app.log")
logging.handlers.RotatingFileHandler(...)
```

## Formatter

A formatter decides how the record appears:

```
"%(asctime)s - %(name)s - %(levelname)s - %(message)s"
```

Example output:

```
2026-09-03 16:30:00 - services.tickets - INFO - Ticket created
```

# 6. Configuring a logger manually

```
import logging
import sys


logger = logging.getLogger("trustdesk")
logger.setLevel(logging.DEBUG)

console_handler = logging.StreamHandler(sys.stdout)
console_handler.setLevel(logging.INFO)

formatter = logging.Formatter(
    "%(asctime)s | %(name)s | %(levelname)s | %(message)s"
)

console_handler.setFormatter(formatter)
logger.addHandler(console_handler)

logger.debug("Debug details.")
logger.info("Application started.")
logger.warning("Cache is unavailable.")
```

Output:

```
2026-09-03 16:30:00,000 | trustdesk | INFO | Application started.
2026-09-03 16:30:00,000 | trustdesk | WARNING | Cache is unavailable.
```

Why is `DEBUG` hidden?

The logger accepts `DEBUG`, but the handler only accepts:

```
INFO
```

This introduces an important rule:

```
A log record must pass both the logger threshold and the handler threshold.
```

The effective output level is controlled by both. A handler can be stricter than its logger.[[docs.python](https://docs.python.org/3/library/logging.html)]

---

# 7. Logger level versus handler level

```
logger.setLevel(logging.DEBUG)
```

This allows the logger to process:

```
DEBUG and above
```

But:

```
console_handler.setLevel(logging.INFO)
```

sends only:

```
INFO and above
```

So:

```
logger.debug("Debug message")
```

is created but not emitted by that handler.

You can add another handler for debug logs:

```
debug_handler = logging.FileHandler("debug.log")
debug_handler.setLevel(logging.DEBUG)
debug_handler.setFormatter(formatter)

logger.addHandler(debug_handler)
```

Now:

- Console receives `INFO` and above.
- `debug.log` receives `DEBUG` and above.

This is a common production arrangement.

# 8. Formatting log messages

A useful formatter:

```
formatter = logging.Formatter(
    fmt=(
        "%(asctime)s | "
        "%(levelname)s | "
        "%(name)s | "
        "%(message)s"
    ),
    datefmt="%Y-%m-%d %H:%M:%S",
)
```

Available fields include:

|Field|Meaning|
|---|---|
|`%(asctime)s`|Time of the event|
|`%(levelname)s`|`INFO`, `ERROR`, etc.|
|`%(name)s`|Logger name|
|`%(message)s`|Final log message|
|`%(filename)s`|Source filename|
|`%(module)s`|Module name|
|`%(funcName)s`|Function name|
|`%(lineno)d`|Source line number|
|`%(process)d`|Process ID|
|`%(threadName)s`|Thread name|

Example:

```
formatter = logging.Formatter(
    (
        "%(asctime)s | %(levelname)s | "
        "%(name)s | %(funcName)s:%(lineno)d | "
        "%(message)s"
    ),
    datefmt="%Y-%m-%d %H:%M:%S",
)
```

Output:

```
2026-09-03 16:31:00 | INFO | trustdesk.api | create_ticket:42 | Ticket created
```

The logging documentation identifies fields such as `asctime`, `levelname`, and `message` as common formatter values.[[docs.python](https://docs.python.org/3/howto/logging.html)]

# 9. Formatting correctly with arguments

Prefer this:

```
logger.info(
    "Ticket %s created for user %s",
    ticket_id,
    user_id,
)
```

Instead of:

```
logger.info(
    f"Ticket {ticket_id} created for user {user_id}"
)
```

Why?

Logging can delay formatting until it knows the message will actually be emitted. This is more efficient, especially for `DEBUG` logs that are disabled.

Use:

```
logger.debug(
    "Payload contains %d records",
    len(records),
)
```

not:

```
logger.debug(
    f"Payload contains {len(records)} records"
)
```

Both are readable, but the first follows conventional logging style.

# 10. Logging exceptions with `logger.exception`

Suppose a database operation fails:

```
import logging


logger = logging.getLogger(__name__)


def load_ticket(ticket_id):
    try:
        return query_database(ticket_id)

    except ConnectionError:
        logger.exception(
            "Could not load ticket %s.",
            ticket_id,
        )

        return None
```

`logger.exception()` should be used inside an `except` block. It logs at `ERROR` level and includes the current exception traceback automatically.

Output may look like:

```
ERROR:services.tickets:Could not load ticket T-001.
Traceback (most recent call last):
  ...
ConnectionError: Database unavailable
```

This is much better than:

```
logger.error("Database failed.")
```

because the traceback tells you where and why it failed.

## Alternative: `exc_info=True`

You can also write:

```
logger.error(
    "Could not load ticket %s.",
    ticket_id,
    exc_info=True,
)
```

inside an exception handler.

But this is simpler:

```
logger.exception("Could not load ticket %s.", ticket_id)
```

# 11. Logging without exposing secrets

Never log sensitive values directly:

```
logger.info("Password: %s", password)
logger.debug("API key: %s", api_key)
logger.info("Authorization header: %s", headers)
```

Avoid logging:

- Passwords
- API keys
- Access tokens
- Session cookies
- Private encryption keys
- Full payment information
- Unnecessary personal information
- Entire confidential customer conversations

Use masking:

```
def mask_token(token):
    if not token:
        return "<missing>"

    return token[:4] + "..." + token[-4:]
```

```
logger.debug(
    "Using API token %s",
    mask_token(api_token),
)
```

For TrustDesk-like systems, be especially careful with support conversations because they may contain identity information, financial details, or authentication data.

# 12. Console and file handlers together

A useful application configuration:

```
import logging
import sys


def configure_logging():
    logger = logging.getLogger()
    logger.setLevel(logging.DEBUG)

    console_handler = logging.StreamHandler(sys.stdout)
    console_handler.setLevel(logging.INFO)

    file_handler = logging.FileHandler(
        "application.log",
        encoding="utf-8",
    )
    file_handler.setLevel(logging.DEBUG)

    formatter = logging.Formatter(
        "%(asctime)s | %(levelname)s | "
        "%(name)s | %(message)s",
        datefmt="%Y-%m-%d %H:%M:%S",
    )

    console_handler.setFormatter(formatter)
    file_handler.setFormatter(formatter)

    logger.addHandler(console_handler)
    logger.addHandler(file_handler)
```

Use it:

```
configure_logging()

logger = logging.getLogger(__name__)

logger.debug("Detailed internal information.")
logger.info("Application started.")
logger.warning("Using default configuration.")
logger.error("Could not process request.")
```

Behavior:

```
Terminal → INFO, WARNING, ERROR, CRITICAL
File     → DEBUG, INFO, WARNING, ERROR, CRITICAL
```

This lets developers see detailed information in the file while keeping the terminal readable.

# 13. Avoid duplicate handlers

If you call configuration more than once, you may add duplicate handlers:

```
configure_logging()
configure_logging()
```

Then one log message may appear twice.

Protect the setup:

```
def configure_logging():
    logger = logging.getLogger()

    if logger.handlers:
        return

    logger.setLevel(logging.INFO)

    handler = logging.StreamHandler()
    formatter = logging.Formatter(
        "%(levelname)s: %(message)s"
    )

    handler.setFormatter(formatter)
    logger.addHandler(handler)
```

Or configure logging only once at the application entry point.

For libraries, never configure the root logger automatically. A library should create a logger:

```
logger = logging.getLogger(__name__)
```

and let the application decide how logs are handled.

# 14. Logger hierarchy

Logger names are hierarchical.

```
logging.getLogger("trustdesk")
logging.getLogger("trustdesk.api")
logging.getLogger("trustdesk.database")
logging.getLogger("trustdesk.agent")
```

The hierarchy is based on dots:

```
trustdesk
├── trustdesk.api
├── trustdesk.database
└── trustdesk.agent
```

Example:

```
root_logger = logging.getLogger("trustdesk")
api_logger = logging.getLogger("trustdesk.api")
db_logger = logging.getLogger("trustdesk.database")
```

A child logger can propagate records to its parent.

This lets you configure the whole application:

```
logging.getLogger("trustdesk").setLevel(logging.INFO)
```

or one component:

```
logging.getLogger("trustdesk.agent").setLevel(logging.DEBUG)
```

This is valuable when debugging one subsystem without making every module noisy.

---

# 15. Propagation

By default, a child logger usually passes records to ancestor handlers.

```
logger = logging.getLogger("trustdesk.api")
```

The record may be processed by:

```
trustdesk.api handlers
trustdesk handlers
root handlers
```

If you attach a handler to both a child and its parent, you may get duplicate messages.

To stop propagation:

```
logger.propagate = False
```

Use this only when you intentionally want a logger to handle its own output independently.

# 16. `basicConfig`

For small scripts, this is enough:

```
import logging


logging.basicConfig(
    level=logging.INFO,
    format=(
        "%(asctime)s | %(levelname)s | "
        "%(name)s | %(message)s"
    ),
)
```

Then:

```
logger = logging.getLogger(__name__)

logger.info("Script started.")
```

## Important behavior

`basicConfig()` does nothing if the root logger already has handlers configured, unless you explicitly force reconfiguration:

```
logging.basicConfig(
    level=logging.DEBUG,
    force=True,
)
```

Use `force=True` carefully, especially in applications or libraries where another component may already have configured logging.

# 17. Logging levels from CLI arguments

Since you just learned `argparse`, connect it with logging.

```
import argparse
import logging


def build_parser():
    parser = argparse.ArgumentParser(
        description="Process support tickets."
    )

    parser.add_argument(
        "--verbose",
        action="store_true",
        help="Enable debug logging.",
    )

    return parser
```

Configure:

```
def configure_logging(verbose):
    level = logging.DEBUG if verbose else logging.INFO

    logging.basicConfig(
        level=level,
        format=(
            "%(asctime)s | %(levelname)s | "
            "%(name)s | %(message)s"
        ),
    )
```

Main function:

```
def main():
    parser = build_parser()
    args = parser.parse_args()

    configure_logging(args.verbose)

    logger = logging.getLogger(__name__)

    logger.debug("Debug mode enabled.")
    logger.info("Processing started.")
```

Run normally:

```
python app.py
```

Only `INFO` and above appear.

Run with:

```
python app.py --verbose
```

`DEBUG` messages also appear.

## Verbosity levels

A more flexible CLI:

```
parser.add_argument(
    "-v",
    "--verbose",
    action="count",
    default=0,
)
```

Use:

```
python app.py -v
python app.py -vv
python app.py -vvv
```

Map levels:

```
def logging_level(verbosity):
    if verbosity >= 3:
        return logging.DEBUG

    if verbosity == 2:
        return logging.INFO

    if verbosity == 1:
        return logging.WARNING

    return logging.ERROR
```

Or use a simpler mapping:

```
levels = {
    0: logging.WARNING,
    1: logging.INFO,
    2: logging.DEBUG,
}

level = levels.get(args.verbose, logging.DEBUG)
```

# 19. Rotating log files

A log file can grow forever. Use rotation.

```
import logging
from logging.handlers import RotatingFileHandler
```

```
logger = logging.getLogger("trustdesk")
logger.setLevel(logging.DEBUG)

handler = RotatingFileHandler(
    "trustdesk.log",
    maxBytes=1_000_000,
    backupCount=3,
    encoding="utf-8",
)

formatter = logging.Formatter(
    "%(asctime)s | %(levelname)s | "
    "%(name)s | %(message)s"
)

handler.setFormatter(formatter)
logger.addHandler(handler)
```

When the file reaches approximately 1 MB:

```
trustdesk.log
trustdesk.log.1
trustdesk.log.2
trustdesk.log.3
```

Older files are rotated out after the backup limit.

This is useful for long-running services.

## Time-based rotation

```
from logging.handlers import TimedRotatingFileHandler
```

```
handler = TimedRotatingFileHandler(
    "trustdesk.log",
    when="midnight",
    backupCount=7,
    encoding="utf-8",
)
```

This can create one log file per day and retain seven backups.

# 20. Filters

A filter gives finer control over which records a handler receives.

```
class OnlyErrors(logging.Filter):
    def filter(self, record):
        return record.levelno >= logging.ERROR
```

Use it:

```
error_handler = logging.FileHandler(
    "errors.log",
    encoding="utf-8",
)

error_handler.setLevel(logging.ERROR)
error_handler.addFilter(OnlyErrors())

logger.addHandler(error_handler)
```

Now `errors.log` receives only errors and critical messages.

## Filter by logger name

```
class AgentOnlyFilter(logging.Filter):
    def filter(self, record):
        return record.name.startswith(
            "trustdesk.agent"
        )
```

This is useful if you want a separate file for:

```
trustdesk.agent
```

without including database or API logs.

# 21. Structured logging with `extra`

You can attach additional context:

```
logger.info(
    "Ticket processed.",
    extra={
        "ticket_id": "T-001",
        "user_id": "U-100",
    },
)
```

To display those fields, the formatter must expect them:

```
formatter = logging.Formatter(
    (
        "%(asctime)s | %(levelname)s | "
        "ticket=%(ticket_id)s | "
        "user=%(user_id)s | "
        "%(message)s"
    )
)
```

Be careful: every record sent to this formatter must contain both fields, or formatting can fail.

A safer approach is to use a custom filter that supplies defaults:

```
class ContextDefaults(logging.Filter):
    def filter(self, record):
        if not hasattr(record, "ticket_id"):
            record.ticket_id = "-"

        if not hasattr(record, "user_id"):
            record.user_id = "-"

        return True
```

Then:

```
handler.addFilter(ContextDefaults())
```

For modern production systems, logs are often emitted as JSON so log platforms can search fields such as:

```
request_id
user_id
ticket_id
model_name
latency_ms
status
```

# 22. Logging AI operations

A useful AI-service example:

```
import logging
from time import perf_counter


logger = logging.getLogger(__name__)


def classify_ticket(model, text):
    start = perf_counter()

    logger.info(
        "Starting ticket classification with model=%s",
        model,
    )

    try:
        normalized = text.strip().lower()

        if "payment" in normalized:
            category = "billing"
        elif "password" in normalized:
            category = "account_access"
        else:
            category = "general"

        elapsed_ms = (
            perf_counter() - start
        ) * 1000

        logger.info(
            "Ticket classified category=%s "
            "latency_ms=%.2f",
            category,
            elapsed_ms,
        )

        return category

    except Exception:
        logger.exception(
            "Ticket classification failed "
            "with model=%s",
            model,
        )

        raise
```

Good logs include:

```
model name
operation
result category
latency
request or ticket ID
failure traceback
```

Do not log the full customer message unless you have a clear privacy and security reason.

Prefer:

```
logger.info(
    "Ticket classified ticket_id=%s category=%s",
    ticket_id,
    category,
)
```

rather than:

```
logger.info(
    "Customer message: %s",
    full_message,
)
```

# 23. Logging decorators

You can combine decorators with logging.

```
import logging
from functools import wraps
from time import perf_counter


logger = logging.getLogger(__name__)
```

```
def log_duration(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        start = perf_counter()

        try:
            result = function(*args, **kwargs)
            return result

        finally:
            elapsed_ms = (
                perf_counter() - start
            ) * 1000

            logger.info(
                "%s completed in %.2f ms",
                function.__name__,
                elapsed_ms,
            )

    return wrapper
```

Use it:

```
@log_duration
def process_tickets(tickets):
    return [
        ticket.strip().lower()
        for ticket in tickets
    ]
```

```
process_tickets([
    "Login issue",
    "Payment issue",
])
```

This is useful for:

- API endpoint timing
- Agent tool timing
- Retrieval latency
- Model inference timing
- Database operations
- Data pipeline stages

If you need to log failures too:

```
def log_duration(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        start = perf_counter()

        try:
            return function(*args, **kwargs)

        except Exception:
            logger.exception(
                "%s failed",
                function.__name__,
            )
            raise

        finally:
            elapsed_ms = (
                perf_counter() - start
            ) * 1000

            logger.info(
                "%s took %.2f ms",
                function.__name__,
                elapsed_ms,
            )

    return wrapper
```

# 24. Logging in libraries

If you are building a reusable Python package, do this:

```
import logging


logger = logging.getLogger(__name__)
```

Then:

```
logger.info("Library operation started.")
```

Do not do this inside the library:

```
logging.basicConfig(...)
```

Why?

Because the application using your library should decide:

- Where logs go.
- Which level is enabled.
- What format is used.
- Whether logs are JSON.
- Whether logs are sent to a monitoring platform.

You can add a null handler for libraries:

```
import logging


logger = logging.getLogger(__name__)
logger.addHandler(logging.NullHandler())
```

This prevents “no handler” warnings while leaving configuration to the application.

# 25. Logging configuration function

A reusable configuration function:

```
import logging
import sys
from logging.handlers import RotatingFileHandler


def configure_logging(
    level=logging.INFO,
    log_file="application.log",
):
    logger = logging.getLogger()
    logger.setLevel(level)

    if logger.handlers:
        return

    formatter = logging.Formatter(
        (
            "%(asctime)s | %(levelname)s | "
            "%(name)s | %(message)s"
        ),
        datefmt="%Y-%m-%d %H:%M:%S",
    )

    console_handler = logging.StreamHandler(sys.stdout)
    console_handler.setLevel(level)
    console_handler.setFormatter(formatter)

    file_handler = RotatingFileHandler(
        log_file,
        maxBytes=1_000_000,
        backupCount=3,
        encoding="utf-8",
    )
    file_handler.setLevel(logging.DEBUG)
    file_handler.setFormatter(formatter)

    logger.addHandler(console_handler)
    logger.addHandler(file_handler)
```

Use it:

```
def main():
    configure_logging()

    logger = logging.getLogger(__name__)

    logger.info("Application started.")
```

A more flexible CLI integration:

```
def main():
    parser = build_parser()
    args = parser.parse_args()

    level = (
        logging.DEBUG
        if args.verbose
        else logging.INFO
    )

    configure_logging(level=level)

    logger = logging.getLogger(__name__)
    logger.info("Application started.")
```

# 26. Logging with `exc_info`

Compare these:

```
logger.error("Request failed.")
```

This only logs the message.

```
logger.error(
    "Request failed.",
    exc_info=True,
)
```

This logs the message and traceback.

Inside an exception handler, prefer:

```
logger.exception("Request failed.")
```

Example:

```
try:
    result = call_external_api()

except TimeoutError:
    logger.exception(
        "External API timed out."
    )
    raise
```

Logging the traceback is important for diagnosing:

- Which function failed.
- Which line failed.
- Which exception was raised.
- What call path led to the failure.

# 27. `stack_info`

Sometimes you want the current stack even without an exception:

```
logger.debug(
    "Entering unusual code path.",
    stack_info=True,
)
```

This is useful during difficult debugging, but it can produce large logs. Use it temporarily or at `DEBUG` level.

# 28. Performance considerations

Logging itself has some cost.

Use level checks when preparing expensive debug data:

```
if logger.isEnabledFor(logging.DEBUG):
    expensive_data = build_debug_report()
    logger.debug("Debug data: %s", expensive_data)
```

Without the check:

```
logger.debug(
    "Debug data: %s",
    build_debug_report(),
)
```

`build_debug_report()` runs even if `DEBUG` logs are disabled.

For ordinary values, this is enough:

```
logger.debug(
    "Processed %d records",
    len(records),
)
```

The message formatting is deferred appropriately.

# 29. Common mistakes

## Logging with `print()` in production code

Use:

```
logger.info("Server started.")
```

instead of:

```
print("Server started.")
```

Use `print()` for direct command output intended for the CLI user. Use logging for internal operational events.

A CLI may appropriately use both:

```
print("Report saved to result.json")
logger.info("Report written successfully.")
```

---

## Using the wrong level

Avoid:

```
logger.error("Retrying request.")
```

if the application is still functioning normally.

Use:

```
logger.warning("Retrying request.")
```

Use `ERROR` when an operation failed.

---

## Logging secrets

Never:

```
logger.debug("API key=%s", api_key)
```

Mask or omit sensitive values.

---

## Duplicate log messages

Usually caused by:

- Configuring logging more than once.
- Adding handlers repeatedly.
- Attaching handlers to both parent and child loggers while propagation remains enabled.

---

## Logging entire objects

Avoid:

```
logger.debug("Request=%r", request)
```

if `request` may contain tokens, cookies, passwords, or private user data.

Log selected safe fields:

```
logger.debug(
    "Request method=%s path=%s request_id=%s",
    request.method,
    request.path,
    request_id,
)
```

---

## Swallowing exceptions after logging

Bad:

```
try:
    process()
except Exception:
    logger.exception("Processing failed.")
    return None
```

This may hide a serious failure.

Sometimes returning `None` is correct, but often you should re-raise:

```
except Exception:
    logger.exception("Processing failed.")
    raise
```

import argparse
import logging


def build_parser():
    parser = argparse.ArgumentParser()

    parser.add_argument(
        "-v",
        "--verbose",
        action="count",
        default=0,
    )

    return parser


def configure_logging(verbosity):
    if verbosity >= 3:
        level = logging.DEBUG
    elif verbosity == 2:
        level = logging.INFO
    elif verbosity == 1:
        level = logging.WARNING
    else:
        level = logging.ERROR

    logging.basicConfig(
        level=level,
        format=(
            "%(asctime)s | %(levelname)s | "
            "%(message)s"
        ),
    )


def main():
    parser = build_parser()
    args = parser.parse_args()

    configure_logging(args.verbose)

    logger = logging.getLogger(__name__)

    logger.debug("Debug details.")
    logger.info("Normal information.")
    logger.warning("Warning information.")
    logger.error("Error information.")


if __name__ == "__main__":
    main()

## Exercise 5 answer

```
import logging
from time import perf_counter


logger = logging.getLogger(__name__)


def classify_ticket(ticket_id, text):
    start = perf_counter()

    logger.info(
        "Classification started ticket_id=%s",
        ticket_id,
    )

    try:
        normalized = text.strip().lower()

        if "payment" in normalized:
            category = "billing"
        elif "password" in normalized:
            category = "account_access"
        else:
            category = "general"

        elapsed_ms = (
            perf_counter() - start
        ) * 1000

        logger.info(
            "Classification completed "
            "ticket_id=%s category=%s "
            "latency_ms=%.2f",
            ticket_id,
            category,
            elapsed_ms,
        )

        return category

    except Exception:
        logger.exception(
            "Classification failed ticket_id=%s",
            ticket_id,
        )
        raise
```

```
ticket ID
category
duration
failure traceback
```

but not the full private message.

# 32. Final logging architecture

Remember the pipeline:

```
logger
  ↓
level filtering
  ↓
LogRecord
  ↓
handler
  ↓
formatter
  ↓
destination
```

## Logger

Your code uses:

```
logger.info("Ticket created.")
```

## Level

The level expresses importance:

```
DEBUG
INFO
WARNING
ERROR
CRITICAL
```

## Handler

The handler chooses the destination:

```
StreamHandler       # Terminal
FileHandler         # File
RotatingFileHandler # Size-limited files
```

## Formatter

The formatter controls the appearance:

```
"%(asctime)s | %(levelname)s | %(name)s | %(message)s"
```

## Best-practice application pattern

```
# In every module
import logging

logger = logging.getLogger(__name__)
```

```
# Once, in the application entry point
logging.basicConfig(
    level=logging.INFO,
    format=(
        "%(asctime)s | %(levelname)s | "
        "%(name)s | %(message)s"
    ),
)
```

```
# During normal application code
logger.info("Operation started.")
logger.warning("Using fallback configuration.")
logger.error("Operation failed.")
logger.exception("Operation failed with traceback.")
```

For your CLI and AI projects:

```
print()   → direct output intended for the user
logging   → internal events, diagnostics, operations, and failures
```

A solid starting configuration is:

```
import logging


logging.basicConfig(
    level=logging.INFO,
    format=(
        "%(asctime)s | %(levelname)s | "
        "%(name)s | %(message)s"
    ),
)

logger = logging.getLogger(__name__)
```

Then add handlers, rotating files, filters, structured context, and JSON output as your application grows. Python’s logging package is deliberately modular: loggers expose the application interface, handlers choose destinations, formatters define presentation, and filters provide detailed selection control.[[docs.python](https://docs.python.org/3/howto/logging.html)][[docs.python](https://docs.python.org/3/library/logging.html)]
