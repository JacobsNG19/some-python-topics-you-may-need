Python type hints let you describe what values, arguments, and return values are expected to contain. `TypedDict`, `Union`, `Optional`, `Literal`, and `Any` are mainly tools for making dictionaries and function interfaces clearer; Python usually does not enforce these annotations automatically at runtime. The `typing` module provides runtime support for type annotations and static-analysis tools use them to detect many mistakes before execution.[[docs.python](https://docs.python.org/3/library/typing.html)]

# 1. What type hints do

Without type hints:

```
def create_ticket(title, priority):
    return {
        "title": title,
        "priority": priority,
    }
```

A reader does not immediately know:

- Must `title` be a string?
- What values are allowed for `priority`?
- What does the function return?
- Which dictionary keys are guaranteed?
- Can the function return `None`?

With type hints:

```
def create_ticket(
    title: str,
    priority: str,
) -> dict:
    return {
        "title": title,
        "priority": priority,
    }
```

This communicates the intended interface.

Type hints help:

- Editors provide better autocomplete.
- Static checkers detect inconsistent types.
- Developers understand functions faster.
- Refactoring becomes safer.
- Large AI/data projects become easier to maintain.
- Interfaces between modules become explicit.

But this annotation does not automatically reject an integer:

```
def greet(name: str) -> str:
    return f"Hello, {name}!"

greet(123)
```

Python may still run it because annotations are generally not runtime validation by themselves.

# 2. Basic type hints

## Variables

```
name: str = "Toussaint"
age: int = 20
height: float = 1.75
is_student: bool = True
```

## Function parameters and return values

```
def add(first: int, second: int) -> int:
    return first + second
```

```
result = add(10, 20)
```

## Common collection types

Modern Python supports built-in generic types:

```
names: list[str] = ["Toussaint", "Aline"]
scores: dict[str, float] = {
    "accuracy": 0.94,
}
coordinates: tuple[float, float] = (3.5, 4.2)
unique_ids: set[int] = {1, 2, 3}
```

For older Python versions, you may see:

```
from typing import List, Dict, Tuple, Set
```

```
names: List[str]
scores: Dict[str, float]
```

For current Python code, prefer:

```
list[str]
dict[str, float]
tuple[float, float]
set[int]
```

# 3. `Any`

`Any` means:

> This value may be of any type, and the type checker should not restrict its use.

```
from typing import Any
```

```
def log_value(value: Any) -> None:
    print(value)
```

This accepts anything:

```
log_value("hello")
log_value(42)
log_value([1, 2, 3])
log_value({"status": "ok"})
```

## `Any` disables type checking

```
def process(value: Any):
    return value.not_a_real_method()
```

A static type checker may not complain because `Any` says:

```
Trust me; do not check this value.
```

At runtime, the code may fail:

```
AttributeError
```

## When `Any` is useful

Use `Any` when:

- Working with genuinely dynamic data.
- Receiving arbitrary JSON.
- Interacting with an untyped third-party library.
- Writing a temporary migration.
- Handling framework-specific dynamic objects.
- Gradually adding types to an old codebase.

Example:

```
import json
from typing import Any


def load_json(path: str) -> Any:
    with open(path, encoding="utf-8") as file:
        return json.load(file)
```

JSON can contain:

```
objects
arrays
strings
numbers
booleans
null
```

So `Any` may be practical at the raw input boundary.

## Do not use `Any everywhere

This weakens your type system:

```
def classify(data: Any) -> Any:
    ...
```

Now the reader learns almost nothing.

Prefer precise types after validation:

```
def classify(
    ticket: dict[str, str]
) -> Literal[
    "billing",
    "account_access",
    "general",
]:
    ...
```

A useful rule:

```
Use Any at uncertain boundaries.
Convert external data into precise types quickly.
```

# 4. `Union`

`Union` means a value may be one of several types.

```
from typing import Union
```

```
def format_id(identifier: Union[int, str]) -> str:
    return f"ID-{identifier}"
```

This accepts:

```
format_id(101)
format_id("T-101")
```

The type is:

```
int | str
```

in modern Python.

## Modern syntax

Prefer:

```
def format_id(identifier: int | str) -> str:
    return f"ID-{identifier}"
```

This is equivalent to:

```
Union[int, str]
```

The `|` union syntax is available in modern Python versions.

## Union with more types

```
def normalize_score(
    score: int | float | str,
) -> float:
    return float(score)
```

Accepted values:

```
normalize_score(90)
normalize_score(0.9)
normalize_score("0.95")
```

The function still may fail for:

```
normalize_score("excellent")
```

Type hints describe accepted types, not every possible semantic rule.

---

# 5. Handling a `Union`

When a value can have different types, your code may need to narrow it.

```
def describe_value(value: int | str) -> str:
    if isinstance(value, int):
        return f"Integer: {value}"

    return f"String: {value}"
```

The `isinstance()` check tells both Python and static type checkers which branch is active.

Another example:

```
def get_length(value: str | list[str]) -> int:
    if isinstance(value, str):
        return len(value)

    return len(value)
```

Both branches support `len()`, so you could simplify:

```
def get_length(value: str | list[str]) -> int:
    return len(value)
```

Good type design can reveal when multiple types support the same behavior.

# 6. `Optional`

`Optional[T]` means:

```
T or None
```

```
from typing import Optional
```

```
def find_ticket(
    ticket_id: str,
) -> Optional[dict[str, str]]:
    ...
```

This means the function may return:

```
dict[str, str]
```

or:

```
None
```

Modern syntax is:

```
def find_ticket(
    ticket_id: str,
) -> dict[str, str] | None:
    ...
```

These are equivalent:

```
Optional[str]
str | None
```

## Example

```
tickets = {
    "T-001": {
        "title": "Cannot log in",
        "priority": "high",
    }
}
```

```
def find_ticket(
    ticket_id: str,
) -> dict[str, str] | None:
    return tickets.get(ticket_id)
```

Use safely:

```
ticket = find_ticket("T-001")

if ticket is None:
    print("Ticket not found.")
else:
    print(ticket["title"])
```

A type checker uses the `if` branch to understand that `ticket` is no longer `None`.

## Common mistake

This may fail:

```
ticket = find_ticket("T-999")

print(ticket["title"])
```

because `ticket` could be `None`.

Correct:

```
if ticket is not None:
    print(ticket["title"])
```

or:

```
if ticket:
    print(ticket["title"])
```

The explicit `is not None` check is clearer when an empty dictionary is still a valid result.

---

# 7. `Optional` does not mean optional parameter

This is important.

```
def greet(name: str | None):
    ...
```

The parameter is still required when calling the function:

```
greet()
```

This fails because no argument was provided.

The annotation means:

```
The caller must provide an argument, but its value may be str or None.
```

To make the parameter optional in the calling syntax, provide a default:

```
def greet(name: str | None = None):
    if name is None:
        name = "Guest"

    return f"Hello, {name}!"
```

Now both work:

```
greet()
greet("Toussaint")
greet(None)
```

Distinguish:

```
Optional value → the value may be None
Optional argument → the caller may omit the argument
```

# 8. `Literal`

`Literal` restricts a value to specific exact values.

```
from typing import Literal
```

```
Priority = Literal["low", "normal", "high"]
```

Use it:

```
def create_ticket(
    title: str,
    priority: Priority,
) -> dict[str, str]:
    return {
        "title": title,
        "priority": priority,
    }
```

Valid:

```
create_ticket(
    "Cannot log in",
    "high",
)
```

Invalid according to a static type checker:

```
create_ticket(
    "Cannot log in",
    "urgent",
)
```

At runtime, Python may still accept `"urgent"` unless you validate it.

## Runtime validation

```
PRIORITIES = {"low", "normal", "high"}
```

```
def create_ticket(
    title: str,
    priority: Priority,
) -> dict[str, str]:
    if priority not in PRIORITIES:
        raise ValueError(
            f"Invalid priority: {priority}"
        )

    return {
        "title": title,
        "priority": priority,
    }
```

`Literal` improves static checking; the `if` statement provides runtime protection.

This works well with the `argparse` lesson:

```
from typing import Literal


OutputFormat = Literal["text", "json", "csv"]
```

```
def render_result(
    result: dict,
    output_format: OutputFormat,

    if output_format == "json":
        return "JSON output"

    if output_format == "csv":
        return "CSV output"

    return "Text output"
```

A type checker knows that the only valid values are:

```

"json"
"csv"
```

With `argparse`, still validate at runtime:

```
parser.add_argument(
    "--format",
    choices=["text", "json", "csv"],
    default="text",
)
```

Now:

```
argparse → runtime validation
Literal  → static documentation and checking
```

They complement each other.

# 11. `TypedDict`

A normal dictionary does not tell the type checker which keys must exist.

```
ticket = {
    "id": "T-001",
    "title": "Cannot log in",
    "priority": "high",
}
```

This annotation is broad:

```
ticket: dict[str, str]
```

It says:

```
Keys are strings and values are strings.
```

But it does not clearly specify:

- Which keys are required.
- What each key means.
- Whether some fields are optional.
- Whether different keys have different value types.

`TypedDict` describes the expected structure of a dictionary.

```
from typing import TypedDict
```

```
class Ticket(TypedDict):
    id: str
    title: str
    priority: str
```

Now:

```
ticket: Ticket = {
    "id": "T-001",
    "title": "Cannot log in",
    "priority": "high",
}
```

A static type checker understands the keys and their types.

The `typing` module provides `TypedDict` specifically for describing dictionary-shaped data with a fixed set of string keys and associated value types.[[docs.python](https://docs.python.org/3/library/typing.html)]

---

# 12. `TypedDict` is not a runtime class

This is an important distinction.

```
class Ticket(TypedDict):
    id: str
    title: str
```

At runtime, you still create a normal dictionary:

```
ticket = {
    "id": "T-001",
    "title": "Cannot log in",
}
```

You do not normally write:

```
ticket = Ticket(
    id="T-001",
    title="Cannot log in",
)
```

`TypedDict` mainly helps static analysis. It does not automatically:

- Validate keys.
- Convert values.
- Reject extra keys.
- Enforce required values at runtime.
- Provide methods like a normal class.

For runtime validation, use:

- Manual checks
- Dataclasses plus validation
- Pydantic
- Marshmallow
- JSON Schema
- Another validation library

# 13. `TypedDict` in functions

```
class Ticket(TypedDict):
    id: str
    title: str
    priority: str
```

```
def summarize_ticket(ticket: Ticket) -> str:
    return (
        f"{ticket['id']}: "
        f"{ticket['title']} "
        f"({ticket['priority']})"
    )
```

```
ticket: Ticket = {
    "id": "T-001",
    "title": "Cannot log in",
    "priority": "high",
}

print(summarize_ticket(ticket))
```

Output:

```
T-001: Cannot log in (high)
```

A type checker can detect:

```
bad_ticket: Ticket = {
    "id": "T-001",
    "title": "Cannot log in",
}
```

because `priority` is missing.

It can also detect:

```
bad_ticket: Ticket = {
    "id": "T-001",
    "title": "Cannot log in",
    "priority": 10,
}
```

because `priority` should be a string.

# 15. Optional fields in `TypedDict`

By default, all fields are required.

```
class User(TypedDict):
    username: str
    email: str
    phone: str
```

This requires all three keys.

To make one field optional, use `NotRequired`.

```
from typing import NotRequired, TypedDict
```

```
class User(TypedDict):
    username: str
    email: str
    phone: NotRequired[str]
```

Now this is valid for static type checking:

```
user: User = {
    "username": "toussaint",
    "email": "toussaint@example.com",
}
```

But this is also valid:

```
user: User = {
    "username": "toussaint",
    "email": "toussaint@example.com",
    "phone": "+25700000000",
}
```

## Older syntax

You may see:

```
from typing import Optional, TypedDict
```

```
class User(TypedDict, total=False):
    phone: str
```

But `total=False` makes all fields optional, not just one.

Modern code can use:

```
NotRequired[str]
```

for individual optional fields.

# 16. Required fields with `total=False`

Sometimes most fields are optional but a few are required.

```

```

```
class UserUpdate(TypedDict, total=False):
    username: str
    email: str
    is_active: Required[bool]
```

This means:

- `username` is optional.
- `email` is optional.
- `is_active` is required.

Example:

```
update: UserUpdate = {
    "is_active": True,

```

This is useful for:

- PATCH-like API payloads.
- Partial configuration updates.
- Optional metadata.
- Incremental pipeline results.

# 18. `TypedDict` versus dataclass

Both can model structured data, but they serve different purposes.

|Feature|`TypedDict`|`dataclass`|
|---|---|---|
|Runtime object|Normal dictionary|Class instance|
|Access style|`ticket["title"]`|`ticket.title`|
|Runtime methods|No|Yes|
|Static key checking|Yes|Attribute checking|
|Natural for JSON/API data|Excellent|Requires conversion|
|Behavior and methods|Limited|Excellent|
|Automatic runtime validation|No|No, unless added|
|Best use|JSON-shaped dictionaries|Domain objects with behavior|

Use `TypedDict` for:

```
{
    "id": "T-001",
    "title": "Cannot log in",
}
```

Use a dataclass for:

```
ticket.title
ticket.close()
ticket.assign_to(user)
```

Example dataclass:

```
from dataclasses import dataclass
```

```
@dataclass
class TicketObject:
    id: str
    title: str
    priority: str

    def close(self):
        print(f"Ticket {self.id} closed.")
```

A useful rule:

```
Data from JSON or APIs → TypedDict
Data with behavior and methods → dataclass or normal class
```

# 19. Combining `TypedDict`, `Optional`, and `Literal`

Here is a realistic API response:

```
from typing import Literal, NotRequired, TypedDict
```

```
Category = Literal[
    "billing",
    "account_access",
    "technical_issue",
    "general",
]
```

```
class Classification(TypedDict):
    category: Category
    confidence: float
    explanation: NotRequired[str]
```

```
def classify(text: str) -> Classification:
    normalized = text.lower()

    if "payment" in normalized:
        return {
            "category": "billing",
            "confidence": 0.96,
        }

    if "password" in normalized:
        return {
            "category": "account_access",
            "confidence": 0.94,
            "explanation": "Password-related keywords detected.",
        }

    return {
        "category": "general",
        "confidence": 0.55,
    }
```

Now the output shape is clearly documented:

```
result = classify("My payment failed")

print(result["category"])
print(result["confidence"])
```

Possible output:

```
billing
0.96
```

This pattern is very useful in AI applications for:

- Model responses.
- Tool outputs.
- Agent state.
- API payloads.
- Evaluation reports.
- Retrieval results.
- Pipeline metadata.

# 20. `Union` with `TypedDict`

Sometimes an API response has multiple possible shapes.

```
class SuccessResponse(TypedDict):
    status: Literal["success"]
    data: dict[str, str]
```

```
class ErrorResponse(TypedDict):
    status: Literal["error"]
    message: str
```

Create a union:

```
APIResponse = SuccessResponse | ErrorResponse
```

Function:

```
def handle_response(response: APIResponse) -> None:
    if response["status"] == "success":
        print(response["data"])
    else:
        print(f"Error: {response['message']}")
```

Success example:

```
handle_response({
    "status": "success",
    "data": {
        "ticket_id": "T-001",
    },
})
```

Error example:

```
handle_response({
    "status": "error",
    "message": "Ticket not found.",
})
```

The `status` literal acts as a discriminator:

```
status == "success" → SuccessResponse
status == "error"   → ErrorResponse
```

This pattern is called a **tagged union** or **discriminated union**.

It is excellent for API responses because each variant has different required fields.

# 21. Type aliases

A type alias gives a complex type a readable name.

```
TicketID = str
```

```
TicketPriority = Literal[
    "low",
    "normal",
    "high",
]
```

```
TicketTags = list[str]
```

Use them:

```
def get_ticket(
    ticket_id: TicketID,
) -> Ticket | None:
    ...
```

In modern Python, for explicit aliases, you can use:

```
from typing import TypeAlias
```

```
TicketID: TypeAlias = str
```

Or:

```
TicketPriority: TypeAlias = Literal[
    "low",
    "normal",
    "high",
]
```

Aliases improve readability but do not create new runtime types.

These are still both strings:

```
TicketID = str
UserID = str
```

A type checker may distinguish aliases conceptually, but Python runtime does not enforce them as separate types.

---

# 22. `NewType`: stronger logical distinction

If you want a static distinction between IDs, use `NewType`.

```
from typing import NewType
```

```
TicketID = NewType("TicketID", str)
UserID = NewType("UserID", str)
```

Create values:

```
ticket_id = TicketID("T-001")
user_id = UserID("U-001")
```

Use:

```
def get_ticket(ticket_id: TicketID):
    ...
```

At runtime, these values behave like strings, but static type checkers can distinguish `TicketID` from `UserID`.

This can prevent mistakes such as passing a user ID where a ticket ID is expected.

You do not need `NewType` immediately, but it becomes useful in larger codebases with many identifiers.

# 23. Type hints and runtime validation

Annotations alone do not protect external input.

```
class Ticket(TypedDict):
    id: str
    priority: Literal["low", "normal", "high"]
```

This does not automatically validate data from:

```
json.loads(...)
```

or:

```
request.json()
```

You must validate at the boundary.

Simple manual validation:

```
def parse_ticket(data: dict) -> Ticket:
    if not isinstance(data.get("id"), str):
        raise ValueError("id must be a string.")

    if data.get("priority") not in {
        "low",
        "normal",
        "high",
    }:
        raise ValueError(
            "priority must be low, normal, or high."
        )

    return {
        "id": data["id"],
        "priority": data["priority"],
    }
```

For larger applications, use a runtime validation library such as Pydantic.

Conceptually:

```
External untrusted data
        ↓
Runtime validation
        ↓
Typed internal data
        ↓
Business logic
```

This is important for:

- HTTP requests.
- CLI input.
- Configuration files.
- Database rows.
- Webhooks.
- LLM-generated JSON.
- Agent tool arguments.
- User-submitted data.

# 24. Type hints for `argparse`

You can combine the CLI lesson with type hints.

```
import argparse
from typing import Literal
```

```
OutputFormat = Literal["text", "json"]
```

```
def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser()

    parser.add_argument(
        "--format",
        choices=["text", "json"],
        default="text",
    )

    return parser
```

The value returned by `argparse` is generally typed dynamically, so you may validate or narrow it:

```
def render_output(
    data: dict,
    output_format: OutputFormat,
) -> str:
    if output_format == "json":
        return "JSON output"

    return "Text output"
```

Because `argparse` validates the choices at runtime, the `Literal` type documents the same contract for your application functions.

# 25. Type hints for protocols

This connects to your previous lesson.

```
from typing import Protocol
```

```
class LLMProvider(Protocol):
    def generate(self, prompt: str) -> str:
        ...
```

```
def answer(
    provider: LLMProvider,
    question: str,
) -> str:
    return provider.generate(question)
```

Now any compatible provider can be passed:

```
class LocalProvider:
    def generate(self, prompt: str) -> str:
        return f"Local response: {prompt}"
```

```
class CloudProvider:
    def generate(self, prompt: str) -> str:
        return f"Cloud response: {prompt}"
```

Both satisfy the protocol structurally.

Protocols describe behavior:

```
What methods are required?
```

`TypedDict` describes dictionary data:

```
What keys and values are required?
```

`Literal` restricts exact allowed values:

```
Which strings are valid?
```

`Optional` expresses possible absence:

```
Can this be None?
```

`Any` allows uncertainty:

```
Do not enforce a specific type here.
```

# 26. A complete typed AI example

```
from typing import Literal, NotRequired, Protocol, TypedDict
```

Define valid categories:

```
Category = Literal[
    "billing",
    "account_access",
    "technical_issue",
    "general",
]
```

Define the output structure:

```
class ClassificationResult(TypedDict):
    category: Category
    confidence: float
    explanation: NotRequired[str]
```

Define the model interface:

```
class Classifier(Protocol):
    def classify(
        self,
        text: str,
    ) -> ClassificationResult:
        ...
```

Implement it:

```
class KeywordClassifier:
    def classify(
        self,
        text: str,
    ) -> ClassificationResult:
        normalized = text.lower()

        if "payment" in normalized:
            return {
                "category": "billing",
                "confidence": 0.96,
                "explanation": (
                    "Payment-related keyword detected."
                ),
            }

        if "password" in normalized:
            return {
                "category": "account_access",
                "confidence": 0.94,
            }

        return {
            "category": "general",
            "confidence": 0.55,
        }
```

Use it:

```
def process_ticket(
    classifier: Classifier,
    text: str,
) -> ClassificationResult:
    return classifier.classify(text)
```

```
classifier = KeywordClassifier()

result = process_ticket(
    classifier,
    "My payment failed.",
)

print(result)
```

Possible output:

```
{
    "category": "billing",
    "confidence": 0.96,
    "explanation": "Payment-related keyword detected."
}
```

This combines:

- `Protocol` for behavior.
- `TypedDict` for structured output.
- `Literal` for valid categories.
- Type annotations for parameters and return values.
- Duck typing because `KeywordClassifier` does not need to inherit from `Classifier`.

# 27. `Any` at an AI boundary

LLM outputs are often uncertain or untrusted.

Weak:

```
def parse_model_output(output: Any) -> Any:
    return output
```

This provides almost no safety.

Better:

```
from typing import Any
```

```
def extract_model_category(
    output: Any,
) -> Category:
    if not isinstance(output, dict):
        raise ValueError(
            "Model output must be an object."
        )

    category = output.get("category")

    if category not in {
        "billing",
        "account_access",
        "technical_issue",
        "general",
    }:
        raise ValueError(
            "Model returned an invalid category."
        )

    return category
```

Use `Any` only at the uncertain boundary:

```
raw model output: Any
        ↓
validation
        ↓
Category / ClassificationResult
```

Once data is validated, stop carrying `Any` through the rest of the application.

# 28. Optional values in AI systems

Many AI operations can fail to produce a result:

```
def retrieve_context(
    query: str,
) -> list[str] | None:
    ...
```

Use:

```
context = retrieve_context(query)

if context is None:
    prompt = query
else:
    prompt = "\n".join(context)
```

Another example:

```
class UserProfile(TypedDict):
    username: str
    bio: str | None
```

Here, the key `bio` is required, but its value may be `None`.

Compare with:

```
class UserProfile(TypedDict):
    username: str
    bio: NotRequired[str]
```

Now the key itself may be absent.

These are different:

```
bio: str | None        → key exists, value may be None
bio: NotRequired[str]  → key may not exist
```

# 29. Type narrowing with `Literal`

```
Mode = Literal["train", "evaluate", "predict"]
```

```
def run_mode(mode: Mode):
    if mode == "train":
        return "Training model."

    if mode == "evaluate":
        return "Evaluating model."

    return "Running prediction."
```

A type checker can understand that after checking `"train"` and `"evaluate"`, the remaining valid value is `"predict"`.

With a `Literal`-based tagged dictionary:

```
class Success(TypedDict):
    status: Literal["success"]
    result: str


class Failure(TypedDict):
    status: Literal["failure"]
    error: str


Response = Success | Failure
```

```
def display(response: Response):
    if response["status"] == "success":
        print(response["result"])
    else:
        print(response["error"])
```

The status field tells your code which structure it has.

# 30. Common mistakes

## Mistaking annotations for validation

```
def add(a: int, b: int) -> int:
    return a + b
```

This does not guarantee callers pass integers.

If runtime validation matters:

```
def add(a: int, b: int) -> int:
    if not isinstance(a, int):
        raise TypeError("a must be an integer.")

    if not isinstance(b, int):
        raise TypeError("b must be an integer.")

    return a + b
```

---

## Using `Any` everywhere

Avoid:

```
def process(data: Any) -> Any:
    ...
```

Prefer:

```
def process(data: Ticket) -> ClassificationResult:
    ...
```

after validating the input.

---

## Using `Optional` when you mean an omitted key

These are different:

```
bio: str | None
```

and:

```
bio: NotRequired[str]
```

Use the first when the key exists but may contain `None`.

Use the second when the key may be missing.

---

## Using `dict[str, str]` for every dictionary

This loses domain information:

```
ticket: dict[str, str]
```

Prefer:

```
class Ticket(TypedDict):
    id: str
    title: str
    priority: Literal["low", "normal", "high"]
```

when the structure matters.

---

## Assuming `Literal` validates at runtime

This:

```
priority: Literal["low", "normal", "high"]
```

does not automatically reject:

```
priority = "urgent"
```

Use `argparse choices`, manual validation, or a runtime validation library.

---

## Overcomplicating types

This may be unnecessary:

```
def process(
    data: dict[
        str,
        list[
            dict[
                str,
                int | str | None
            ]
        ]
    ]
):
    ...
```

Create named types:

```
class Metric(TypedDict):
    name: str
    value: float
```

```
class Report(TypedDict):
    title: str
    metrics: list[Metric]
```

Named structures are easier to read, test, and reuse.

# 33. Final cheat sheet

## `Any`

```
from typing import Any

value: Any
```

Means:

```
Any type; static checking is mostly disabled.
```

Use at uncertain boundaries, not everywhere.

## `Union`

Older syntax:

```
from typing import Union

value: Union[int, str]
```

Modern syntax:

```
value: int | str
```

Means:

```
The value may be one of several types.
```

## `Optional`

Older syntax:

```
from typing import Optional

result: Optional[str]
```

Modern syntax:

```
result: str | None
```

Means:

```
The value may be a string or None.
```

## `Literal`

```
from typing import Literal

Priority = Literal["low", "normal", "high"]
```

Means:

```
Only these exact values are valid.
```

Static restriction; add runtime validation separately.

## `TypedDict`

```
from typing import TypedDict

class Ticket(TypedDict):
    id: str
    title: str
    priority: str
```

Means:

```
A dictionary with this expected key structure.
```

Static description; not automatic runtime validation.

## `NotRequired`

```
from typing import NotRequired

class User(TypedDict):
    username: str
    phone: NotRequired[str]
```

Means:

```
The phone key may be missing.
```

## Recommended pattern

```
from typing import Literal, NotRequired, TypedDict
```

```
Priority = Literal[
    "low",
    "normal",
    "high",
]
```

```
class Ticket(TypedDict):
    id: str
    title: str
    priority: Priority
    description: NotRequired[str]
```

```
def create_ticket(
    title: str,
    priority: Priority,
) -> Ticket:
    return {
        "id": "T-001",
        "title": title,
        "priority": priority,
    }
```

The core mental model is:

```
TypedDict → What does this dictionary contain?
Literal   → Which exact values are allowed?
Union     → Which types are possible?
Optional  → Can the value be None?
Any       → The type is currently unknown or intentionally dynamic.
```

For your AI projects, use `Any` only for raw external data, validate it, then convert it into precise structures using `TypedDict`, `Literal`, `Optional`, and protocols. The `typing` module is designed to support this kind of type description, while static type-checking tools use the annotations to identify interface and data-shape mistakes before runtime.[[docs.python](https://docs.python.org/3/library/typing.html)]
