Special methods—often called **dunder methods** because of their double underscores—let your custom classes work naturally with Python syntax such as `print(obj)`, `len(obj)`, `obj + other`, `obj[key]`, `for item in obj`, `obj()`, and `with obj:`. They are Python’s mechanism for protocols and operator overloading: you define a specially named method, and Python calls it when the corresponding language feature is used. [docs.python](https://docs.python.org/3/reference/datamodel.html?highlight=setattr)

# 1. What “dunder” means

“Dunder” is short for:

```text
double underscore
```

Examples:

```python
__init__
__str__
__repr__
__len__
__add__
__eq__
__iter__
__getitem__
```

They have this form:

```python
__special_name__
```

These are not ordinary methods you call manually in most cases. Instead, Python calls them when you use normal syntax.

| Normal Python syntax | Special method Python uses |
|---|---|
| `obj = MyClass()` | `__new__()` then `__init__()` |
| `print(obj)` | `__str__()` |
| `repr(obj)` | `__repr__()` |
| `len(obj)` | `__len__()` |
| `obj + other` | `__add__()` |
| `obj == other` | `__eq__()` |
| `obj < other` | `__lt__()` |
| `obj[key]` | `__getitem__()` |
| `obj[key] = value` | `__setitem__()` |
| `del obj[key]` | `__delitem__()` |
| `value in obj` | `__contains__()` |
| `for value in obj` | `__iter__()` |
| `next(iterator)` | `__next__()` |
| `obj()` | `__call__()` |
| `with obj:` | `__enter__()` and `__exit__()` |
| `bool(obj)` | `__bool__()` or `__len__()` |

For example:

```python
x[i]
```

is roughly equivalent to:

```python
type(x).__getitem__(x, i)
```

And:

```python
x + y
```

is roughly equivalent to:

```python
type(x).__add__(x, y)
```

Python’s data model defines these special names as hooks for arithmetic, indexing, iteration, and many other parts of the language. [docs.python](https://docs.python.org/3/reference/datamodel.html?highlight=setattr)

***

# 2. Why special methods matter

Dunder methods let you create classes that feel like built-in Python objects.

Without them:

```python
wallet.add_money(other_wallet)
wallet.get_amount()
wallet.is_equal_to(other_wallet)
```

With them:

```python
wallet + other_wallet
len(wallet)
wallet == other_wallet
print(wallet)
```

The second style is often:

- More readable
- More expressive
- Easier to use correctly
- Better integrated with Python tools and built-ins
- Compatible with polymorphism and duck typing

But do not add special methods only to make code “look clever.” Use them when the behavior genuinely matches Python’s expectations.

***

# 3. `__init__`: initialize an object

You already know this one.

```python
class Student:
    def __init__(self, name, age):
        self.name = name
        self.age = age
```

```python
student = Student("Toussaint", 20)
```

When you create an object:

```python
Student("Toussaint", 20)
```

Python calls:

```python
Student.__init__(student, "Toussaint", 20)
```

Conceptually, Python first creates the object, then initializes it.

## Important detail

`__init__` does **not** create the object. It initializes an object that already exists.

Object creation is handled by:

```python
__new__
```

Most normal classes only need `__init__`.

***

# 4. `__new__`: create an object

`__new__` runs before `__init__`.

```python
class Example:
    def __new__(cls):
        print("__new__ creates the object")
        return super().__new__(cls)

    def __init__(self):
        print("__init__ initializes the object")
```

```python
obj = Example()
```

Output:

```text
__new__ creates the object
__init__ initializes the object
```

## When to use `__new__`

Use `__new__` only for advanced designs, such as:

- Immutable types like custom `str`, `int`, or `tuple` subclasses
- Singleton-like patterns
- Object caching or interning
- Controlling whether an object is created
- Metaclasses and framework internals

For normal classes, prefer `__init__`.

## Immutable-type example

```python
class PositiveInt(int):
    def __new__(cls, value):
        if value <= 0:
            raise ValueError("Value must be positive.")

        return super().__new__(cls, value)
```

```python
score = PositiveInt(10)

print(score)
print(type(score))
```

Output:

```text
10
<class '__main__.PositiveInt'>
```

This fails:

```python
PositiveInt(-5)
```

because `int` objects are immutable. By the time `__init__` runs, the integer’s value has already been created, so validation belongs in `__new__`.

# 5. `__repr__` vs `__str__`

These two methods control how objects appear as text.

```python
class Ticket:
    def __init__(self, ticket_id, title, priority):
        self.ticket_id = ticket_id
        self.title = title
        self.priority = priority
```

```python
ticket = Ticket(
    "T-101",
    "Cannot reset password",
    "high",
)

print(ticket)
```

Without `__str__` or `__repr__`, output looks like:

```text
<__main__.Ticket object at 0x...>
```

That is technically valid but not useful.

***

## `__repr__`: developer representation

`__repr__` is intended for developers, debugging, logs, and interactive Python sessions.

```python
class Ticket:
    def __init__(self, ticket_id, title, priority):
        self.ticket_id = ticket_id
        self.title = title
        self.priority = priority

    def __repr__(self):
        return (
            f"Ticket("
            f"ticket_id={self.ticket_id!r}, "
            f"title={self.title!r}, "
            f"priority={self.priority!r}"
            f")"
        )
```

```python
ticket = Ticket(
    "T-101",
    "Cannot reset password",
    "high",
)

print(repr(ticket))
print(ticket)
```

Output:

```text
Ticket(ticket_id='T-101', title='Cannot reset password', priority='high')
Ticket(ticket_id='T-101', title='Cannot reset password', priority='high')
```

If `__str__` is absent, Python uses `__repr__` for `print()` too. [docs.python](https://docs.python.org/3/reference/datamodel.html?highlight=setattr)

## Best-practice goal for `__repr__`

If reasonably possible, make `__repr__` look like code that could recreate the object:

```python
Ticket(
    ticket_id='T-101',
    title='Cannot reset password',
    priority='high'
)
```

The official documentation describes `__repr__` as the “official” representation and recommends an information-rich, unambiguous result; when possible, it should resemble a valid Python expression that recreates the value. [docs.python](https://docs.python.org/3/reference/datamodel.html?highlight=setattr)

***

## `__str__`: human-friendly representation

`__str__` is designed for normal users and readable output.

```python
class Ticket:
    def __init__(self, ticket_id, title, priority):
        self.ticket_id = ticket_id
        self.title = title
        self.priority = priority

    def __repr__(self):
        return (
            f"Ticket("
            f"ticket_id={self.ticket_id!r}, "
            f"title={self.title!r}, "
            f"priority={self.priority!r}"
            f")"
        )

    def __str__(self):
        return (
            f"[{self.priority.upper()}] "
            f"{self.ticket_id}: {self.title}"
        )
```

```python
ticket = Ticket(
    "T-101",
    "Cannot reset password",
    "high",
)

print(ticket)
print(repr(ticket))
```

Output:

```text
[HIGH] T-101: Cannot reset password
Ticket(ticket_id='T-101', title='Cannot reset password', priority='high')
```

## Difference to remember

| Method | Purpose | Usually used by |
|---|---|---|
| `__repr__` | Unambiguous developer/debugging representation | `repr(obj)`, REPL, containers, logs |
| `__str__` | Friendly user-facing text | `str(obj)`, `print(obj)`, f-strings |

```python
print(ticket)       # Uses __str__
print(str(ticket))  # Uses __str__
print(repr(ticket)) # Uses __repr__
```

# 6. `__len__`: support `len(obj)`

If your object represents a collection or has a natural size, define `__len__`.

```python
class TaskBoard:
    def __init__(self):
        self._tasks = []

    def add_task(self, task):
        self._tasks.append(task)

    def __len__(self):
        return len(self._tasks)
```

```python
board = TaskBoard()

board.add_task("Design database schema")
board.add_task("Build API")

print(len(board))
```

Output:

```text
2
```

Python effectively calls:

```python
TaskBoard.__len__(board)
```

## Rules for `__len__`

It must return a non-negative integer.

Incorrect:

```python
def __len__(self):
    return -1
```

Incorrect:

```python
def __len__(self):
    return "two"
```

Correct:

```python
def __len__(self):
    return len(self._tasks)
```

# 7. `__bool__`: truthiness

Python decides whether an object is truthy or falsy in conditions.

```python
if object:
    ...
```

By default, most custom objects are truthy.

You can customize this with:

```python
__bool__
```

```python
class TaskBoard:
    def __init__(self):
        self._tasks = []

    def add_task(self, task):
        self._tasks.append(task)

    def __bool__(self):
        return bool(self._tasks)
```

```python
board = TaskBoard()

if board:
    print("Board has tasks.")
else:
    print("Board is empty.")
```

Output:

```text
Board is empty.
```

Add a task:

```python
board.add_task("Build MVP")

if board:
    print("Board has tasks.")
```

Output:

```text
Board has tasks.
```

## Relationship between `__bool__` and `__len__`

When Python evaluates:

```python
if obj:
```

it generally follows this order:

1. Use `obj.__bool__()` if defined.
2. Otherwise, use `obj.__len__()`.
3. Otherwise, treat the object as `True`.

So this class is enough:

```python
class TaskBoard:
    def __init__(self):
        self._tasks = []

    def __len__(self):
        return len(self._tasks)
```

An empty board becomes falsy:

```python
if board:
    ...
```

because:

```python
len(board) == 0
```

# 8. `__eq__`: equality with `==`

Without `__eq__`, two objects are usually equal only if they are the same object in memory.

```python
class Ticket:
    def __init__(self, ticket_id):
        self.ticket_id = ticket_id
```

```python
ticket_a = Ticket("T-100")
ticket_b = Ticket("T-100")

print(ticket_a == ticket_b)
```

Output:

```text
False
```

They have the same ID, but they are separate objects.

Define equality:

```python
class Ticket:
    def __init__(self, ticket_id):
        self.ticket_id = ticket_id

    def __eq__(self, other):
        if not isinstance(other, Ticket):
            return NotImplemented

        return self.ticket_id == other.ticket_id
```

```python
ticket_a = Ticket("T-100")
ticket_b = Ticket("T-100")

print(ticket_a == ticket_b)
```

Output:

```text
True
```

Python uses:

```python
__eq__
```

for:

```python
==
```

The operator module documents that `operator.eq(a, b)` corresponds to `a == b`, as part of Python’s rich comparison operations. [docs.python](https://docs.python.org/3/library/operator.html)

***

# 9. Why return `NotImplemented`?

In operator and comparison methods, do not immediately raise an error just because the other object has a different type.

```python
def __eq__(self, other):
    if not isinstance(other, Ticket):
        return NotImplemented

    return self.ticket_id == other.ticket_id
```

`NotImplemented` tells Python:

> “I do not know how to compare myself to this kind of object.”

Python can then:

1. Try the other object’s related operation.
2. Use appropriate fallback behavior.
3. Return `False` for many equality comparisons.
4. Raise a sensible `TypeError` for unsupported ordering or arithmetic.

Example:

```python
ticket = Ticket("T-100")

print(ticket == "T-100")
```

This becomes:

```text
False
```

Returning `NotImplemented` is usually better than doing this:

```python
raise TypeError("Can only compare Ticket objects.")
```

for equality.

# 10. Equality and hashing: `__eq__` with `__hash__`

This is one of the most important advanced topics.

Python uses hashes for:

- `set`
- Dictionary keys
- Caching
- Fast membership checks

```python
users = set()
```

If you implement `__eq__`, you must think about `__hash__`.

## The hash rule

If:

```python
a == b
```

then it must also be true that:

```python
hash(a) == hash(b)
```

for hashable objects.

## Immutable value object example

```python
class TicketKey:
    def __init__(self, ticket_id):
        self.ticket_id = ticket_id

    def __eq__(self, other):
        if not isinstance(other, TicketKey):
            return NotImplemented

        return self.ticket_id == other.ticket_id

    def __hash__(self):
        return hash(self.ticket_id)

    def __repr__(self):
        return f"TicketKey({self.ticket_id!r})"
```

```python
key_a = TicketKey("T-100")
key_b = TicketKey("T-100")

print(key_a == key_b)
print(hash(key_a) == hash(key_b))
```

Output:

```text
True
True
```

Now a set removes duplicates logically:

```python
keys = {key_a, key_b}

print(keys)
```

Output:

```text
{TicketKey('T-100')}
```

## Critical warning: mutable objects

Do not make a mutable object hashable if fields involved in equality can change.

Bad idea:

```python
class MutableUser:
    def __init__(self, username):
        self.username = username

    def __hash__(self):
        return hash(self.username)
```

If you add the object to a set, then mutate `username`, the set can no longer reliably find it.

```python
user = MutableUser("toussaint")
users = {user}

user.username = "new_name"
```

The object’s hash meaning changed after insertion.

### Safe rule

- If your object is mutable, usually leave it unhashable.
- If your object is immutable and value-like, implementing `__hash__` can make sense.
- If you define `__eq__` but do not define a compatible `__hash__`, Python normally makes the class unhashable to avoid incorrect behavior.

# 11. Ordering comparisons

Python has separate methods for comparisons.

| Operator | Special method |
|---|---|
| `==` | `__eq__` |
| `!=` | `__ne__` |
| `<` | `__lt__` |
| `<=` | `__le__` |
| `>` | `__gt__` |
| `>=` | `__ge__` |

Create a task class ordered by priority score.

```python
class Task:
    def __init__(self, title, priority_score):
        self.title = title
        self.priority_score = priority_score

    def __lt__(self, other):
        if not isinstance(other, Task):
            return NotImplemented

        return self.priority_score < other.priority_score

    def __repr__(self):
        return (
            f"Task("
            f"title={self.title!r}, "
            f"priority_score={self.priority_score}"
            f")"
        )
```

```python
task_a = Task("Fix login bug", 10)
task_b = Task("Update homepage", 3)

print(task_a > task_b)
```

Output:

```text
True
```

Python can often infer `>` using the other object’s `<` behavior, but it is usually clearer to implement needed comparisons intentionally.

## `functools.total_ordering`

When a class has equality and one ordering method, `functools.total_ordering` can generate the remaining ordering methods.

```python
from functools import total_ordering
```

```python
@total_ordering
class Task:
    def __init__(self, title, priority_score):
        self.title = title
        self.priority_score = priority_score

    def __eq__(self, other):
        if not isinstance(other, Task):
            return NotImplemented

        return self.priority_score == other.priority_score

    def __lt__(self, other):
        if not isinstance(other, Task):
            return NotImplemented

        return self.priority_score < other.priority_score
```

Now Python can support:

```python
==
!=
<
<=
>
>=
```

Use this for convenience, but for extremely performance-sensitive code, explicitly implementing the methods may be faster and clearer.

# 12. Arithmetic: `__add__`, `__sub__`, and friends

Dunder methods let objects support arithmetic operators.

| Operator | Method |
|---|---|
| `a + b` | `__add__` |
| `a - b` | `__sub__` |
| `a * b` | `__mul__` |
| `a / b` | `__truediv__` |
| `a // b` | `__floordiv__` |
| `a % b` | `__mod__` |
| `a ** b` | `__pow__` |
| `a @ b` | `__matmul__` |

Python maps these operators to special methods; for example, addition corresponds to `__add__`, and the standard `operator` module exposes `operator.add(a, b)` as the functional equivalent of `a + b`. [docs.python](https://docs.python.org/3/reference/datamodel.html?highlight=setattr)

## Example: `Money`

```python
class Money:
    def __init__(self, amount, currency="BIF"):
        self.amount = amount
        self.currency = currency

    def __add__(self, other):
        if not isinstance(other, Money):
            return NotImplemented

        if self.currency != other.currency:
            raise ValueError(
                "Cannot add amounts with different currencies."
            )

        return Money(
            self.amount + other.amount,
            self.currency,
        )

    def __repr__(self):
        return (
            f"Money("
            f"amount={self.amount!r}, "
            f"currency={self.currency!r}"
            f")"
        )

    def __str__(self):
        return f"{self.amount:,.0f} {self.currency}"
```

```python
budget_a = Money(10_000, "BIF")
budget_b = Money(5_500, "BIF")

total = budget_a + budget_b

print(total)
print(repr(total))
```

Output:

```text
15,500 BIF
Money(amount=15500, currency='BIF')
```

## Do not mutate unexpectedly

For value-like objects, this is usually better:

```python
return Money(self.amount + other.amount, self.currency)
```

than this:

```python
self.amount += other.amount
return self
```

Users normally expect:

```python
a + b
```

to produce a new value rather than silently modify `a`.

# 13. Reverse arithmetic: `__radd__`

What happens here?

```python
10 + money
```

Python first tries:

```python
int.__add__(10, money)
```

If that cannot handle the custom object, Python may try:

```python
Money.__radd__(money, 10)
```

Example:

```python
class Money:
    def __init__(self, amount, currency="BIF"):
        self.amount = amount
        self.currency = currency

    def __add__(self, other):
        if isinstance(other, Money):
            if self.currency != other.currency:
                raise ValueError("Currencies must match.")

            return Money(
                self.amount + other.amount,
                self.currency,
            )

        if isinstance(other, (int, float)):
            return Money(
                self.amount + other,
                self.currency,
            )

        return NotImplemented

    def __radd__(self, other):
        return self.__add__(other)

    def __repr__(self):
        return f"Money({self.amount!r}, {self.currency!r})"
```

```python
monthly_costs = [
    Money(1000),
    Money(2500),
    Money(500),
]

print(sum(monthly_costs))
```

This may fail because `sum()` starts with:

```python
0 + first_item
```

So implement `__radd__` and allow zero:

```python
class Money:
    def __init__(self, amount, currency="BIF"):
        self.amount = amount
        self.currency = currency

    def __add__(self, other):
        if isinstance(other, Money):
            if self.currency != other.currency:
                raise ValueError("Currencies must match.")

            return Money(
                self.amount + other.amount,
                self.currency,
            )

        if isinstance(other, (int, float)):
            return Money(
                self.amount + other,
                self.currency,
            )

        return NotImplemented

    def __radd__(self, other):
        if other == 0:
            return self

        return self.__add__(other)

    def __repr__(self):
        return f"Money({self.amount!r}, {self.currency!r})"
```

```python
monthly_costs = [
    Money(1000),
    Money(2500),
    Money(500),
]

print(sum(monthly_costs))
```

Output:

```text
Money(4000, 'BIF')
```

# 14. In-place arithmetic: `__iadd__`

This controls augmented assignment:

```python
a += b
```

Python tries:

```python
__iadd__
```

Example:

```python
class Counter:
    def __init__(self, value=0):
        self.value = value

    def __iadd__(self, amount):
        self.value += amount
        return self

    def __repr__(self):
        return f"Counter({self.value})"
```

```python
counter = Counter(10)

counter += 5

print(counter)
```

Output:

```text
Counter(15)
```

## Important concept

For mutable objects, in-place operations often modify the object.

For immutable value objects, you may omit `__iadd__`; Python can fall back to:

```python
a = a + b
```

Do not implement in-place operations if mutation would surprise users.

# 15. Unary operators

|---|---|
| `-obj` | `__neg__` |
| `+obj` | `__pos__` |
| `abs(obj)` | `__abs__` |
| `~obj` | `__invert__` |

Example:

```python
class Temperature:

```


```text

Temperature(10)
```

```python
__getitem__
```

```python
class TicketQueue:
```

```python
queue = TicketQueue([
```

# 17. `__setitem__` and `__delitem__`

These support assignment and deletion by index or key.

```python
class TicketQueue:
    def __init__(self, tickets):
        self._tickets = list(tickets)

    def __getitem__(self, index):
        return self._tickets[index]

    def __setitem__(self, index, value):
        if not isinstance(value, str) or not value.strip():
            raise ValueError(
                "Ticket title must be a non-empty string."
            )

        self._tickets[index] = value.strip()

    def __delitem__(self, index):
        del self._tickets[index]

    def __repr__(self):
        return f"TicketQueue({self._tickets!r})"
```

```python
queue = TicketQueue([
    "Cannot log in",
    "Payment failed",
])

queue [docs.python](https://docs.python.org/3/reference/datamodel.html?highlight=setattr) = "Payment verification failed"

del queue[0]

print(queue)
```

Output:

```text
TicketQueue(['Payment verification failed'])
```

# 18. Membership: `__contains__`

To support:

```python
value in obj
```

define:

```python
__contains__
```

```python
class AllowedRoles:
    def __init__(self, roles):
        self._roles = set(roles)

    def __contains__(self, role):
        return role in self._roles
```

```python
roles = AllowedRoles({"admin", "agent", "viewer"})

print("admin" in roles)
print("guest" in roles)
```

Output:

```text
True
False
```

Python’s operator mapping includes containment tests: `item in container` corresponds to the relevant containment protocol. [docs.python](https://docs.python.org/3/library/operator.html)

## Do you always need `__contains__`?

No.

If an object is iterable, Python can often check membership by iterating through it.

But implementing `__contains__` can be clearer and faster when your internal structure supports efficient membership checks, such as a `set`.

# 19. Iteration: `__iter__`

To support:

```python
for item in obj:
    ...
```

define:

```python
__iter__
```

```python
class TicketQueue:
    def __init__(self, tickets):
        self._tickets = list(tickets)

    def __iter__(self):
        return iter(self._tickets)
```

```python
queue = TicketQueue([
    "Cannot log in",
    "Payment failed",
    "Feature request",
])

for ticket in queue:
    print(ticket)
```

Output:

```text

Payment failed
Feature request
```

`__iter__` should return an iterator object. For mapping-like objects, iteration conventionally yields keys. [docs.python](https://docs.python.org/3/reference/datamodel.html?highlight=setattr)

## Combining container methods

```python
class TicketQueue:
    def __init__(self, tickets=()):

        return ticket in self._tickets

    def __repr__(self):
        return f"TicketQueue({self._tickets!r})"
```

Now it behaves naturally:

# 20. Building an iterator with `__next__`

An iterator is an object that remembers its current position.

It supports:

```python
__iter__()
__next__()
```

Example:

```python
class Countdown:
    def __init__(self, start):
        self.current = start

    def __iter__(self):
        return self

    def __next__(self):
        if self.current < 0:
            raise StopIteration

        value = self.current
        self.current -= 1

        return value
```

```python
countdown = Countdown(3)

for number in countdown:
    print(number)
```

Output:

```text
3
2
1
0
```

## Iterator protocol

Conceptually:

```python
iterator = iter(countdown)
```

Python calls:

```python
countdown.__iter__()
```

Then repeatedly:

```python
next(iterator)
```

which calls:

```python
iterator.__next__()
```

When the iterator has no more values, it must raise:

```python
StopIteration
```

## Container versus iterator

A **container** can create a fresh iterator each time:

```python
def __iter__(self):
    return iter(self._items)
```

An **iterator** often returns itself:

```python
def __iter__(self):
    return self
```

For most application-level collection classes, prefer the container style. It makes repeated loops work correctly.

# 22. `__call__`: make an object callable

If a class defines:

```python
__call__
```

then its objects can be called like functions.

```python
class TextCleaner:
    def __call__(self, text):
        return text.strip().lower()
```

```python
clean_text = TextCleaner()

print(clean_text("  TRUSTDESK AI  "))
```

Output:

```text
trustdesk ai
```

This works because:

```python
clean_text("  TRUSTDESK AI  ")
```

is conceptually like:

```python
clean_text.__call__("  TRUSTDESK AI  ")
```

## AI-pipeline use case

```python
class NormalizeText:
    def __call__(self, text):
        return text.strip().lower()
```

```python
class RemovePunctuation:
    def __call__(self, text):
        return "".join(
            character
            for character in text

```

```python
pipeline = [
```

- A normal function
- A lambda
- A class instance with `__call__`
- A third-party callable

# 23. Context managers: `__enter__` and `__exit__`

The `with` statement is powered by special methods.

```python
with resource as value:
    ...
```

uses:

```python
__enter__
__exit__
```

Example:

```python
class DatabaseSession:
    def __enter__(self):
        print("Opening database connection.")
        return self

    def query(self, sql):
        return f"Running query: {sql}"

    def __exit__(self, exc_type, exc_value, traceback):
        print("Closing database connection.")
```

```python
with DatabaseSession() as session:
    print(session.query("SELECT * FROM tickets"))
```

Output:

```text
Opening database connection.
Running query: SELECT * FROM tickets
Closing database connection.
```

## Why context managers matter

They guarantee cleanup even if an exception happens.

```python
with DatabaseSession() as session:
    result = session.query("SELECT * FROM tickets")
    raise RuntimeError("Unexpected error")
```

Python still calls:

```python
__exit__()
```

before propagating the error.

## Exception handling in `__exit__`

```python
def __exit__(self, exc_type, exc_value, traceback):
    ...
```

Arguments:

| Parameter | Meaning |
|---|---|
| `exc_type` | Exception class, such as `ValueError` |
| `exc_value` | Exception object |
| `traceback` | Traceback information |

If `__exit__` returns:

```python
True
```

it suppresses the exception.

Example:

```python
class IgnoreValueErrors:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        return exc_type is ValueError
```

```python
with IgnoreValueErrors():
    raise ValueError("This error is suppressed.")
```

Use exception suppression very carefully. In production, silently suppressing unexpected errors can hide data loss, security issues, and failed operations.

# 24. Attribute access methods

These are powerful and should be used carefully.

| Syntax | Special method |
|---|---|
| `obj.attribute` | `__getattribute__()` |
| Missing `obj.attribute` | `__getattr__()` |
| `obj.attribute = value` | `__setattr__()` |
| `del obj.attribute` | `__delattr__()` |

## `__getattr__`: handle missing attributes

`__getattr__` runs only when normal lookup fails.

```python
class Config:
    def __init__(self, values):
        self._values = values

    def __getattr__(self, name):
        try:
            return self._values[name]
        except KeyError as error:
            raise AttributeError(
                f"Configuration has no setting named {name!r}."
            ) from error
```

```python
config = Config({
    "debug": True,
    "model_name": "ticket-classifier-v1",
})

print(config.debug)
print(config.model_name)
```

Output:

```text
True
ticket-classifier-v1
```

Missing key:

```python
print(config.port)
```

Output:

```text
AttributeError: Configuration has no setting named 'port'.
```

## `__getattribute__`: intercept all access

`__getattribute__` runs for **every** attribute access.

```python
class Example:
    def __getattribute__(self, name):
        print(f"Reading: {name}")
        return super().__getattribute__(name)
```

This is advanced because it is easy to create infinite recursion.

Incorrect:

```python
def __getattribute__(self, name):
    return self.name
```

This calls `__getattribute__` again forever.

Use it only when you have a strong reason, such as proxies, tracing, lazy loading, security layers, or framework internals.

***

# 25. `__setattr__`: controlled assignment

```python
class User:
    def __setattr__(self, name, value):
        if name == "age" and value < 0:
            raise ValueError("Age cannot be negative.")

        super().__setattr__(name, value)
```

```python
user = User()

user.age = 20
print(user.age)
```

Invalid:

```python
user.age = -5
```

Output:

```text
ValueError: Age cannot be negative.
```

## But prefer properties for normal validation

For a small number of controlled attributes, this is clearer:

```python
class User:
    def __init__(self, age):
        self.age = age

    @property
    def age(self):
        return self._age

    @age.setter
    def age(self, value):
        if value < 0:
            raise ValueError("Age cannot be negative.")

        self._age = value
```

Use `__setattr__` only when you genuinely need universal assignment behavior across many attributes.

***

# 26. `__delattr__`: controlled deletion

```python
class ProtectedConfig:
    def __init__(self, api_url):
        self.api_url = api_url

    def __delattr__(self, name):
        if name == "api_url":
            raise AttributeError(
                "api_url cannot be deleted."
            )

        super().__delattr__(name)
```

```python
config = ProtectedConfig(
    "https://api.example.com"
)

del config.api_url
```

Output:

```text
AttributeError: api_url cannot be deleted.
```

Again, this is specialized. Prefer simple class design and properties for normal application logic.

# 27. `__slots__`: restricting object attributes

You encountered `__slots__` during encapsulation.

```python
class Point:
    __slots__ = ("x", "y")

    def __init__(self, x, y):
        self.x = x
        self.y = y
```

```python
point = Point(3, 4)

point.z = 5
```

Output:

```text
AttributeError: 'Point' object has no attribute 'z'
```

`__slots__` defines the allowed instance attribute names and can reduce memory use when you create many instances. It does not make attributes private or secure.

Python implements slots at the class level using descriptors. [docs.python](https://docs.python.org/3/reference/datamodel.html?highlight=setattr)

Use it when:

- You will create many small objects.
- The set of attributes is intentionally fixed.
- You want to prevent accidental new attributes such as `obj.nmae = "typo"`.

Avoid it early in a project if you need flexibility, multiple inheritance, dynamic attributes, or simple debugging.

***

# 28. `__del__`: finalizers—usually avoid

```python
class Example:
    def __del__(self):
        print("Object is being cleaned up.")
```

`__del__` may run when an object is garbage-collected.

However, you should usually avoid relying on it because:

- The timing is not predictable.
- It may run during interpreter shutdown in a partially destroyed environment.
- Reference cycles can make cleanup complicated.
- Exceptions inside it can be ignored or printed unpredictably.
- It is not a reliable replacement for explicit cleanup.

Prefer:

```python
with resource:
    ...
```

using `__enter__` and `__exit__`, or provide an explicit `.close()` method.

# 29. A complete real-world class

Here is a `TicketCollection` class that behaves like a Python collection.

```python
class Ticket:
    def __init__(self, ticket_id, title, priority="normal"):
        self.ticket_id = ticket_id
        self.title = title
        self.priority = priority

    def __repr__(self):
        return (
            f"Ticket("
            f"ticket_id={self.ticket_id!r}, "
            f"title={self.title!r}, "
            f"priority={self.priority!r}"
            f")"
        )

    def __str__(self):
        return (
            f"[{self.priority.upper()}] "
            f"{self.ticket_id}: {self.title}"
        )

    def __eq__(self, other):
        if not isinstance(other, Ticket):
            return NotImplemented

        return self.ticket_id == other.ticket_id

    def __hash__(self):
        return hash(self.ticket_id)
```

```python
class TicketCollection:
    def __init__(self, tickets=()):
        self._tickets = list(tickets)

    def add(self, ticket):
        if not isinstance(ticket, Ticket):
            raise TypeError("Only Ticket objects can be added.")

        self._tickets.append(ticket)

    def __len__(self):
        return len(self._tickets)

    def __iter__(self):
        return iter(self._tickets)

    def __getitem__(self, index):
        return self._tickets[index]

    def __contains__(self, ticket):
        return ticket in self._tickets

    def __repr__(self):
        return f"TicketCollection({self._tickets!r})"

    def __str__(self):
        if not self._tickets:
            return "TicketCollection(empty)"

        return "\n".join(
            str(ticket)
            for ticket in self._tickets
        )
```

Usage:

```python
tickets = TicketCollection()

tickets.add(
    Ticket(
        "T-001",
        "Cannot log in",
        "high",
    )
)

tickets.add(
    Ticket(
        "T-002",
        "Payment verification failed",
        "medium",
    )
)
```

Now it supports natural Python syntax:

```python
print(tickets)
```

```text
[HIGH] T-001: Cannot log in
[MEDIUM] T-002: Payment verification failed
```

```python
print(len(tickets))
```

```text
2
```

```python
print(tickets[0])
```

```text
[HIGH] T-001: Cannot log in
```

```python
for ticket in tickets:
    print(ticket.ticket_id)
```

```text
T-001
T-002
```

```python
print(
    Ticket("T-001", "Different title")
    in tickets
)
```

```text
True
```

That final membership check works because `Ticket.__eq__()` compares objects by `ticket_id`.

# 30. Common mistakes

## Calling dunder methods directly

Avoid:

```python
ticket.__str__()
money.__add__(other_money)
queue.__len__()
```

Prefer:

```python
str(ticket)
ticket + other_money
len(queue)
```

Why? The built-in syntax may apply Python’s full protocol behavior, including reflected operations and fallbacks. The official `operator` module also provides readable functional equivalents, such as `operator.add(a, b)` for `a + b`. [docs.python](https://docs.python.org/3/library/operator.html)

***

## Returning the wrong type

These methods have strict expectations.

```python
def __str__(self):
    return 123  # Wrong
```

`__str__` must return a string.

```python
def __len__(self):
    return "3"  # Wrong
```

`__len__` must return a non-negative integer.

```python
def __bool__(self):
    return "yes"  # Wrong
```

`__bool__` must return a Boolean.

***

## Mutating values in `__add__`

Avoid surprising behavior:

```python
def __add__(self, other):
    self.amount += other.amount
    return self
```

Most users expect:

```python
new_total = a + b
```

to leave `a` and `b` unchanged.

Use `__iadd__` for deliberate in-place mutation:

```python
a += b
```

***

## Ignoring `NotImplemented`

For binary operators and comparisons, return:

```python
NotImplemented
```

when the other operand is unsupported.

```python
def __add__(self, other):
    if not isinstance(other, Money):
        return NotImplemented

    return Money(self.amount + other.amount)
```

This lets Python use the normal operator-resolution rules.

***

## Making mutable objects hashable

Do not use mutable fields in `__hash__`.

Bad:

```python
class User:
    def __init__(self, name):
        self.name = name

    def __hash__(self):
        return hash(self.name)
```

If `name` changes after placing the object in a `set` or using it as a dictionary key, your program can behave incorrectly.

***

## Overusing magic

Do not implement a special method merely because you can.

Question:

> Does this operation have the meaning Python users expect?

Good:

```python
cart + item
len(queue)
ticket in ticket_collection
for row in dataset
```

Potentially confusing:

```python
user + 5
database[0]
model / prompt
```

unless the meaning is genuinely obvious in your domain.

# 34. Final mental model

Special methods make your classes participate in Python’s language features.

```python
print(obj)      # __str__
repr(obj)       # __repr__
len(obj)        # __len__
obj == other    # __eq__
obj + other     # __add__
obj[index]      # __getitem__
item in obj     # __contains__
for x in obj:   # __iter__
obj()           # __call__
with obj:       # __enter__ / __exit__
```

The best learning order is:

1. Master `__init__`, `__repr__`, and `__str__`.
2. Learn `__eq__` and understand `__hash__`.
3. Learn `__len__`, `__iter__`, `__getitem__`, and `__contains__`.
4. Practice `__add__`, `__radd__`, and `NotImplemented`.
5. Learn `__call__` for callable objects and pipelines.
6. Learn `__enter__` and `__exit__` for safe resource management.
7. Treat `__new__`, `__getattribute__`, `__setattr__`, `__slots__`, and `__del__` as advanced tools—use them only when their behavior is clearly needed.

The core principle is simple: implement a dunder method only when your object should honestly behave like the corresponding built-in Python concept. Python then handles the syntax and protocol integration for you. [docs.python](https://docs.python.org/3/reference/datamodel.html?highlight=setattr)
